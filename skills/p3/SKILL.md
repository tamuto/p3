# p3 でこのプロジェクトの作業を管理する

このリポジトリの作業は、infodb p3 の **要望** と、要望から生まれた **タスク** で管理する。
要望・タスク・Preflight の記録は「データのフォルダ」にファイルで置かれ、人と AI が同じ CLI で操作する。
データのフォルダのファイルは直接編集しない。必ず CLI を通す。

## CLI の呼び方

```bash
P3_ACTOR=ai:<エージェント名> p3 <コマンド> [引数] --json
```

- `p3` が入っていなければ `pnpx @infodb/p3 <コマンド>` で同じように動く（`npx @infodb/p3` でもよい）
- 最初に `p3 whoami --json` で、操作するプロジェクト・データのフォルダ・決まり方（`via`）・変更者・今の要望・Preflight の担当
  （`preflight.runner`。下の「Preflight を頼まれたとき」）を確かめる。
  対象のプロジェクトは今いる場所（リポジトリ・作業ツリー）と個人設定から決まる。決まらなければ、出てきた一覧と案内に従って
  `--project <名前>` を付ける（名前を推測で決めない）
- `via` が `cwd`（今いる場所で決まった）でなければ（`dir` / `project` / `legacy` / `only`）、それ以上 p3 を操作せず、
  対象のプロジェクトでよいかユーザーに確かめる。特に `only` は登録が1つだけというだけで、p3 を使わないフォルダでも決まる。
  推測した `--project` や `--dir` を付けて確認を避けない。ユーザーが対象を指定した・確かめた後は、その対象のまま続ける
- プロジェクトが無い・登録されていない（未登録）ときは、`p3 init`・`p3 join` を自分から実行しない。新しく作る（`init`）のか、
  共有されたものに参加する（`join`）のかをユーザーに確かめる
- `P3_ACTOR=ai:<名前>` は変更者の記録。変更するコマンドには必ず付ける
- 結果は `--json` で読む。人に見せる表はオプションなしの出力でよい
- 終了コード: 0 成功 / 1 使い方の誤り（メッセージに次にすることが出る）/ 2 見つからない / 3 競合（`show --brief` で読み直してやり直す）
- 詳細は、作業に使うときは短い出力 `show <要望ID>/T003 --brief --json` / `request show <要望ID> --brief --json` で読む
  （本文・状態・rev・依存とその状態・置き換えの注意・成果物・ブランチだけが出る）
- 迷ったら `p3 help`

## 人と AI の役割

| 操作 | するのは |
| --- | --- |
| 要望の登録（`request new`） | AI も人も |
| Preflight（評価・細分化。`preflight`） | 担当（`whoami --json` の `preflight.runner`）で決まる。**codex** は人（人がチャットで対象の要望の手元の評価を明示的に頼んだときだけ AI が評価する）、**agent** は人に頼まれた AI（手元で評価する）。どちらも AI から始めない（下の「Preflight を頼まれたとき」） |
| タスク化（`accept`） | **人だけ** |
| タスクの着手・完了（`move ... doing` / `done`）と成果物の登録、作業中に見つけたタスクの追加 | AI も人も |
| 要望を対応済にする（`request set <要望ID> status=resolved`） | 作業を終えた AI（か人） |
| 要望の完了済（`done`）・見送り（`rejected`）、タスクの済み（`check`） | **人だけ** |

## 要望を登録する（ユーザーから新しい作業を頼まれたとき）

1. `request new "<タイトル>" --body "<背景・やりたいこと・完了条件を箇条書きで>"`（任意で `--area src/web --tag ui --due YYYY-MM-DD --milestone <id>`）
2. 登録したら要望 ID をユーザーに伝えて終える。**Preflight（評価・細分化）は自分から始めず、タスク化（`accept`）は人が行う。**
   Preflight を勧めたり、実行してよいか尋ねたりもしない。人に Preflight を頼まれたら、下の「Preflight を頼まれたとき」に従う
   （担当で分ける）。人がタスク化を終えたら、タスクを進める

人が行った Preflight の内容を聞かれたら、`drafts <要望ID>` で評価とタスク案を読んで答えてよい（読むだけ）。
`drafts` には「調べた範囲」（参照先ごとに読んだか）と「判断の根拠」（確かめた / 推測）も出る。答えるときは、見ていない参照先や
推測の根拠に基づく判断であることを伝える。参照先の登録（`repo add` / `repo path`）はユーザーに頼まれたときだけ行う。
評価の確認事項（questions）への回答を頼まれたら、`preflight <要望ID> --note "..." --note-only` でメモとして残す（実行はしない）。

## Preflight を頼まれたとき（担当で分ける）

誰が Preflight を実行するかは、プロジェクトの担当（`whoami --json` の `preflight.runner`）で決まる。担当は人が
`p3 init` か `p3 config set preflight.runner=...` で決める（AI は変えない）。

- **`codex`**（`preflight` の項目が無い古い p3 も同じ）: Preflight は人が `p3 preflight` か画面から実行する（Codex が評価する）。
  AI は `p3 preflight <要望ID>`（`--prepare` の無い通常の実行）をしない。人がチャットで対象の要望を挙げて、手元の評価を明示的に
  頼んだとき（例: 「要望 261009-k7m3x の Preflight を Claude Code のこのチャットで実行して」）だけ、下の手順で評価する。
  「Preflight して」とだけ頼まれたら、断らずに、人が `p3 preflight <要望ID>`・画面で実行するのか、このチャットで手元の評価をするのかを確かめる
- **`agent`**（Codex を使えない環境）: 人に Preflight を頼まれたら（「Preflight して」「要望 <ID> の Preflight をして」など。
  「このチャットで」のような言い方は求めない）、下の手順で手元で評価する。`p3 preflight <要望ID>`（`--prepare` の無い通常の実行）はしない
- **`runner` が `null`**（担当が読めない。理由は `problem`）: `agent` と推測しない。`problem` を人に伝え、`codex` と同じ扱いにする
- どの担当でも: 要望の登録・タスクの作業・子の要望の作成・分割の採用のついでに自分から始めない（勧めたり、実行してよいか尋ねたりも
  しない）。対象の要望が分からなければ確かめる。子の要望も親と同じ担当・同じ手順。P3 はモデルを呼ばない（`claude -p` や API キーは使わない）

1. `whoami --json` で対象のプロジェクトと担当を確かめ（`via` の扱いは上と同じ）、`request show <要望ID> --brief --json` で頼まれた要望かを確かめる
2. 準備: `preflight <要望ID> --prepare --json`（変更なので `P3_ACTOR` を付ける）。評価対象を固定し、`instructions`（指示のファイル）・
   `outputs`（書く成果物）・`run`（PF-...）・`next`（次のコマンド）を返す。始められない（同じ要望の Preflight が待っている・実行中）
   ときは止めて人に伝える（自分の判断で `--cancel` しない。`--acknowledge-stopped` は、人が run の止まっていることを確かめて
   中断にするよう頼んだときだけ）
3. `instructions` のファイルを最後まで読み、その「制約」に従って評価する。指示の長い文はスキルに写さない（P3 が要望ごとに作る）。
   参照先は読むだけ（変更・git の書き込み・アプリの起動をしない）。書き込むのは `outputs` に挙がった、その run の成果物だけ
   （`assessment.json`・`drafts/`・`children/`・`ui/index.json`・`ui/src/`）。これが「データのフォルダを直接編集しない」の唯一の例外で、
   `run.json`・`instructions.md`・ほかの要望やタスクのファイルは書かない。指示のファイル・添付・参照先が読めなければ、読んだことにせず、
   評価に未確認として書く（読めない理由も人に伝える）
4. 書き終えたら `preflight <要望ID> --complete --run <run> --json`。`code: invalid_result` なら `problems` を直して同じコマンドをやり直す
   （run は待ったまま。ファイルを消して作り直さない）
5. `drafts <要望ID>` で取り込んだ評価（判定・確認事項・タスク案か子の案）を読み、要約を人に伝えて終える。**タスク化（`accept`）・タスクの着手はしない**
   （人が案を確かめて採用してから、「タスクを進める」に従う）
- 人にやめるよう頼まれたら `preflight <要望ID> --cancel --run <run>`

## タスクを進める

作業は **作業先のリポジトリの、要望のブランチ** で行う。タスクごとの作業先とブランチは
`show <要望ID>/T003 --brief --json` の `work`（`repo`・`branch`）に出る（要望全体は `request show <要望ID> --brief --json` の `branches`）。

1. 作業先に入る: `work.repo` のリポジトリ（場所は `repo ls`）で、`work.branch` に切り替える（無ければ最新の既定のブランチから作る。
   作業ツリーを使うかどうかと置き場所は任せる）。`work.repo` が `null`（作業先なし: 調査・人の判断など）なら移動は要らない。ブランチの無い
   作業先（git でないフォルダ）はそのフォルダで作業する。このマシンのパスが未登録（`work.registered` が false）なら、場所をユーザーに
   聞いて登録してもらい（`repo path <名前> <パス>`）、`whoami` で今の要望と今いる参照先を確かめてから始める
2. `ls --req <要望ID>` で一覧、`show <要望ID>/T003 --brief --json` で中身と依存を読む。`dependencies` の `status` が
   `done` でない依存があるタスクから始めない（`null` は相手が見つからない。完了とは扱わず、ユーザーに確かめる）。
   **置き換えられたタスク**（`ls` の `※置換`、`--json` の `superseded` と `warnings`）からは始めない。残っていれば扱いをユーザーに確かめる
   （不要ならユーザーの了承を得て `archive`）。`move` が警告（`warnings`）を返したら、作業を止めてユーザーに伝える
   **受け入れ基準**（`--brief --json` の `item.acceptanceCriteria`。A1, A2, ...）があれば、着手する前に読み、何を確かめれば完了かを
   決めてから作業する（無いタスクは本文の完了条件で判断する）。`[Q1]` で始まる基準はプロジェクトの品質基準
   （`p3 quality`）から取り込んだもので、確認の方法（検査のコマンドと成功の条件か、人の確認の方法）が書いてある
3. 着手: `move T003 doing --req <要望ID>`
4. 作業し、プロジェクトのテストを通したら、**コミットする前に** 完了にする:
   `move T003 done --req <要望ID> --output <成果物> --record - < record.md`（成果物が複数あれば `--output` を繰り返す）。
   成果物は今あるもの（変えたファイル・ドキュメントのパスや短い説明）。まだ無い URL や仮のコミットの SHA は書かない（URL は 8 で足す）。
   **変更の記録（`--record`）は必須**: 何を変えたか（振る舞いの言葉で）・なぜ・入れた決まり・やめたもの を Markdown で短く書く。
   後の Preflight が経緯を調べるとき、タスクの解析・リリースノートの材料として読む（パスの羅列ではなく、目的と決まりを書く）。
   テストが通っていない・作業が途中のうちは完了にしない。
   **受け入れ基準があるタスクは、完了と同時に基準ごとの証拠を残す**: `--evidence-file evidence.md`（見出し `## A1 met` ごとに、
   通したテスト・実行したコマンドと結果・画面で確かめたこと・成果物の場所を書く。`--record -` と標準入力を取り合うので証拠はファイルで）。
   結果は `met`（満たした。証拠が要る）/ `unmet`（満たせなかった）/ `unverified`（確かめていない）で、満たせなかった・確かめて
   いない項目はそうと理由を正直に書く（推測で `met` にしない）。証拠は自分の申告で、レビューの判定ではない。
   変更の記録（`--record`）は何を変えたか・なぜ、証拠は基準ごとの確かめた材料で、役割が違う（両方書く）。
   未達・未検証を残して完了にしたら、そのことと理由をユーザーに伝える（不足があっても完了は拒まれないが、済みにするかは人が決める）。
   後から証拠を足す・直すなら `evidence <T> <ID> <結果> --file 本文.md`。
   品質基準の検査は作業する側（あなた）が実行し、証拠には実行したコマンド・参照先とコミット（未コミットならそう書く）・結果・確かめた
   範囲・省いたならその理由を書く。P3 が実行して確かめたとは書かない（P3 はコマンドを実行しない）
5. 作業中に見つけた追加の作業は `new "<タイトル>" --req <要望ID> --body "..."` でタスクにする（タスクの関係は Preflight のタスク化が張るもので、手では張らない。順序は本文に書く）
   **進められなくなったら止まっている理由を付けて終える**（安全に続けられる通常の修正・調査の途中では使わない）:
   人の判断や権限が要る・前提が崩れた・直しても調べてもテストが通らず先に進めない、などでこのタスクを続けられなくなったら、
   `block <T> --req <要望ID> --reason "<具体的な理由>" --decision "<人に決めてほしいこと>" --json`（複数行は `--reason -` で標準入力）。
   人への質問を新しいタスクにする代わりに、今のタスクに付ける。未着手の依存待ちのタスクを作業中にしてまで付けない。
   返った JSON の `block` で保存できたことを確かめ、要望とタスクの ID・理由・いつから（`since`）・答えてほしいこと・確かめたこと・
   再開のしかたをユーザーに伝えて、そのタスクの作業を終えて回答を待つ。止まったまま完了・済み・要望の対応済に進めない
   （止まったままは完了へ動かせない）。止まっていることを避けるために基準や証拠を書き換えない。停止の履歴と完了の変更の記録（`record`）は別。
   保存が競合・失敗したら読み直して結果を確かめ、記録できたと偽らずに伝える（タスクを変え続けて理由を覆い隠さない）
   **回答を受けたら解除して再開する**: `unblock <T> --req <要望ID> --resolution "<回答・解決の内容>"`。人が先に解除していたら、
   `show <T> --json` の停止の履歴で回答を読み、前提が満たされたことを確かめてから再開する。解除だけでは自動で再開しない。
   新しい理由で止まったら、新しい停止として付ける
6. 要望のタスクが全部完了したら（`ls --req <要望ID>` が全部 done、成果物と検証も済み）、コミットする前に要望を **対応済** にする:
   `request set <要望ID> status=resolved --json`。未完了のタスクがあると拒否される（終わらせるか、不要ならユーザーの了承を得て
   `archive`）。拒否をタスクを偽って完了にする・ファイルを直接書き換えるなどで回避しない
7. コミットして push する。データのフォルダ（`whoami` の場所）がこの作業ツリーの中にあって git で管理されている（無視されていない）なら、
   **要望のフォルダ（`<データのフォルダ>/requests/<要望ID>/`）の変更も実装と同じコミットに入れる**。要望とタスク・変更の記録が
   コードと一緒に残り、後のレビュー（AI のレビューも）で、コードだけでなく「何を目的に頼まれ、何をしたか」を精査できる。
   親子でつながる要望のフォルダも、まだコミットに入っていない変更があれば入れる: 子の要望なら**祖先の要望のフォルダ**（分割の採用・
   子の順・状態は親に残る）、親を対応済にするときは**子孫の要望のフォルダ**（見送りにした子など、実装の無い要望）。それ以外の要望や
   関係ない変更はまとめて add しない（`git status` でフォルダを確かめてから add する）。データのフォルダが外・別のリポジトリ・git で無視されている、または git の作業ツリー（worktree）で作業して
   いてデータがメインの作業ツリーにあるときは、同じコミットには入らない（データの移動・写し・`git add -f` はしない。記録は p3 に
   残り、コードとは成果物の URL で結ぶ）。commit・push に失敗したら、完了の記録はそのまま残し、公開できていないことをユーザーに
   伝えてやり直す（完了を push できたことのように伝えない）。同じコミットに入れた要望のフォルダは、
   マージするまで要望のブランチにしか無い。既定のブランチに切り替えると、その要望（子なら親の子の一覧からも）が消えたように見えるが、
   データはブランチにある（作り直したり、別のブランチから写したりしない。親の詳細には `child_missing` が出る）
8. コミットや PR の URL を残すなら、後から `move T003 done --req <要望ID> --output <URL>` で足す（完了・記録・前の成果物はそのまま。
   完了から戻さない）。要望のフォルダを同じコミットに入れているなら、この追記もコミットして同じブランチに push する（追記のコミット
   自身の URL は残さなくてよい）。PR はユーザーに確認してから作る（本文に要望 ID とタスクの一覧）。作った PR の URL は最後のタスクに
   足す。複数のリポジトリにまたがる要望は、関係するリポジトリの PR を全部 `--repo-output <参照先の名前>=<PR の URL>` で最後のタスクに
   残す（例: `move T005 done --repo-output app=<URL> --repo-output infra=<URL>`。1つのリポジトリなら今までどおり `--output` でよい）。
   マージ・要望の完了済（`done`）は人が行う
9. 対応済の後にタスクを足した・完了から戻したときは、要望は自動で進行中に戻る（`--json` の `reopened`）。
   終えたらもう一度 6 で対応済にする

### 子の要望（大きい要望を分けたもの）

- 子の要望（`parent` のある要望）は、親とは別の要望として、子ごとのタスクとブランチで作業する（親のタスクにしない。
  手順は上と同じ）。親子は `request show <要望ID> --brief --json` の `parent`・`ancestors`・`children` で読む
- 分割の案（Preflight の子の案）の採用（`accept`）は人が行う。子の Preflight は親と同じく、頼まれたときだけ
  「Preflight を頼まれたとき」の担当に従う（分割の採用・子の作成から、自分で子の評価へ進まない）
- 子のタスクを全部終えたら、子を対応済にする（6）。親を対応済にするのは、親のタスクと見送り以外の子（`children`）が
  全部 対応済か完了済になってから。条件を満たさなければ拒否される（理由が出る）
- 子にタスクを足す・完了から戻すと、対応済の親も進行中に戻る（`--json` の `reopenedAncestors`）。完了済の親は変わらず
  `warnings`（`ancestor_done`）が出るので、作業を止めて人に伝える

## してはいけないこと

- Preflight（`preflight`）を自分から始めない・勧めない。`p3 preflight <要望ID>`（Codex で評価する通常の実行）は人が行い、AI は
  しない。手元の評価（`--prepare` / `--complete`）は、上の「Preflight を頼まれたとき」の担当ごとの条件を満たしたときだけ
- タスク化（`accept`）をしない（人が行う。Preflight を頼まれたときも、評価の後にタスク化・着手へ進まない）
- `check`（済み）を付けない。済みは人が成果物を確認して付ける
- 要望のステータスを `done`（完了済）/ `rejected`（見送り）にしない（人が決める）。AI がするのは作業を終えたときの `resolved`（対応済）まで。
  タスク化で `active` になるのは自動
- タスクを要望をまたいで動かさない。別の要望の作業なら、その要望にタスクを足すか、新しい要望を提案する
- データのフォルダ（`p3 whoami` に出る場所）や個人設定（`~/.config/infodb-p3/`）のファイルを直接書き換えない
  （例外は、頼まれた Preflight で `--prepare` が返した run の成果物だけ）
- 人への質問をタスクにしない（続けられないなら今のタスクに止まっている理由を付ける）
- 止まっている理由を付けたまま作業を続けたり、完了・済み・対応済に進めたりしない。回答を受けずに自分で解除しない
- タスクの AI レビュー（`review`）を頼まれずに始めない（Codex を使い、利用者のプランを消費する）。頼まれたら Preflight と同じく担当で
  分け、`agent` のプロジェクトでも Codex で実行するのは人が明示したときだけ（`--engine codex`）。レビューの結果を理由に済みにしない・
  基準や証拠を書き換えない（結果は参考の記録で、済みは人が決める）
- 受け入れ基準を自分で消す・書き換える・並べ替えて、満たしたことにしない（基準を変える必要があれば人に確かめる。済みのタスクの
  基準・証拠を変えると人の済みが外れる）。確かめていない項目を `met` にしない

## 状況を報告する

- 全体: `progress`（マイルストーンごと）。要望の中: `ls --req <要望ID>`
- 画面はユーザーが `p3 serve` で開く（既定 http://localhost:4310）。CLI の変更はそのまま画面に反映される
