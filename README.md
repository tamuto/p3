# infodb p3（P³）

> 正式名称は **infodb p3**。`pnpx @infodb/p3` で CLI を起動する。
> 旧名 `pcube` の名残として、`pcube` コマンド（`p3` と同じ）・`.pcube/`・環境変数の `PCUBE_*` を使っている。

ファイルベースのプロジェクト管理ツール。作業の単位は **要望** で、要望ごとにフォルダを作り、
そこから生まれたタスクや評価の記録をすべてその下に置く。

最大の特徴は **Preflight** —— 要望をタスクにする前に、Codex（`codex app-server`）がリポジトリを読んで
妥当性・実現可能性・影響範囲を評価し、着手できる粒度のタスク案を **ファイルとして** 書き出す。

- 要望 = フォルダ。ブランチ（作業ツリー）は作業先のリポジトリごとに1つ。タスクは要望の中で連番（T001, T002, ...）。共有も要望単位
- タスクは AI か人が実施する。状態は 未着手 / 作業中 / 完了 の3つで固定（設定では変えない）。保留や取りやめの状態は持たず、
  手を付けないなら未着手のまま、AI が進めた作業をマージしないなら完了のまま（成果物の側で閉じる）。
  完了したタスクには成果物（PR・MR・ドキュメント）を残す。
  タスクボードは V 字（上段に未着手と完了、下段に作業中）。完了を人が確認して「済み」にするとボードから消え、対応済みの一覧に移る。
  ボードに残るのは要対応のものだけになる
- 進捗は、左に要望・右にスケジュールで横断して見る。タスクボードは要望の中で見る
- タスクは予定の日付や見積りを持たない。ステータスを変えた日時（作業中にした・完了にした）を pcube が記録し、
  完了したものは人が確認して「済み」にする
- タスク間の関係は多元的（型付き・有向・由来/確信度つきのエッジ + 構造 + 暗黙の近さ）。要望をまたぐ影響も辿れる
- DB なし。1タスク = 1 Markdown ファイル。人・AI・Codex が直接編集しても整合する
- 人も AI も同じ **CLI**（`pcube`）で操作する。ファイルを直接読み書きするので認証が要らない
- ブラウザはローカルのビューア兼エディタ（`pcube serve`）。データはすべてローカルで完結する

> 現在はプロトタイプ。設計の方針は [docs/architecture.md](docs/architecture.md) を参照。

## はじめかた

### 必要なもの

| もの | 何に使う |
| --- | --- |
| Node.js 22 以上 | P3 本体（CLI と `p3 serve`） |
| pnpm（`pnpx`）か npm（`npx`） | P3 を入れずに動かす。`pnpm add -g @infodb/p3` / `npm i -g @infodb/p3` で `p3` コマンドにしてもよい |
| Docker（`docker version` が通ること） | Preflight の Codex を、リポジトリとデータのフォルダだけを見せたコンテナの中で動かす。DevContainer の中なら、ホストの Docker デーモンに繋がること |
| Git | 管理したいリポジトリと、要望ごとのブランチ |
| ChatGPT のアカウント（プラン） | Preflight の Codex をその人のアカウントで動かす |

Codex を手元に入れる必要はない（コンテナのイメージに入れる）。画面はビルド済みのものが入っているので、ビルドも要らない。

### 最初の手順

管理したいリポジトリの中で:

```bash
pnpx @infodb/p3 init --agents      # データを置くフォルダを決めて個人設定に登録する。AI 向けの指示とスキルも置く
pnpx @infodb/p3 chatgpt login      # Preflight に使う ChatGPT プランに接続する（ブラウザが開く）
pnpx @infodb/p3 codex update       # Codex のイメージを作る（初回は数分。しなくても最初の Preflight の前に作る）
pnpx @infodb/p3 serve              # http://localhost:4310 を開き、要望を書いて Preflight → タスク化
```

以下の例では `p3` と書く（`pnpx @infodb/p3` と同じ）。マシンごとの設定（パスの対応など）は「Preflight」の
「マシンごとの設定」を参照。

### DevContainer の中で使うとき

P3 をコンテナの中で動かし、Docker はホストのデーモンを使う（docker-outside-of-docker）とき:

- **パスの対応:** Codex のコンテナはホストのデーモンが作るので、マウントするパスはホストから見たものでなければならない。
  リポジトリとデータのフォルダが、コンテナの中とホストでどこに当たるかを個人設定の `codex.pathMap` に書く
  （例: コンテナの `/workspaces` がホストの `<開いたフォルダの親>` なら `/workspaces: <そのホストのパス>`）。
  データのフォルダもホストから見える（バインドマウントされた）場所に置く
- **サインインのコールバック（1455）:** `p3 chatgpt login` は 127.0.0.1:1455 で待ち、VS Code がそのポートをホストへ転送するので、
  ホストのブラウザから届く。1455 が使えずに別のポートで待ったときや、転送先のポートが変わったとき、転送されない環境
  （SSH・別のコンテナ）では、ブラウザが「接続できません」になる。そのときは `p3 chatgpt login --paste` で、その画面の
  アドレスバーの URL を貼る
- **画面（4310）:** `p3 serve` のポートも転送して、ホストのブラウザで開く。サインインと解除は、転送された localhost の画面か CLI から行う

### P3 を開発するとき（このリポジトリから動かす）

```bash
pnpm install
pnpm build                   # 画面（p3 serve で配信する dist/web）
pnpm link --global           # `pcube` / `p3` コマンドをこのチェックアウトで使う（任意）
```

グローバルに入れずに、p3 の場所を指定して pnpm で直接動かしてもよい。管理したいリポジトリ（やその作業ツリー）の中で:

```bash
pnpm -s --dir /path/to/p3 p3 whoami     # -s で pnpm 自身の出力を抑える（--json の出力は stdout だけに出る）
```

pnpm はスクリプトをパッケージの場所で動かすが、p3 は呼び出し元の場所（pnpm が渡す `INIT_CWD`）に戻ってから
対象のプロジェクト・今の要望（作業ツリーのブランチ）・git のユーザーを判定する。

### プロジェクトの始め方

管理したいリポジトリの中（どの作業ツリー・サブフォルダからでもよい）で `p3 init` を実行し、
プロジェクト名と **データを置くフォルダ** を決める。データのフォルダの場所は自由で、リポジトリの外を勧める
（例: `~/p3-data/myapp`。チームで共有するなら同期するフォルダ）。端末からなら対話式で、リポジトリの中身から既定値を推測して聞く。

```bash
cd ~/src/myapp
p3 init
#   プロジェクト名（切り替えに使う短い名前） [myapp]:
#   （このリポジトリは本体の参照先 myapp として登録する。名前は --repo-name で変えられる）
#   データを置くフォルダ（リポジトリの外を勧めます）: ~/p3-data/myapp
#   何を作っているプロジェクトか（Preflight の前提になります）: 社内向けの経費精算アプリ
#   ドキュメントのパス（カンマ区切り。Preflight で最初に読みます） [docs, README.md]:
#   Preflight で重視する観点・制約（任意）: 個人情報を扱う変更は必ずリスクに挙げる
#   AGENTS.md に AI 向けの p3 の使い方を追記しますか (y/n) [y]:

# AI やスクリプトからは引数で（--yes で質問しない）
p3 init --yes --project myapp --dir ~/p3-data/myapp --description "社内向けの経費精算アプリ" --docs docs,README.md
```

データのフォルダには `project.yaml` と空の `requests/` が作られる。既に作られたフォルダ（他の人が作って共有したもの）を
指したときは、作らずに **参加** だけする。

新しく作るときは、このリポジトリを **本体の参照先**（`project.yaml` の `repos`。名前は既定でフォルダ名、役割「本体」・最初に読む・
作業先にできる）として登録する。参加するときは、同じ名前の参照先か、参照先が1つならそれにこのリポジトリを結び付ける
（決まらなければ `p3 repo path <名前> <パス>` を案内する）。

どちらの場合も **個人設定**（`~/.config/infodb-p3/config.yaml`。このマシン・この人だけのもので共有しない）に
「プロジェクト名 → データのフォルダ・参照先のこのマシンのパス」を登録する。

```yaml
projects:
  myapp:
    dir: /home/me/p3-data/myapp
    repos:
      myapp: /home/me/src/myapp      # 参照先の名前 → このマシンのパス
  other:
    dir: /home/me/p3-data/other
```

**操作するプロジェクトは環境変数ではなく、今いる場所と個人設定から決まる。**

1. `--project <名前>` を付ければそれ
2. 登録した参照先（サブフォルダ・その git の作業ツリーを含む）か、データのフォルダの中ならそのプロジェクト
3. 登録が1つだけなら、どこからでもそれ
4. 決まらなければ、登録済みのプロジェクトと選び方を表示する

`p3 project` で一覧（今いる場所のプロジェクトに `*`）、`p3 project add <名前> <フォルダ>` で init せずに登録
（参照先のこのマシンのパスは続けて `p3 repo path <名前> <パス>`）、`p3 project rm <名前>` で登録を外す（データは消さない）。
`p3 whoami` で今の判定を確かめられる。

個人設定は、p3 が書き換えるときもコメントと p3 の知らない項目を残す。書き換えは「ロックを取って最新のファイルを読み、
対象の項目だけを変えて書く」ので、CLI と serve が同時に別の項目（プロジェクトの登録とテーマなど）を変えても消し合わない。
YAML が壊れている・読めないときは、書かずにエラーと直し方を出す。

**画面のテーマ**（`ui.theme`: `system` = OS に合わせる（既定）/ `light` / `dark`）も個人設定に置き、このマシンの
すべてのプロジェクトで共通にする。画面では「設定」の「画面のテーマ（個人）」で選ぶ（選んだらすぐ保存する。
プロジェクト設定の「保存」とは別で、編集中のプロジェクト設定はそのまま残る。保存できなかったときは知らせて元の表示に戻し、
「もう一度保存する」でやり直せる）。同じ serve を開いているほかのタブの設定画面にも、変更通知で反映する。CLI では:

```bash
p3 user-config                       # 今のテーマ（ui.theme）と個人設定の場所。--json も
p3 user-config set ui.theme=dark     # system / light / dark
```

`p3 user-config` が扱うのは今はテーマだけ（ほかの個人設定は見せない・変えない）。プロジェクトの設定は `p3 config`。
画面からは `/api/user-theme`（テーマだけを読み書きする。変更はこのマシンのローカルの画面からだけ）を使う。

画面は、最初の描画の前（CSS より先）に `/api/user-theme.js` を読んでテーマを反映するので、OS と逆の固定のテーマでも
ちらつかない。`system` のときは表示中に OS の明暗を変えるとすぐ追従し、`light` / `dark` は OS によらない。
CLI やほかの serve でテーマを変えたときは、開いている画面を読み直すと反映する（タブ間で自動では同期しない）。
個人設定が読めないときは、画面は `system` で起動する。

設定はあとから `p3 config`、画面の「設定」、`project.yaml` の直接編集のどれでも変えられる（コメントは p3 が書き換えても残る）。

| 設定 | 使われ方 |
| --- | --- |
| `name` / `description` | 画面の表示と、Preflight の前提（説明が空だと画面に警告を出す） |
| `docs` | Preflight で Codex に最初に読ませるドキュメント（`<参照先>:<パス>`、名前なしは先頭の参照先。複製はしない） |
| `preflight.instructions` | プロジェクト固有の評価の観点・制約。Codex への指示に加わる |
| `branchPattern` | 要望のブランチ名（既定 `req/{id}-{slug}`。作業先のリポジトリごとに同じ名前で割り当てる） |

### 要望からタスクまで

```bash
pcube milestone add v0.2 --title "通知まわり" --due 2026-11-30   # まとめてリリースする単位（任意）
pcube request new "通知機能を追加したい" --area src/notify --milestone v0.2 --due 2026-11-15 --tag jira:PROJ-123 \
  --body "- メール送信基盤
- 通知設定画面"                        # → 261009-k7m3x（作成日-乱数。ID の一部 k7m3x でも指せる）
pcube preflight k7m3x                  # Codex で評価・細分化（完了まで待つ）
pcube drafts k7m3x                     # 評価とタスク案（D1, D2 ...）を見る。ファイルを直接直してもよい
pcube preflight k7m3x --note "対象は CLI だけ。Web は不要"   # 確認事項に答えて再評価（前回の結果とメモを引き継ぐ）
pcube preflight k7m3x --note - --note-only < answer.md     # メモを書き足すだけ（次の Preflight に渡す）
pcube notes k7m3x                      # メモの一覧と、次の Preflight に渡すもの
                                       # 画面では評価の下のメモ欄から書いて「保存して再実行」できる（初回の実行の後から）
pcube accept k7m3x --skip D3           # タスク化 → requests/261009-k7m3x/tasks/T001.md ...
                                       # 再評価で古いタスクが置き換えられるなら表示して残す（--archive-superseded でアーカイブ）
pcube serve                            # http://localhost:4310 で進捗・タスクボードを見る
```

タスク化すると要望は「進行中」になり、作業先のリポジトリごとにブランチ名（`req/261009-k7m3x-...`）が割り当てられる
（下の「作業先とリポジトリごとのブランチ」）。P3 は名前を決めるだけで、ブランチや作業ツリーは作業する人・AI が作る。
**そのブランチ（作業ツリーでもよい）の中で CLI を実行すると、その要望が「今の要望」になり、指定を省ける。**
状態の書き込みは常にプロジェクトのデータのフォルダに行く（ブランチごとに状態が分岐しない）。

```bash
git switch -c req/261009-k7m3x       # 作業ツリー（git worktree）でもよい
export PCUBE_ACTOR=ai:claude
pcube move T001 doing
pcube new "作業中に見つかった追加の作業" --body "..."        # → T004（要望の中の続きの番号）
pcube move T001 done --output https://github.com/me/myapp/pull/42
```

### CLI

| コマンド | 内容 |
| --- | --- |
| `pcube progress` | 要望ごとの進捗（マイルストーンごと。`--all` で完了・見送りも）。既定でも対応済を出す（画面の未完了とは違う） |
| `pcube milestone ls\|add\|set\|rm` | マイルストーン（`--title` `--due` `--done`） |
| `pcube request new\|ls\|show\|set\|archive` | 要望の作成・一覧・詳細・更新（`status=resolved` `due=` `milestone=` `tags=` / `--tag`）・アーカイブ |
| `pcube ls` | 今の要望のタスク（`--status` `--area` `-q`、`--all` で全要望）。置き換えられたタスクには `※置換` |
| `pcube show <T003\|要望\|語句>` | 詳細と関係（明示・暗黙・影響範囲）。`--brief` で作業に要る項目だけ（下の「短い出力」） |
| `pcube new <タイトル>` | 今の要望にタスクを足す（`--body -` で標準入力から本文） |
| `pcube set <T003> key=value ...` | 更新（`outputs=URL,...` など。値を空にすると消す） |
| `pcube move <T003> <status>` | 列を移動（`--output` で成果物を足す。繰り返し可）。置き換えられたタスクを作業中にすると警告（移動はする） |
| `pcube check <T003> [--off]` | 完了したタスクを人が確認して「済み」にする / 外す |
| `pcube link\|unlink <T003> <種類> <相手>` | 関係（相手は `T004` / `<要望>/T004` / `<要望>`。`depends_on` は循環チェックあり） |
| `pcube find <語句>` / `pcube impact <T003>` | 対象の特定 / 変更が波及する項目（要望をまたいで） |
| `pcube preflight\|drafts\|accept [<要望>]` | Preflight の実行（`--note` でメモを足して再評価）・確認・タスク化（`--archive-superseded` で置き換えられるタスクをアーカイブ） |
| `pcube notes [<要望>]` | Preflight へのメモと、次に渡すもの |
| `pcube init` / `pcube config` / `pcube whoami` | 初期設定 / 設定 / 変更者と今の要望 |
| `pcube serve` | ビューアの起動 |

今の要望は `--req <要望>` → `PCUBE_REQUEST` → 今いる参照先に割り当てたブランチ → ブランチ名の要望 ID の順で決まる（パスに要望 ID が入っているだけでは決めない。detached HEAD では決めない）。
`--json` で機械可読な出力、`--rev` で楽観ロック（競合すると終了コード 3、見つからないと 2）。
CLI はサーバを経由せずファイルに直接書く（serve が動いていなくてよい）。開いている画面には、ヘッダーの「再読み込み」か、
タブ・ウィンドウに戻ったときの読み直しで反映される（ファイル監視で届くこともあるが当てにしない。下の「画面への反映」）。

#### 短い出力（`show --brief` / `request show --brief`）

AI がタスクを進めるときに読む形。作業に要る項目だけを出し、本文は切り詰めない。関係や影響を調べるときは通常の出力を使う。

| | 残すもの | 省くもの |
| --- | --- | --- |
| タスク | `item` の id・ref・request・title・status・body・rev・outputs・relations（`depends_on` だけ）、`dependencies`、`superseded`、`warnings` | 日時・areas・labels・変更者・ファイルのパス・依存以外の関係・`graph`（関係しそう・影響範囲） |
| 要望 | `item` の id・title・status・body・rev・workstreams（作業先ごとのブランチ。あるときだけ）、`branches`、`tasks` の id・ref・title・status・repo、`issue` | 日時・areas・tags・関係・`graph`・タスクの本文など |

JSON の項目名と階層は通常の `--json` と同じで、項目を省くだけ。タスクの通常の `--json` にも、次の2つを足した:

- `dependencies`: 依存の相手と状態 `[{ ref, title, status }]`。`ref` は `<要望ID>/T001` か `<要望ID>`。
  相手が見つからない（アーカイブした・参照の誤り）ときは `title` と `status` が `null`（完了とは扱わない）
- `warnings`: 詳細を読んだときの注意 `[{ code: "superseded", target, from: [...], message }]`。`move` の着手の警告と同じ形
  （置き換えた側が複数なら `from` に全部）

テキストの短い出力は、見出し・状態と rev・依存（`T002 doing / … / T004 （状態不明）`）・成果物・注意・本文の順。

どれだけ減るか（6タスクの `show` の stdout の合計。UTF-8 のバイト数）:

| 対象 | テキスト（通常 → 短い） | JSON（通常 → 短い） |
| --- | --- | --- |
| 261011-wng6f の6タスク（実データ。2026-10-11） | 31,556 → 13,344（57% 減） | 54,618 → 16,895（69% 減） |
| 周辺の関係が多い固定データ（`test/showBrief.test.ts`） | 21,761 → 4,726（78% 減） | 52,292 → 7,318（86% 減） |

目安は「周辺の関係が多い6タスクで半分以下」（テストで確かめる）。減るのは関係しそう・影響範囲・日時などなので、
本文が長く関係の少ないタスクほど減り方は小さい（本文は切り詰めない）。測り直すときは:

```bash
for t in T001 T002 T003 T004 T005 T006; do p3 show <要望ID>/$t | wc -c; p3 show <要望ID>/$t --brief | wc -c; done
pnpm vitest run test/showBrief.test.ts --reporter=verbose   # 固定データの数字を出す
```

既に `p3 init --agents` で置いたスキル（`.claude/skills/p3/SKILL.md`）と AGENTS.md / CLAUDE.md の追記は自動では変わらない。
短い出力を使う手順にするには、「AI エージェントから使う」の「P3 を新しくしたとき」のとおり、同梱の版と見比べて手で直す。

## データの持ち方

```
<データのフォルダ>/                     （例: ~/p3-data/myapp。リポジトリの中なら .pcube/）
  project.yaml                          プロジェクト設定
  requests/
    261009-k7m3x/                       要望のフォルダ（作成日 + 乱数5文字。タイトルが変わっても変わらない）
      request.md                        要望
      tasks/T001.md, T002.md ...        タスク（要望の中の連番。1ファイル1タスク）
      tasks/.archive/                   アーカイブしたタスク（その ID は新しいタスクに再利用しない）
      notes/N-....md                    Preflight へのメモ（確認事項への回答・方針の変更。1件1ファイルで書き足す）
      preflight/PF-.../
        request.md                      評価時点の要望のスナップショット
        context.md                      インテリジェンス層が選んだ関連項目と理由
        carryover.md                    引き継いだ前回の評価・タスク案と、渡したメモ（開始時点で固定）
        assessment.json                 評価（Codex が書く）
        drafts/D1.md, D2.md ...         タスク案（Codex が書く。1案1ファイル。人が直してもよい）
        run.json                        実行メタデータ・ログ・タスク化の結果・実行者・引き継いだ run とメモ
    .archive/                           アーカイブした要望（フォルダごと）
```

タスクファイルの例（`<データのフォルダ>/requests/261009-k7m3x/tasks/T003.md`）:

```markdown
---
id: T003
title: ファイル監視で外部編集を取り込む
status: done
areas: [src/server/store/workspace.ts]
outputs:                                     # 成果物（1項目ずつ。URL・文章・パスを混ぜてよい）
  - https://github.com/me/myapp/pull/42      # 項目全体が http(s) の URL なら画面でリンクになる
  - 判断の理由は docs/notify.md にまとめた    # 文章はそのまま出す（中の URL やパスはリンクにしない）
startedAt: 2026-10-09T10:12:00.000Z         # 作業中にした日時（pcube が記録）
doneAt: 2026-10-09T15:40:00.000Z            # 完了にした日時（pcube が記録）
checkedAt: 2026-10-10T09:00:00.000Z         # 人が確認して「済み」にした日時
relations:
  - type: depends_on
    target: T002                             # 同じ要望のタスク
  - type: impacts
    target: 261001-ab3cd/T001                # 別の要望のタスク
    origin: ai                               # human | ai | preflight
    confidence: 0.6
rev: 3                                       # 楽観ロック
updatedBy: ai:claude
---

AI やエディタがファイルを直接変更したら、画面の「再読み込み」（またはタブに戻ったとき）で取り込む。
```

- **ID**: 要望は「作成日-乱数」なので、複数人が別々に作っても衝突しない。タスクは要望をまたいで移動しないので、要望の中の素直な連番でよい
- **参照**: 同じ要望の中は `T003`、別の要望は `<要望ID>/T003`、要望そのものは `<要望ID>`
- 書き込みは tmp → rename で原子的に行い、番号は排他作成で採番する（同じマシンの別プロセスと衝突しない）
- 外部での編集（CLI・エディタ・git pull で要望のフォルダが増えた場合も）は、画面の「再読み込み」で取り込む（下の「画面への反映」）
- 読めないファイルがあっても全体は止めず、画面上部に件数を出す

### 画面への反映

- **画面からの変更・Preflight の進み具合と終了** は、serve の中から変更通知（SSE, `/api/events`）で、開いているほかのタブにもすぐ届く。
  ファイル監視には頼らない
- **外での変更（CLI・AI・エディタ・git pull）** は、ヘッダーの「再読み込み」で取り込む。serve がデータのフォルダを全部
  （project.yaml・要望・タスク・関係の索引。外で足した・消した・アーカイブしたものも）読み直してから、画面が取り直す
  （ブラウザのリロードはしないので、URL・開いているタスク・入力中の内容はそのまま）。タブやウィンドウに戻ったときも1回同じことをする。
  定期的な問い合わせはしない。読み直している間にまた押す・戻ると、終わってからもう1回だけ読む
- serve はデータのフォルダの監視も続けるが、補助にすぎない。NFS などでは通知が届かず、Node の再帰的な監視は、置き換えて
  保存したファイル（CLI の書き方）の2回目以降の変更を通知しないことがある。画面を開いたままでは同期は保証されないので、
  外で変えたら「再読み込み」する
- 読み直しはファイルを書かない。project.yaml やデータのフォルダが読めないときは失敗を知らせ、表示は前の内容のまま
  （「もう一度」でやり直せる）。壊れた Markdown は「読めないファイル」に出し、ほかは表示する
- 取り直しても **入力中の内容は消さない**。要望のタイトル・タグとタスク詳細は、編集中に外で変わったら入力を残して知らせ、
  保存は編集を始めたときの rev で行う（外で変わっていれば競合になり、上書きしない。「入力を捨てて最新にする」/「破棄」で
  最新を表示）。設定（project.yaml には rev が無い）は、編集中に外で変わったことを知らせ、保存するとこの画面の内容で上書きする
- 開いている要望やタスクが外で削除・アーカイブされたら、最後に読めた内容と入力を残して知らせ、保存はしない（消えたものを
  作り直さない）。写してから閉じる。通信の一時的な失敗は削除とはみなさず、前の内容のまま知らせて取り直せるようにする
- 書き込みはこれまでどおり、書く直前にファイルを読み直し、古い rev なら競合として止める。読み直しの最中に同じものを
  書き込んでも、読み直しが先に読んだ古い内容で戻さない

## タグ（外部 ID・分類）

要望の `tags`（文字列の配列。保存の形は今までと同じ）は、要望に付ける自由な文字列で、外部の ID や分類を持たせるのに使う。

- 例: `jira:PROJ-123`（外部の課題 ID）、`group:顧客A`（まとまり）、`release/2026Q4`、`feature`。接頭辞（`jira:` など）は決まって
  おらず、好きに付けてよい。同じ値を複数の要望に付けられる（グループにする）
- 対象外: 要望・タスクの ID や関係の参照の代わりにはしない。外部のシステムとの同期・リンクにする・一意であることの保証・
  意味での検索・Preflight への自動の受け渡しはしない

**入力の決まり**

- 画面と CLI で新しく入れる値は、前後の空白を除いた文字列。空（空白だけ）は付けない。同じ値（大小文字も含めて完全に同じ）は1つにまとめる
- 値の中のカンマ・空白・コロン・スラッシュ・日本語・長い値はそのまま残す（分けたり変えたりしない）
- 既にファイルにある値は読み込むだけで正規化しない（カンマを含む値も1つのまま。保存しても変わらない）
- 画面は値ごとに足す・外す（入力欄で Enter か「追加」。カンマで分けない）。長い値は折り返して全文を出す
- CLI: `request new --tag 値`（繰り返し可。カンマで分けない）、`request set <要望> --tag 値 ...`（付いているタグをこの値の並びに
  置き換える。カンマで分けない）。`request set <要望> tags=a,b` はカンマで分ける書き方なので、カンマを含む値には `--tag` を使う。
  `tags=` で全部外す。`request ls --tag 値`（繰り返すとどれかが付いている要望）
- API: `tags` は配列（`POST /api/requests`、`PATCH /api/requests/:rid`）で、送られた並びをそのまま保存する（画面は上の決まりで送る）

**進捗の絞り込み**

- 「タグ」を開いて、検索して複数選ぶ。選んだタグの **どれか** が付いている要望（OR）で、状態の絞り込み（未完了など）とは **かつ**（AND）。
  何も選ばなければタグでは絞らない
- 要望との突き合わせは大小文字を区別する完全一致。候補の検索は部分一致で、大小文字を区別しない
- 候補は状態によらずすべての要望のタグ（付いている要望の数つき）。どの要望にも無くなったタグも、選んだままなら「選択中」に残り、
  外せる（黙って外さない）
- URL: `?tags=` に JSON の配列（例 `?tags=["jira:PROJ-123","group:顧客A"]` を URL エンコードしたもの。カンマや記号を含む値も
  そのまま戻る）。以前の `?tag=値` は1つ選んだものとして読む（`tags` があれば `tags` を使う）。配列でない・文字列でない要素・
  空の値は捨て、重複はまとめる。`show` / `zoom` / `task` はそのまま残る

確かめるケース（実装のテスト）: カンマ入りの既存値の読み込みと保存、`jira:PROJ-123` / `group:顧客A` の作成・更新、空・空白・重複・
長い値・日本語・記号、未選択・1つ・複数（OR）・状態との AND・未完了から対応済を除く、選んだタグが無くなった、旧 URL・新 URL・
不正な値の往復。

## 成果物（outputs）

タスクの成果物は文字列の配列（保存の形は今までと同じ）で、1項目ずつ PR / MR の URL・文章・ドキュメントのパスのどれでもよい。

- 画面（タスク詳細・タスクボードのカード・対応済み）では、項目全体（前後の空白を除いて）が絶対の `http://` / `https://` の URL
  ならリンクにして別のタブで開く（カードの上のリンクを押してもタスク詳細は開かない）。それ以外は文字のまま出す。
  文章の中の URL は拾わず、Markdown も解釈しない。`javascript:` / `data:` / `file:` などはリンクにしない。保存する値は変えない
- 足し方: 画面ではタスク詳細の「成果物を編集」に1行に1つ。CLI では `move <T> done --output 値`（繰り返し可。カンマで分けない）、
  `new <題> --output 値`。`set <T> outputs=a,b` はカンマで分けて置き換える（カンマを含む文章は `--output` か画面で）
- 既存のタスク: 保存の形は変わらないので、移し替えは要らない。既に URL だけが入っている項目は、そのままリンクになる
  （1つの文字列で書かれた古いファイルも配列として読む）。説明の文の中に URL があるもの（例: 「ブランチ X を push（PR は…）」）は
  推し量って書き換えないので、リンクにしたいときは正しい URL を1項目として足す（`p3 move <T> done --output <URL>` か画面）。
  アーカイブ（`.archive/`）したタスクは画面に出ないので対象外

## 要望のステータス

| 値 | 表示 | 誰が・いつ |
| --- | --- | --- |
| `draft` | 下書き | 作ったとき |
| `preflight` / `reviewed` | 評価中 / 開始前 | Preflight の実行中 / 評価が済みタスク化の前（自動） |
| `active` | 進行中 | タスク化したとき（自動）。対応済の要望に未完了のタスクができたときも戻る |
| `resolved` | 対応済 | 作業する側（AI など）が全タスクを終えたら `p3 request set <要望> status=resolved` |
| `done` / `rejected` | 完了済 / 見送り | 人が決める |

- **対応済にできる条件**: タスクが1件以上あり、全部が完了（`status=done`）で、読めないタスクファイルが無いこと。
  人の「済み」（`checkedAt`）・PR・マージは条件にしない。置き換えられて残したタスクも数える（不要ならアーカイブする）。
  満たさなければ何も書かずに失敗し、完了していないタスクを知らせる。最後のタスクを完了にしても自動では対応済にしない
- **進行中に戻る**: 対応済の要望に未完了のタスクを足した・タスクを完了から戻した・再評価をタスク化したとき（CLI・API・画面）。
  完了のタスクを足す・済みを外す・題や成果物を直すだけでは戻らない。完了済・見送りの要望は戻さない
- タスクファイルを直接編集して対応済と未完了のタスクが並んだときは、`request show` と画面に知らせを出す
  （ファイルは勝手に直さない。`p3 request set <要望> status=active` で直す）
- タスクの「完了 → 済み（人）」と同じく、要望も「対応済（作業した側）→ 完了済（人）」の2段階にしている。
  流れ: タスクを全部完了 → 対応済（AI など）→ 人が成果物を確かめて完了済。対応済の後にタスクを足すと進行中に戻り、終えたらまた対応済にする
- `p3 init --agents` は AGENTS.md / CLAUDE.md に AI への指示を書く（対応済にする手順を含む）。既に指示の見出しがあるファイルには
  書き足さないので、以前に作ったファイルは手で直す（`docs/architecture.md` の「タスク管理（infodb p3）」の内容に合わせる）

## 一覧の並び

日時（ミリ秒まで）が同じものの順番も決めておく（続けて作ると同じミリ秒になることがある）。
ID の順は数を含む部分を数として比べる（T2 < T10）。要望・メモ・run の ID は乱数を含むので、**ID の順は作った順を表さない**。

| 一覧 | 並び | 同じ日時なら |
| --- | --- | --- |
| 進捗（要望） | 最終更新（要望自身とタスクの更新日時の新しい方）の新しい順 | 要望 ID の順 |
| 要望のタスク（`ls`・ボード） | タスク ID の順 | — |
| 全要望のタスク（`ls --all`） | 要望 ID の順 → タスク ID の順 | — |
| Preflight の run | 開始日時の新しい順（先頭が「直近」） | run ID の大きい方が先 |
| メモ | 作成日時の古い順 | メモ ID の順 |
| 対応済み（済みにしたタスク） | 済みにした日時の新しい順 | タスク ID の順 |

## タスクの関係（多元的な紐付け）

単純な親子や1本の依存では表せないので、3つの次元を重ねて扱う（`src/server/intel/`）。

1. **明示エッジ** — `relations` に型付きで持つ。`depends_on` / `part_of` / `derived_from` / `impacts` /
   `relates_to` / `duplicates` / `supersedes`。エッジは張った側のファイルに保存し、逆向きはインデックスで導く。
   誰が張ったか（`origin`）と AI の確信度（`confidence`）を持ち、AI 由来の関係は人が見直せる。
2. **構造** — タスクは要望（フォルダ）に所属する。
3. **暗黙の近さ** — 影響領域（`areas`、パスの包含関係を考慮）の重なりと、内容の類似（TF-IDF、日本語は bigram）。
   明示されていないが関係しそうなもの（過去の要望の作業を含む）を「理由つき」で提示する。

関係は「相手の役割 + 相手」で見せる（`src/shared/types.ts` の `RELATION_TYPES`）。A → B と張ると、A の詳細には B の役割、
B の詳細には A の役割が出る。保存する種類の名前（`depends_on` など）と向きは変わらない。

| 種類 | 意味（A → B） | A に出る | B に出る | 例 |
| --- | --- | --- | --- | --- |
| `depends_on` | A は B が先に終わっている必要がある | 依存先 B | 依存元 A | T002 → T001: T002「依存先 T001」、T001「依存元 T002」 |
| `part_of` | A は B の一部 | 親 B | 子 A | T003 → 要望: T003「親 要望」、要望「子 T003」 |
| `derived_from` | A は B から生まれた | 派生元 B | 派生先 A | 要望 X → 要望 Y: X「派生元 Y」、Y「派生先 X」 |
| `impacts` | A は B に影響が及ぶ | 影響先 B | 影響元 A | T001 → 別の要望の T004: T001「影響先 …/T004」 |
| `relates_to` | 関連する | 関連 B | 関連 A | |
| `duplicates` | A は B と同じ内容 | 重複 B | 重複 A | |
| `supersedes` | A は B を置き換える（B は古い案） | 旧案 B | 新案 A | T005 → T001: T005「旧案 T001」、T001「新案 T005」 |

これらから次を導く:

- **影響範囲** — `depends_on` / `part_of` の逆向きと `impacts` を、要望をまたいで推移的に辿る
- **循環検出** — `depends_on` を追加するときに拒否する
- **文脈選定** — Preflight で Codex に渡す関連項目を、全件ではなくスコア上位に絞る（トークン節約）


## Preflight

### 参照先（複数のリポジトリ・フォルダ）

Preflight の Codex が読むリポジトリ・フォルダ（参照先）を、**数と名前を自由に** 登録できる。本体・ドキュメント・基盤・
依存しているライブラリのように分かれたシステムでも、全部を読ませて判断させるため。

- **共有の定義**（`project.yaml` の `repos`）: 名前・役割・最初に読むか（`readFirst`）・タスクの作業先になりうるか（`writable`。
  今は表示だけで、作業先とブランチの複数対応は別の要望で入れる）・主なフォルダ
- **このマシンのパス**（個人設定 `projects.<プロジェクト>.repos.<名前>`）: 人によって違うので共有しない。git のリポジトリで
  なくてもよい（フォルダだけ・リポジトリの中のサブフォルダも可）

```bash
p3 repo add app /workspaces/app role=システム本体 readFirst=true writable=true
p3 repo add docs /workspaces/docsrepo/guide role=ドキュメント mapFile=MAP.md   # リポジトリの中のサブフォルダ
p3 repo add infra /workspaces/infrarepo role=基盤
p3 repo ls                       # 一覧。このマシンのパスが無いものは「未登録 → p3 repo path <名前> <パス>」
p3 repo path docs ~/src/docsrepo/guide   # ほかの人が足した参照先に、自分のマシンのパスだけを登録する
p3 repo set infra role=基盤（Terraform）            # 共有の定義を変える（role readFirst writable mapFile）
p3 repo rm infra --local         # このマシンのパスだけ外す（共有の定義は残る）
p3 repo rm infra                 # 共有の定義ごと消す（ほかの人の Preflight でも読まなくなる。フォルダは消さない）
```

設定画面の「参照先（リポジトリ・フォルダ）」でも同じことができる（足す・役割・最初に読む・作業先にできる・構成の説明（Markdown）・
主なフォルダ・消す）。このマシンのパスは、P3 を動かしているマシンのローカルの画面でだけ見え、登録・変更できる
（ほかのマシンの画面には出さない）。

```yaml
# project.yaml（共有）
repos:
  app:
    role: システム本体
    readFirst: true
    writable: true
    map:                               # 主なフォルダ: どこから読むかの案内（全部を読む指示ではない）
      src/server: API とデータ
      src/web: { role: 画面, entry: src/web/main.tsx }
  docs:
    role: ドキュメント
    mapFile: MAP.md                    # 構成の説明を Markdown で書くとき（参照先の中のパス）
  infra: { role: 基盤 }
docs: [README.md, "docs:guide/"]      # <参照先>:<パス>。名前なしは先頭の参照先
```

- **参照の書き方**: `docs` と要望・タスクの `areas` は `<参照先>:<パス>`（例 `docs:guide/`・`infra:terraform`）で
  書ける。名前なしは先頭の参照先の中のパス（今までの書き方のまま読める）。登録に無い名前・絶対パス・`..` は読まない。
  文脈の選定（関係しそうな項目）は、同じ参照先の中だけで領域の重なりを見る（別の参照先の同じ `src` は重ならない）
- **本体**: `p3 init` が本体のリポジトリを参照先として登録する。足すのは、ドキュメント・基盤・依存しているライブラリなど
  ほかのリポジトリ・フォルダだけ
- **Preflight での扱い**: 読める参照先を全部 `/workspace/<名前>` に **読むだけで** マウントする（`/workspace` 自体は空。
  データは今までどおり `/data`、書けるのは run のフォルダだけ）。パスの対応（`codex.pathMap`）は全部に効く。このマシンの
  パスが無い・無いパス・フォルダでないものは飛ばし、「見ていない参照先」として理由をログと記録（run.json の `scope`）に残す
  （P3 が決める。Codex の申告では変わらない。記録にはこのマシンのパスを入れない）。読める参照先が無くても、要望と P3 の
  データだけで評価する（その制約を Codex に伝える）
- **調べた根拠**: 評価（`assessment.json` の `evidence`）に、判断に使ったファイル・箇所（`<参照先>:<ファイル> <行・関数>`）を
  書かせ、読まずに推測した判断も消さずに「推測」として書かせる。P3 は、見ていない参照先・参照先の外・無いファイルを指す
  「確かめた」を「推測」に直して理由を残す。再評価では前回の根拠を前回の時点のものとして渡し、今回の根拠に写さない。
  タスク案の本文にも「判断の根拠」と「未確認」を書かせる。以前の評価は「記録なし」と出す。画面の「調べた範囲」「判断の根拠」と
  `p3 drafts`（`--json` では `scope` と `assessment.evidence`）で確かめる
- テストは偽の app-server で、マウントの引数・指示文・記録・根拠の扱いを確かめる。本物の Codex が実際にどこまで読むか、
  読むだけのマウントへの書き込みが拒まれることは、偽の app-server では確かめられない（Docker での確認は docs/architecture.md）

### 作業先とリポジトリごとのブランチ

1つの要望が本体と基盤の両方を変える・ドキュメントのリポジトリだけを直す、のように、作業するリポジトリは要望ごとに違う。

- **タスクの作業先**（`repo`）: 作業先になりうる（`writable=true`）参照先の名前か、作業先なし（調査・人の判断など）。参照だけの
  参照先（依存しているライブラリなど）は選べない。1つのタスクの作業先は1つ（またがる作業はタスクを分ける）。Preflight は案に
  作業先を書き（`repo: <名前>` か `none`）、人がレビューで直せる（画面の案の「作業先」、ファイルを直してもよい。タスク化の前に
  確かめ、作業先にできない名前なら何も変えずに断る）。作業先を書かずにタスクを足すと、作業先にできる参照先が1つならそれ、
  ほかは作業先なし
- **リポジトリごとのブランチ**（要望の `workstreams`: 名前 → `{ branch }`）: タスク化で、採用した案の作業先の分だけ割り当てる
  （作業先なし・不採用は割り当てない。既にあるものは変えない）。後からタスクを足した・作業先を変えたときも、足りない分だけ足す。
  P3 は名前を決めるだけで、git のブランチや作業ツリーは作らない（作業する人・AI が作る）。git でないフォルダはブランチなし（そのフォルダで
  作業する）。リポジトリの中のサブフォルダは、それを含む git のリポジトリを基準にし、同じ git を指す2つの名前に割り当てることに
  なるときは断る（作業先をそろえる）。作業ツリーの置き場所は記録しない（Claude Code などに任せる）
- **リポジトリごとの成果物**（タスクの `repoOutputs`: `{ repo, output }` の並び）: 最後のタスクに、関係するリポジトリの PR を全部残せる。
  `outputs`（文字列の並び）はそのまま使え、成果物の所属を作業先から推し量ることはしない

```bash
p3 new "基盤の設定" --req <要望> --repo infra   # 作業先（none で作業先なし）。足りないブランチは割り当てる
p3 set T004 --req <要望> repo=app               # 作業先を変える（repo=none で外す）
p3 ls --req <要望> --repo infra                 # 作業先で絞る（none は作業先なし）。共有の参照先があれば一覧に作業先の列
p3 show T004 --brief --json                     # work: { repo, branch, registered }
p3 request show <要望> --brief                  # branch  app: req/…  /  branch  infra: req/…
p3 move T005 done --repo-output app=https://…/pull/1 --repo-output infra=https://…/pull/2   # 全部の PR を最後のタスクに
p3 whoami                                       # 今いる参照先と今の要望
```

今の要望は、今いる参照先（参照先の中か、その git のリポジトリの作業ツリーの中）を見て、その参照先に割り当てたブランチだけと照らす
（別のリポジトリの同じ名前のブランチと取り違えない）。detached HEAD や git でないときは決めない。
決まらない・複数に当たるときは `--req` を案内する。画面では、案のレビューとタスク詳細で作業先を選び、要望の概要に作業先ごとの
ブランチ、ボードのカードに作業先、成果物にリポジトリごとの成果物を出す。

### ChatGPT プランで動かす（Sign in with ChatGPT）

Preflight の Codex は、各自の ChatGPT アカウント（プラン）で動かす。サインインは P3 が行う（Codex の初期設定のサインインは要らない）。

```bash
p3 chatgpt login        # ブラウザで ChatGPT にサインインし、プランの利用に同意する（127.0.0.1:1455 で待つ）
p3 chatgpt login --paste  # ブラウザがコールバックに届かない環境: 「接続できません」の画面のアドレスバーの URL を貼る
p3 chatgpt status       # 接続の状態（アカウント・プラン利用の可否・期限）
p3 chatgpt logout       # 接続を解除（ChatGPT 側の取り消しも行う）。--forget でこのマシンの登録ごと消す
```

- 接続はこのマシン・この人のもので、どのプロジェクトにも属さない（`~/.config/infodb-p3/chatgpt.json`、0600）。
  トークンは CLI の出力・画面・ログに出さない。個人設定（`config.yaml`）とは別のファイルなので、互いの保存で消えない
- トークンは使うときに更新する（期限の 35 分前を過ぎていたら。refresh token は毎回入れ替わる）。更新できなくなったら
  サインインし直してもらう。解除しても、このマシンの登録（ホスト ID・発行された client ID）とアカウントは残し、次のサインインで使う
- 設定画面の「Continue with ChatGPT」でも同じことができる（serve が待ち受ける。待っている間は取消と、届かなかったときの URL の貼り付け）。
  この操作と状態の表示は **P3 を動かしているマシンのローカルの画面からだけ** 受け付ける（serve は既定で 0.0.0.0 で待つので、
  LAN の別のマシンからのサインイン・解除を断る。`docker run -p` で公開した serve の画面からはできないので CLI を使う）
- DevContainer では、VS Code が待ち受けのポートを転送するので、ホストのブラウザからのコールバックが届く
  （届かないときは「はじめかた」の「DevContainer の中で使うとき」）。詳しい設計は [docs/chatgpt-sign-in.md](docs/chatgpt-sign-in.md)

```
要望を書く ─▶ 文脈選定 ─▶ Codex が評価・細分化 ─▶ レビュー（案を取捨・編集）─▶ タスク化
             (intel)      (codex-workspace)         (drafts/D*.md)              (tasks/T*.md + 関係 + ブランチ)
```

Codex は llmcs の [codex-workspace-ts](https://github.com/tamuto/llmcs/tree/main/codex-workspace-ts)
（npm の `@infodb/codex-workspace`）で、操作する人のマシンのコンテナの中で、その人のアカウントで動かす。
コンテナには管理対象リポジトリを `/workspace`、データのフォルダを `/data` としてマウントする（データのフォルダは
リポジトリの外にあってよい）。途中経過は SSE で画面に流れる。

Codex のイメージ（`llmcs-codex-workspace:local`）は、無いか作ってから1日より古ければ、Preflight の前に作り直す
（そのときの最新の Codex が入る）。新しい Codex をすぐ使いたいとき・最初の Preflight の前に作っておきたいときは
`p3 codex update` で今すぐ作り直せる（入った版を表示する。Docker があればよく、プロジェクトの登録やサインインは要らない）。

```bash
p3 codex update
#   Codex のイメージ llmcs-codex-workspace:local を作り直しています（…）   ← 進み具合は stderr
#   Codex を更新しました: codex-cli 0.162.1（変わらず。これが最新）
#     イメージ llmcs-codex-workspace:local（2026-10-11 15:54:06 作成）
```

Docker が無い・デーモンに繋がらない・作れない（ネットワークなど）・版を読めないときは、次にすることを出して終了コード 1。開発の手順（手元の llmcs で試す方法など）は [docs/architecture.md](docs/architecture.md#codex-workspace-の依存)。

- Codex に書かせるのは要望のフォルダの `preflight/<RUN>/` 配下だけ。それ以外の変更があればログに警告を出す
- 結果は戻り値ではなく **ファイル契約**（`assessment.json` + `drafts/*.md`）。Mock エンジンでも人手でも同じ取り込み処理になる
- 存在しない要望・タスクへの関係はタスク化のときに捨てる
- 旧来の認証では、使用量の上限に当たっている場合は頼まずに失敗させる。ChatGPT プランには使用量を読む公式の API が無いので、
  上限に当たったら「Usage limit reached」として失敗させ、Manage usage（https://chatgpt.com/settings/usage）を案内する
- 再評価では、前回の評価・確認事項・タスク案（人の編集と採否を含む）と、その後のメモをプロンプトに資料として渡す。
  Codex との会話は続けず、毎回新しいコンテナ・スレッドで評価し直す（経緯はファイルに残る）

### マシンごとの設定

Codex の認証・パスの対応などはマシン（と人）ごとに違うので、プロジェクトのデータには置かない。
**個人設定**（`~/.config/infodb-p3/config.yaml`。`XDG_CONFIG_HOME` があればその下）に書くか、環境変数で渡す。
`.env` は読まない（P3 のパッケージの中にも、プロジェクトの中にも置かない）。

```yaml
# ~/.config/infodb-p3/config.yaml（projects・ui と同じファイル。必要な項目だけ書く）
codex:
  pathMap:                         # DevContainer のとき: このマシンのパス → Docker デーモンから見たパス
    /workspaces: /home/me/workspaces
  # auth: legacy                   # ChatGPT に接続していても旧来の auth.json を使う（既定 auto）
  # authVolume: codex-state        # 旧来: auth.json を入れた Docker ボリューム
  # authFile: /home/me/.codex/auth.json   # 旧来: ホストの auth.json（authVolume とどちらか）
  # model: gpt-5.5
  # effort: medium
  # ensureImage: false             # Preflight の前のイメージの作り直し（1日ごと）を止める
# preflight:
#   engine: mock                   # 明示したときだけ Mock で評価する
# serve:
#   host: 127.0.0.1
#   port: 4310
```

値は項目ごとに **CLI の明示（`--port` / `--host` / `--engine`）→ 環境変数 → 個人設定 → 既定値** の順で決まる。
環境変数を空にすると（`PCUBE_CODEX_MODEL=`）、個人設定の値を使わずに既定値に戻す。読めない値（`ensureImage: maybe`、
`=` の無いパスの対応など）は、どこの何を直すかを出して止まる。ChatGPT のトークンはここに置かない（`chatgpt.json`）。

| 個人設定 | 環境変数 | 内容 |
| --- | --- | --- |
| `codex.auth` | `PCUBE_CODEX_AUTH` | `auto`（既定。ChatGPT に接続していれば ChatGPT、無ければ旧来）/ `legacy`（接続していても旧来の `auth.json`） |
| `codex.authVolume` / `codex.authFile` | `PCUBE_CODEX_AUTH_VOLUME` / `PCUBE_CODEX_AUTH_FILE` | 旧来: Codex の初期設定でサインインした `auth.json`（Docker ボリューム内 / ホストのファイル） |
| `codex.pathMap` | `PCUBE_CODEX_PATH_MAP`（`a=b,c=d`） | このマシンのパス → Docker デーモンから見たパス。リポジトリとデータのフォルダの両方に使う |
| `codex.model` / `codex.effort` | `PCUBE_CODEX_MODEL` / `PCUBE_CODEX_EFFORT` | モデル・推論の深さ（省略時は Codex の既定） |
| `codex.ensureImage` | `PCUBE_CODEX_ENSURE_IMAGE`（`0` / `1`） | `false` でイメージの自動更新確認をしない |
| `preflight.engine` | `PCUBE_PREFLIGHT_ENGINE` | `mock` にすると Mock で評価する（明示したときだけ） |
| `serve.host` / `serve.port` | `PCUBE_HOST` / `PCUBE_PORT` | `p3 serve` の待ち受け（既定 `0.0.0.0` / `4310`） |

`PCUBE_ACTOR`（変更者）と `PCUBE_REQUEST`（今の要望）は操作ごとの指定なので、環境変数（と `--actor` / `--req`）だけで決める。

**serve を起動し直さずに効く設定:** `p3 serve` は Codex と Preflight の設定（`codex.*` と `preflight.engine`）を、
**Preflight を始めるたび** と **エンジンの状態を見るたび**（概要ページ・設定画面の ChatGPT の欄）に個人設定から読み直す。
始めたときの設定（認証・パスの対応・モデル・イメージの確認）はその Preflight の間ずっと使い、実行中に書き換えても途中の
run や並んで動いている run は変わらない。待ち受け（`serve.host` / `serve.port`）と、開いているプロジェクト・リポジトリ・
データのフォルダは起動のときのまま（変えるときは起動し直す）。環境変数は serve を起動したときのもの。

個人設定が読めない（壊れた YAML・読めないファイル・`codex:` などの形が違う・読めないパスの対応）ときは、serve は止めずに、
その Preflight を **設定のエラーとして失敗** にする（Docker は起こさず、古い設定や Mock に落とさない）。エラーとログには
直すファイルと項目を出す。概要ページのエンジンの状態にも同じ理由を出して実行のボタンを止め、直すと次の Preflight から効く。
`--engine mock` を明示したときは個人設定を読まずに動く。概要ページのエンジンの状態は、画面を取り直すとき（「再読み込み」・
タブやウィンドウに戻ったとき・変更通知）に確かめ直す（定期的には問い合わせない）。取れなかったときは使えると見せない。

**これまでの `.env` からの移し方:** P3 は前の版まで、P3 の置き場所の `.env` を読んでいた。今は読まないので、その中の値を
上の表に従って個人設定に書き写す（または環境変数で渡す）。秘密の値を自動でコピーしたり、旧来の `auth.json` を ChatGPT の
接続に変えたりはしない。書き写したら `.env` は消してよい。

概要ページには評価エンジンの状態を出す（Codex なら Docker・認証情報・イメージを確かめ、使えなければ理由を出して実行させない）。

**Docker のエラーを見る:** Preflight の開始のログに、参照先とデータのフォルダそれぞれの「名前 → コンテナの中のパス
（`codex.pathMap` の対応が当たったか。当たらない・パスが変わらない対応も書く）」を出す。ログとエラーは共有の記録（run.json）に
残るので、このマシンのパス・Docker のホストのパス・個人設定のファイルの場所は出さない（Docker の出力の中のパスも参照先の名前に
置き換える。想定外の変更も `<参照先>:<パス>` で出す）。実際のパスは、手元で `p3 repo ls` と個人設定で確かめる。
app-server（`docker run`）がすぐ・途中で終わったときは、Docker の出力（stderr。長ければ先頭と末尾を残して省略を明示）と
終了コード（またはシグナル）をログとエラーに出し、よくある原因には次にすることを添える（要約にはエラーらしい最後の行を出す）。
トークンなどは伏せてから残す。

```text
app-server（docker run）が初期化の前に終わりました（終了コード 125）: docker: Error response from daemon: invalid mount config for type "bind": bind source path does not exist: <参照先 pcube>
参照先 pcube のパスが Docker のホストにありません。個人設定（config.yaml）の codex.pathMap を確かめてください
今のパスの対応:
  参照先 pcube → コンテナ /workspace/pcube（codex.pathMap の対応なし（このマシンのパスのまま渡す））
  データ → コンテナ /data（codex.pathMap の対応なし（このマシンのパスのまま渡す））
```

| Docker の出力 | 次にすること |
| --- | --- |
| `bind source path does not exist` | DevContainer などでは Docker のホストから見たパスが違う。`codex.pathMap` に「このマシンのパス: ホストのパス」を書く（直せば serve はそのままで次から効く） |
| `Cannot connect to the Docker daemon` など | Docker を起動し、接続先（`DOCKER_HOST`・docker context）と権限を確かめる |
| `Unable to find image` / `pull access denied` | `p3 codex update` でイメージを作る |
| `docker` が無い（ENOENT） | Docker を入れて PATH を確かめる |

イメージの自動の確認（`codex.ensureImage`）で失敗したときは「Codex のイメージを用意できません（app-server を起こす前）」と出し、
`docker run` の失敗と分ける。@infodb/codex-workspace は app-server の stderr を捨てるので、P3 は小さな中継
（`src/server/preflight/launcher.mjs`）を挟んで、stdin / stdout はそのまま通し、stderr と終わり方だけを一時フォルダに残す
（読んだら消す）。

既定のエンジンは Codex で、認証は次の順に選ぶ: `codex.auth: legacy` と旧来の設定 → 旧来の `auth.json` /
ChatGPT に接続済み → ChatGPT プラン / 旧来の設定（`codex.authVolume` / `codex.authFile`）だけ → 旧来の `auth.json` /
どれも無い → 使えない（画面と CLI でサインインを案内する。**認証が無いときに Mock に切り替えない**）。

**Mock**（要望本文の箇条書きをそのままタスク案にするだけの簡易評価）は、`preflight.engine: mock`（`PCUBE_PREFLIGHT_ENGINE=mock`）か `--engine mock` で
明示したときだけ使う。再評価ではメモの箇条書きを案に足し、
前回不採用にした案（同じ題）は不採用のままにする。メモの意味は解釈しない。Codex を使えない環境で画面とファイルの流れを
確かめるためのもの。

Preflight でステータスが動くのはタスク化する前の要望（下書き → 評価中 → 開始前）だけで、
進行中・完了の要望を再評価してもステータスは変わらない。

## 画面

`pcube serve` で開くローカルのビューア兼エディタ（React + TanStack Router + Tailwind CSS）。
画面の状態は URL に載るので、URL を共有すれば同じ画面が開ける。

| URL | 画面 |
| --- | --- |
| `/` | 進捗。左に要望、右にスケジュール。下の記号で描く。`?show=` の既定は未完了（下書き・Preflight・レビュー済・進行中。対応済は含めない）、`resolved` で確認待ち（対応済）だけ、`closed` で完了済・見送り、`all` ですべて。対応済は確認待ちかすべてで見る。`?tags=`（タグ。複数選ぶとどれか。上の「タグ」）|
| `/requests/new` | 新しい要望 |
| `/requests/261009-k7m3x` | 要望の概要（期限・マイルストーン・タグ）と Preflight（`?run=PF-...` で過去の評価）。評価エンジンの状態も出す。ブラウザの幅をそのまま使い（上限なし）、1024px 以上で文脈とログを左右に並べる。狭い画面では縦に並べ、工程は今の工程の名前だけを出す。長いパスや参照は折り返し、タスク案の列は入りきらなければその中だけ横にスクロールする |
| `/requests/261009-k7m3x/board` | 要望のタスクボード（V 字。ドラッグで列を移動。完了カードの「✓ 済み」でボードから外す） |
| `/requests/261009-k7m3x/done` | 要望の対応済み（済みにしたタスクと成果物の一覧。要望のステータスの「対応済」とは別） |
| `/settings` | このマシンの ChatGPT プランの接続（「Continue with ChatGPT」・取消・解除・Manage usage）と、プロジェクト設定（マイルストーン・ドキュメントなど） |

要望の中のページでは `?task=T003` でタスク詳細を重ねて開く。

関係の一覧（タスク詳細の「関係」、Preflight の「既存項目への影響」）は同じ形で並べる（`src/web/components/RelationRow.tsx`）:
役割の列は幅を決め、その右に相手の参照と題、次の行に理由。確信度・由来・削除は右端。題が長ければ切って、マウスを乗せると全文
（狭い画面では2行まで）。理由は折り返す。狭い画面（375px）ではタスクボードの列を縦に積み、見出しやタブの文字は折り返さない。

再評価のタスク化では、置き換えられる既存タスクをタスク案の下に出す。チェックしたものだけをタスク化と一緒に
アーカイブし、チェックしなければ残す（作業中のタスクには印を付ける。アーカイブしても作業そのものは止まらない）。
残した置き換えられたタスクには、タスクボードのカードに「置き換え ← T005」（評価での置き換えなら「← 要望」）、
タスク詳細に置き換えた側を出す。作業中にすると移したうえで警告を出す（状態は 未着手 / 作業中 / 完了 のまま）。

進捗のスケジュールの記号:

| 記号 | 意味 |
| --- | --- |
| ○ / ✓ | 完了にした日 / 人が確認して「済み」にしたもの |
| ◐ | 作業中にした日 |
| □ | 未着手のタスク（今日の線の右に、残りの数だけ） |
| ⚑ | 要望の期限（過ぎて未完了なら赤） |
| ◆ と縦の破線 | マイルストーン |
| 縦の線・丸囲みの日付 | 今日 |

どの印もクリックするとタスクの詳細が開く（進捗の画面のまま）。同じ日・週・月にまとまった印は件数が付き、クリックで
中のタスクを選ぶ。「済み」は詳細の「済みにする」ボタン（または `pcube check`）で付け外しする。

狭い画面（スケジュールの枠の幅が 640px 未満。スマートフォンなど）では、左の要望の一覧を枠の幅の 36%（112〜380px。375px で
135px）に縮め、ステータスを上に、タイトルを下に2行まで出す（全文は要望の画面で）。右のスケジュールには残りの幅
（375px で 240px）を使い、横にスクロールして印をタップする。640px 以上の表示（380px の一覧）は変えない。見出しの
プロジェクト名は、収まらなければ省略する。

期間に上限はなく、データのある全期間（最初の出来事から、最後の期限・マイルストーンまで）を描く。描画するのは
見えている範囲の日付・印・行だけ（仮想スクロール）なので、1年・2年と運用して横に長くなっても重くならない
（2年分・要望300件・タスク3,000件で、描く要素は画面1枚分の約250〜1,000、表示まで約0.3秒）。
ズーム（日 / 週 / 月。1日あたり 30 / 10 / 3px）で長い期間を見渡せる。ズームは URL（`?zoom=week`）に載り、
切り替えても画面中央の日付を保つ。「今日」ボタンで今日に戻る。マウスを乗せると内容を大きめの文字で出す。

要望のステータスは、並べて位置がそろうよう3文字: 下書き（Preflight 前）/ 評価中 / 開始前（評価済み・タスク化の前）/
進行中 / 対応済（作業は終わり、人の確認待ち。水色の枠）/ 完了済 / 見送り。一覧で長いタイトルは「…」で切り、マウスを乗せると全文が出る。
要望の概要でステータスを選べる。対応済にできないとき（未完了のタスクがある）は理由を出して変えない。
対応済なのに未完了のタスクがある（ファイルの直接編集など）ときは知らせを出し、「進行中に戻す」で直せる。

要望の画面の見出しはタイトルとタスクの完了数だけ。ステータス・要望 ID は概要・Preflight の管理情報に出す（ブランチ名は `p3 request show` で見る）。
要望 ID はタイトルの入力欄の上にあり、横の「コピー」ボタン（アイコンつき。キーボードでも押せる）で ID の全文をクリップボードに入れる。
コピーできないとき（http で別のマシンから開いていてブラウザがクリップボードを使わせない、拒まれたなど）はそう知らせるので、
ID をクリックして選び、手でコピーする。

ページは TanStack Router のファイルベースのルーティングで、`src/web/routes/` にファイルを置けば足りる。
ページの中身もそのファイルに書き、複数のページで使う部品だけを `src/web/components/` に置く
（`requests/$requestId.tsx` は要望の枠、`requests/$requestId/board.tsx` → `/requests/:id/board`、`__root.tsx` は全画面共通の枠）。
ルート一覧 `src/web/routeTree.gen.ts` は `pnpm dev` / `pnpm build` / `pnpm typecheck` のたびに生成される
（設定は `tsr.config.json`。生成物だが、型検査のためにコミットしておく）。

## AI エージェントから使う

AI にも CLI を使わせる（API ごとの認証を持たせずに済む）。管理したいリポジトリで `p3 init --agents` を実行すると:

- `AGENTS.md`（無ければ `CLAUDE.md`、どちらも無ければ `AGENTS.md` を作る）に、短い使い方を追記する
  （内容は [docs/architecture.md](docs/architecture.md) の「AI エージェントへの指示」。見出しがあれば重ねない）
- `.claude/skills/p3/SKILL.md` に、手順の詳しい版のスキルを置く（パッケージに同梱した `skills/p3/SKILL.md` の写し）

新しくプロジェクトを作るときにも、既にあるプロジェクトに参加するときにも使える（端末からなら聞かれる。非対話では `--agents`
を付けたときだけ）。どちらにも「Preflight とタスク化は人が行う」「AI は作業を終えたら対応済にし、完了済・見送り・済みは人が決める」
などの同じ役割を書いてある。置いたファイルはリポジトリに入れて共有する。

**P3 を新しくしたとき:** 既に置いたスキルは、内容が違っても上書きしない（手で直した分を消さないため）。`p3 init --agents` を
もう一度実行すると「最新です」か「同梱の版と違う」かを出すので、違えば表示された同梱の原本と見比べて手で更新する。
`AGENTS.md` / `CLAUDE.md` の追記も、見出し（`タスク管理（infodb p3）`）があれば足さないので、新しい内容は
docs/architecture.md の版と見比べて手で直す。

- 要望のブランチ（作業ツリーでもよい）で作業すれば、要望を指定せずに `pcube move` / `pcube new` が使える
- 作業中に新しく必要になった作業は、AI がそのままタスクとして足す（可視化される）
- 人への質問（Human in the Loop）はタスクにせず、Claude Code などのチャットで行う

ブラウザ用の REST API（`/api/...`、自己記述は `GET /api/ai/manifest`）もあるが、ローカルの画面のためのもの。

## pcube 自体の開発

```bash
pnpm dev                     # API サーバ（pcube serve, tsx watch）+ Vite  http://localhost:5173
pnpm build && pnpm start     # ビルドした画面を pcube serve から配信  http://localhost:4310
pnpm typecheck
pnpm test                    # ユニットテスト（vitest）。pnpm test:watch で監視
pnpm check                   # 型検査 + テスト + ビルド
pnpm demo:reset              # デモデータ（.pcube-demo/）を作り直す
pnpm verify:pack             # 配布物を別の場所に入れて動かす（--docker で codex update も）
```

`pnpm dev` / `pnpm start` は pcube 自身の開発を題材にしたデモデータ（`.pcube-demo/`、git 管理外）を開く。
デモデータは無ければ自動で作られる（`scripts/demo.ts`。製品のコードではないので `src/` の外に置いている）。
作るときに実際に Preflight（Mock）を走らせ、評価・タスク案・タスク化・作業の進行（成果物つきの完了など）まで
済ませるので、マイルストーン・期限・タグを含めて各画面をそのまま確かめられる。
`pnpm demo:reset` はこのデモデータを作り直すだけで、実際のプロジェクトの `.pcube/` には触れない。
`.pcube-demo/` が既にあると `pnpm demo`（`pnpm dev` / `pnpm start` の前）は何もしないので、デモの例が増えたとき
（例: 成果物に URL・文章・パスを混ぜた例。「要望ごとのタスクボード」の T001 は済み＝対応済みの一覧、T002 は完了＝ボード）
は `pnpm demo:reset` で作り直す。手で直した内容も消えるので、残したいものは先に別の場所へ写しておく。
実際のプロジェクトのデータは、デモの作り直しでは変わらない（成果物は保存の形が同じなので、移し替えも要らない）。
デモの中身は `scripts/demoData.ts`（テストからも一時フォルダに作って確かめる）。
サーバと Vite は既定で `0.0.0.0` で待ち受ける（DevContainer の外から見るため）。認証は無いので、
信頼できないネットワークでは `serve.host: 127.0.0.1`（`PCUBE_HOST=127.0.0.1`）に絞ること。

テストは一時ディレクトリに git リポジトリと `.pcube/` を作って動かす（`test/helpers.ts`）。
Codex の経路は、JSON-RPC を話す偽の app-server（`test/fixtures/fake-codex.mjs`）に差し替えて確かめる。
CLI のテストは別プロセスで `bin/pcube.mjs` を動かし、個人設定を一時フォルダに分け、このマシンの `PCUBE_*` の環境変数は効かないようにしている。

### npm で配る中身

`@infodb/p3` として npm に公開する（公開そのものは人が行う）。TypeScript のソースを `tsx` でそのまま動かし、
画面だけをビルドして同梱する。

| 何を | どうする |
| --- | --- |
| 同梱するもの（`files`） | `bin/`・`src/cli`・`src/server`・`src/shared`（実行するソース）、`dist/web`（ビルド済みの画面）、`skills/`（AI 向けスキルの原本）、README・LICENSE |
| 同梱しないもの | `.env`・個人設定・デモデータ（`.pcube-demo/`）・テスト・`scripts/`・画面のソース（`src/web`）・開発用のスキル（`.claude/`） |
| 実行時の依存 | `tsx`・`hono`・`@hono/node-server`・`yaml`・`zod`・`@infodb/codex-workspace`。React などの画面の部品はビルドに使うだけなので開発用 |
| Node | `>=22`（`@infodb/codex-workspace` と同じ。Node 22.0.0 で tsx が `await using` を変換して動くことを確かめた）。開発（Vite 8）は Node 24 を使う |
| 公開前のビルド | `prepack` で `pnpm build`（`npm pack` / `npm publish` の前に画面を作る）。利用者が入れるときにはビルドも Docker の操作もしない |
| bin | `p3` と `pcube`（同じもの）。起動口は今いる場所の `tsconfig.json` を読まない。`INIT_CWD` に戻るのは P3 自身の `pnpm p3` スクリプトのときだけ |

```bash
pnpm -s check                       # 型検査・テスト・画面のビルド
pnpm verify:pack --docker           # npm pack → 実行時の依存だけで別の場所に入れて動かす（scripts/verify-pack.mjs）
```

公開の手順とチェックリストは [docs/publishing.md](docs/publishing.md)。

## 構成

```
src/
  shared/            型定義・参照の解き方・日付（サーバ/Web 共通）
  cli/               pcube CLI（ファイルを直接操作。serve でサーバも起動する）
  server/
    ops.ts           CLI と API で共通の操作（参照・関係の規則・進捗の集計など）
    store/           要望のフォルダとタスクのコレクション、frontmatter、Preflight の保存、監視
    intel/           関係グラフ・影響範囲・類似検索（インテリジェンス層）
    preflight/       エンジン（codex-workspace / mock）と実行・タスク化
    api/             REST + SSE
  web/               React + TanStack Router + Tailwind（text-base 基準）
    routes/          ページ（1ファイル1ページ。__root.tsx が共通の枠）
    routeTree.gen.ts ルート一覧（自動生成）
    components/      複数のページで使う部品（タスク詳細のドロワー、要望のステータスなど）
bin/pcube.mjs        CLI の起動口（tsx でソースをそのまま動かす）
scripts/demo.ts      開発用のデモデータを作る
docs/                設計の方針
test/                ユニットテスト（store / locate / intel / ops / preflight / api / cli）
```
