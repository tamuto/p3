# 構成の方針: ローカルで完結させる

pcube は **ファイルが唯一の正（source of truth）で、すべてローカルで完結する** ことを前提にする。
サーバ（S3 / API Gateway / Cognito など）にデータを置く案も検討したが、採らない。以下はその判断と、
残っている課題の整理。

## 作業の単位は要望

Preflight で扱う要望が、プロジェクトで行う作業の粒度になる。そこで **要望ごとにフォルダを作り**、
そこから生まれたタスクや評価の記録はすべてその下に置く。要望 = フォルダ。ブランチ（作業ツリー）は作業先のリポジトリごとに1つ。

```
<データのフォルダ>/requests/<作成日-乱数>/request.md
                              tasks/T001.md ...
                              preflight/<run>/...
```

- **要望の ID は作成日 + 乱数5文字**（例: `261009-k7m3x`）。時刻順に並び、人が読み書きでき、
  複数人が別々に作っても実用上衝突しない。タイトルは後から変わるので含めない（ULID は人が扱うには長い）
- **一覧の並び**は日時だけで決めず、同じ日時のときの第2キー（ID）を必ず持つ（README の「一覧の並び」）。
  乱数を含む ID の順は作った順ではないので、「作った順」が要るところは日時で比べる。
- **タスクは要望をまたいで移動しない** ので、要望の中の素直な連番（T001, T002, ...）で採番できる。
  `tasks/.archive/` にある ID も使用済みとして扱い、再利用しない（アーカイブしたタスクへの関係が新しいタスクを指さないように）。
  守れるのはアーカイブのファイルが残っている範囲まで。消したアーカイブの ID や、既に再利用された ID は直さない。
  同じ要望を複数人が同時に触ることは少なく、触る場合の排他は人が行う
- 要望をまたぐ関係（影響・依存）は `<要望ID>/T003` の絶対参照で書き、インテリジェンス層が要望を横断して辿る
- タスクボード（V 字: 未着手 → 作業中 → 完了。済みにすると消え、対応済みの一覧へ）は要望の中で見る。進捗は要望ごとの状況を横断して見る
- 日程は要望の単位で持つ（期限）。リリースは複数の要望をまとめることがあるので、マイルストーンで束ねる
- タスクは予定の日付・見積り・進捗%を持たない。AI が実施する作業の量や期間は人の感覚では見積もれず、
  AI に自己申告させても正確にはならないため。代わりに、ステータスを変えた日時（作業中にした＝着手を指示した目安、
  完了にした）を pcube が記録する
- タスクは AI か人が実施する。人から見て要るのは「まだ動いていない / AI が処理中 / 処理が終わった」だけなので、
  状態は 未着手 / 作業中 / 完了 で固定する（保留・取りやめは持たない）。終わったもの（PR・MR・ドキュメント）のレビューは成果物の側で行い、タスクとしては完了にする
- 担当者（メンバー）は持たない。誰が変えたか（`ai:claude` / `human:<git の user.name>`）だけを記録する
- AI が作業中に見つけた追加の作業は、AI がそのままタスクとして足す。人への質問（Human in the Loop）は
  タスクにせず、Claude Code などのチャットで行う

## プロジェクトの置き場所と個人設定

管理したいシステムは、本体・ドキュメント・基盤のように **複数のリポジトリに分かれている** ことが多い。
要望・Preflight・タスクはそれらを横断するので、プロジェクトのデータはどのリポジトリにも属さない
**データのフォルダ** に置く（場所は自由。例: `~/p3-data/myapp`、チームで同期するフォルダ）。

| 何を | どこに | 共有 |
| --- | --- | --- |
| プロジェクトのデータ（要望・タスク・Preflight の記録、`project.yaml`） | データのフォルダ | する（方法は下の「共有」） |
| 個人設定（参加しているプロジェクトとフォルダの場所、手元のリポジトリの場所、画面の設定、マシンごとの設定（Codex の認証の選び方・パスの対応・serve の待ち受けなど）） | `~/.config/infodb-p3/config.yaml` | しない |
| ChatGPT の接続（トークン） | `~/.config/infodb-p3/chatgpt.json`（所有者だけが読める） | しない |
| コード・ドキュメント | 各リポジトリ | 今までどおり |

- 手元のリポジトリの場所はマシンごとに違うので、プロジェクトのデータではなく個人設定に持たせる
- **操作するプロジェクトは環境変数では決めない**（同じ人が複数のプロジェクトを行き来するため）。
  `--project <名前>` → 今いる場所（登録したリポジトリ・作業ツリー・データのフォルダの中）→ 登録が1つならそれ、の順で決め、
  決まらなければ登録済みの一覧と選び方を出す（`src/server/store/locate.ts`）
- 使う人はフォルダや実行パスを意識しない前提で、セットアップは2段階まで・エラーは次にすることを示す、を守る
- リポジトリの中の `.pcube/` も以前の置き方として読める（デモ・テスト）
- 個人設定の書き換えは、ロック（`config.yaml.lock`）の中で最新のファイルを読み、対象の項目（プロジェクト1つの登録・
  `ui.theme`）だけを変えて書く（`updateUserConfig`）。init・project add / rm・テーマの保存が同じ経路を通るので、
  CLI と serve が同時に書いても消し合わない。壊れた YAML・読めないファイルは書かずにエラーにする（無いのとは区別する）。
  ChatGPT の接続（`chatgpt.json`）は別のファイル・別のロックのまま
- 画面のテーマ（`ui.theme`）の反映: index.html の先頭（CSS より前）で `/api/user-theme.js` を同期で読み、
  html 要素に `data-theme`・class `dark`・`color-scheme` を付ける（Tailwind の `dark:` は class `dark` を見る
  `@custom-variant`。OS のメディアクエリでは切り替えない）。応答はテーマだけを埋め込み `no-store`。その後は画面の
  `web/lib/theme.ts` が持ち、`system` の間だけ `prefers-color-scheme` の変化を購読する。保存先は個人設定だけで、
  localStorage は使わない。ほかのプロセスでの変更は読み直しで反映する
- 設定画面のテーマの選択は、選んだらすぐ `PUT /api/user-theme` で保存し、保存できてから画面に反映する
  （`web/lib/themeSave.ts`。保存中に続けて選んだら、終わってから最後の選択だけを保存する。失敗したら保存済みの表示に戻す）。
  ブラウザでの確認（2026-10-11、ビルドした serve と Vite の開発サーバ、Chromium）:
  - テーマ3つ × OS の明暗の6通りで、進捗・要望の概要（Preflight）・タスクボード・TaskDrawer・対応済み・要望の作成・設定の
    7画面が期待どおりの明暗になる。OS と逆の固定のテーマでも、画面のスクリプトを止めて CSS を遅らせた最初の描画から正しい
    背景と文字の色になる（color-scheme でフォームなどブラウザの部品もそろう）
  - system の間は表示中に OS の明暗を変えると追従し、固定のテーマは変わらない
  - 設定画面でキーボード（矢印キー）で選べ、個人設定に保存され、読み直し・serve の起動し直しでも保たれる。CLI（`p3 user-config`）と
    同じ値。CLI で変えたら読み直しで反映し、同じ serve のほかのタブの設定画面には変更通知で反映する
  - テーマを変えても編集中のプロジェクト設定は残り、プロジェクト設定を保存してもテーマは消えない（ChatGPT の接続のファイルとは
    別のファイルで、互いに消さないことはテストで確かめた。実際のサインイン・解除はこの確認では行っていない）
  - 1280px と 375px で選べる。375px の設定画面の横のはみ出し（見出しの「新しい要望」とマイルストーンの行）は以前からのもので、
    テーマの欄によるものではない
- 進捗のスケジュールの狭い画面: 左の一覧の幅を枠の幅から決める（`web/lib/timeline.ts` の `leftWidth`。640px 未満で
  枠の 36%・112〜380px、640px 以上は 380px）。スケジュールの見える幅（`scheduleSpan`）・描く期間の右端・見える範囲の判定・
  今日への移動・ズームの中央の日付は、すべてこの幅から計算する（測る前は幅 0 で、見える幅は負にならない）。行の高さと
  縦の仮想スクロールは変えない。ブラウザでの確認（2026-10-11、Chromium、デモのデータと 150 件・約2年分のデータ）:
  - 1280px は日・週・月とも、一覧の幅・今日の線・印・行の位置・スクロール量・画像が変更の前と同じ
  - 375px（タッチ）で一覧 135px・スケジュール 240px。印をタップして正しいタスクの詳細を開閉でき、まとまった印は Picker で
    選べる（画面の中に収まる）。期限の日付はタップで出る。日・週・月、「今日」、横・縦のスクロール、空の一覧、タグ・状態の
    絞り込み、ライト・ダークで確認し、ページの横のはみ出しは無い（見出しのプロジェクト名を省略できるようにした）
  - 1280 → 640 → 639 → 375 → 639 → 640 → 1280 と幅を変えても、境目の前後ではみ出さず、見える幅は正のまま
  - 150 件・約2年分でも、一番下・一番右まで描け、描く行は画面の分（14〜17 行）だけ
- タグ（要望の `tags`）は外部 ID・分類のための自由な文字列。仕様（用途・対象外・入力の決まり・絞り込み・URL）は README の
  「タグ（外部 ID・分類）」にまとめた。保存の形（文字列の配列）は変えない。
  - 入力（`components/TagInput.tsx`、`shared/tags.ts`）: 値ごとに足す・外す。要望の管理情報では足す・外すたびに編集を始めた
    ときの rev で保存し（保存中は次の操作を待たせる）、下書き（`web/lib/draft.ts`）で持つので取り直しても入力中の値は残る。
    入力欄のまだ足していない文字は、新しい要望では作成のときに足す
  - 進捗の絞り込み（`components/TagFilter.tsx`、`web/lib/requestFilter.ts`）: ヘッダーにはボタンだけを置き、開いた中
    （画面に固定。ボタンの下で画面の幅に収める）に検索・選択中（高さを決めてスクロール）・候補（同じ。一度に 200 件まで）を
    出す。URL は `tags`（ルーターが JSON の配列で書く）。以前の `tag` は読むだけで、選び直すと外す
  ブラウザでの確認（2026-10-12、Chromium）:
  - 1280px: 検索して2つ選ぶと、どちらかの付いた要望だけになり（OR）、「未完了」に切り替えると対応済の要望が消える（AND）。
    ヘッダーの高さは選ぶ前と同じ。Escape で閉じてボタンにフォーカスが戻る。URL の読み直し・戻る・進むで選択が戻り、
    ズームと状態は残る。以前の `?tag=` は1つ選んだものとして読む。`a,b` や `記号 & ? # / %` も URL を往復して残る
  - 選んだタグを CLI で外して「再読み込み」すると、選択は「（該当なし）」として残り、要望は0件。× で外せる
  - 候補 1007 件: 並べるのは 200 件で、検索で絞るよう知らせる。開いた中の高さは 372px。375px（タッチ・ライト／ダーク）でも
    開いた中は画面の幅に収まり（左右 16px）、ページの横のはみ出しは無い。外をタップすると閉じる
  - キーボードだけで開く・検索・選ぶ（Space）・すべて解除できる
  - タグの入力（1280px ライト・375px ダーク）: 前後の空白を除いて足し、カンマを含む値は1つのまま、同じ値は「付いています」と
    知らせて足さない。× はキーボードでも押せる。書きかけの値は「再読み込み」しても残る。長い値（108 文字）は折り返して全文を
    出し、横にはみ出さない。新しい要望は Enter で足した値と書きかけの値（`x/y, z`）の両方を付けて作る
  - 開いた中が、スケジュールの左の列（sticky, z-30）の下に隠れていたので z-50 にした
- Preflight の参照先（`shared/repos.ts`・`server/repoRefs.ts`）: 共有の定義は project.yaml の `repos`（名前をキーにした対応。
  名前・役割・readFirst・writable・主なフォルダ map。入口 entry がそのフォルダで最初に読むファイル）、このマシンのパスは個人設定の `projects.<p>.repos`。
  `Workspace.refs()` が始めるたびに合わせ、`ok / unregistered / missing / notdir` を決める。`p3 init` が本体を参照先として
  登録する。`p3 repo` は project.yaml の `repos` の1件だけを書き（`writeRepoEntry`。コメント・知らない項目は残す）、
  設定の保存（画面・`p3 config`）は `repos` を書き換えない。コンテナの中の名前（mount）は論理名から英数字と `. _ -` だけで作り、
  重複は番号で分ける。参照の書き方 `<名前>:<パス>`（`parseRepoPath`）は areas・evidence で共通。名前なしは先頭の参照先。
  - マウント（`withMounts`）: dockerCommand の `/workspace` の bind を tmpfs に替え、参照先を `/workspace/<mount>` に
    `readonly` で、データを `/data` に置く。Codex の cwd は `/workspace` のまま。変更のパスは参照先の対応で戻す
  - 調べた範囲（`run.scope`）は P3 が始めるときに決めて残す（パスは入れない）。根拠（`assessment.evidence`）は Codex が書き、
    P3 が `parseEvidence` で確かめる（verified は読めた参照先の中の、ある相対パスを指すときだけ）
  - 本物の Docker（29.3.0）での確認（2026-10-12）: 生成した docker run の引数で、このマシンの3つのフォルダ（git のリポジトリ
    2つと、別のリポジトリの中のサブフォルダ1つ）を `codex.pathMap` で対応させてマウントし、コンテナの中で3つとも読め、それぞれへの
    書き込みは `Read-only file system` で拒まれ、`/workspace`（tmpfs）には書けた。ホストのフォルダには何もできていない。イメージの
    entrypoint を sh にして確かめたので、本物の Codex に評価させてはいない（認証が要る）
- タスクの成果物（`outputs: string[]`）は URL・文章・パスを1項目ずつ混ぜてよい。画面は `components/Outputs.tsx` で、
  項目全体が絶対の http(s) URL（`web/lib/outputs.ts` の `outputHref`。前後の空白は判定でだけ除く）ならリンク、ほかは文字。
  保存の形を変えないので、既存のデータの移し替えはしない（実データの読み取り確認: 2026-10-12、要望 24・タスク 51・
  成果物 64 項目のうち 63 項目が URL でリンクになり、1 項目は「branch req/…（コミット）」の文章で同じタスクに PR の URL も
  ある。アーカイブのタスク 3 件は画面に出ないので対象外。読むだけで何も書いていない）
  ブラウザでの確認（2026-10-12、Chromium、一時フォルダに2回作り直したデモ。1280px ライト・375px ダーク）: ボードの完了の
  カード（T002）は PR のリンク1つと文章・パスを出し、リンクは別のタブで開いてカード（詳細）は開かない。済みの T001 は
  詳細と対応済みの一覧で2つのリンクと文章・パスを出す。長い文章・パスは折り返し、横のはみ出しは無い。詳細で成果物を
  書きかけのまま外で更新されてタブに戻ると、入力は残って知らせが出て、保存すると競合になり、入力は残る
- 全件の読み直し（`Workspace.reloadAll`、`POST /api/reload`）: project.yaml・要望・全タスクをディスクから読み、読み終えて
  から同期でまとめて入れ替える（`MarkdownCollection.prepareLoad` → `commit`。読んでいる途中の空や半分の状態は見せず、
  要望だけ新しくタスクは古い、ということもない）。読み込みの間に作成・更新・アーカイブ・1件の読み直し（監視）があった ID は、
  読んだ結果ではなくその時点の状態を残す（タスク化や画面からの保存を、先に読んだ古い内容で戻さない）。タスクのコレクションは
  作り直さない（処理中の操作が持っている参照に書いた結果も残る）。同時には走らせず、読み込み中の呼び出しは終わってから
  もう1回にまとめる。project.yaml とデータのフォルダが読めなければ ReloadError（503）で何も変えない。終えたら変更通知
  `changed`/`reload` を出し、関係・検索の索引（ProjectIndex）はこれで作り直す。Preflight の履歴・メモは問い合わせのたびに
  ディスクを読むので扱わない。応答は読み直しを終えた後（画面はその後に取り直す）。ほかの serve・CLI が同時に書いている
  最中のファイルは、読んだ時点の内容になる（次の読み直しで追いつく）
- 画面の取り直し（`web/lib/appData.tsx`）: `reload` は API から取り直すだけ（変更通知・保存の後）、`refresh` はサーバに
  全件を読み直させてから取り直す（`web/lib/refresh.ts`。ヘッダーの「再読み込み」と、タブが見えた・ウィンドウにフォーカスが
  戻ったとき。離れてから戻ったときだけで、両方続けて起きても1回）。実行中に頼まれたら終わってからもう1回だけ。取得は
  `web/lib/latest.ts` で最後に始めたものの応答だけを使う（読み直しより前に始めた取得の遅い応答で上書きしない）。自分の
  再読み込み中に届いた `reload` の通知では取り直さない。どの通知でも全件の読み直しは呼ばない
- 入力の保持（`web/lib/draft.ts`）: 要望のタイトル・タグとタスク詳細は下書き（値・編集を始めたときの値と rev・外の最新）で
  持つ。編集していなければ追従し、編集中は上書きせず知らせる。保存は編集を始めたときの rev。古い rev の応答は無視する。
  済み・関係の操作のように入力欄以外を自分で変えたときは、入力欄の項目が変わっていなければ自分の上げた rev に合わせる。
  要望の取り直し（`web/lib/requestLoad.ts`）: 404 は表示中なら gone（前の内容と入力を残して保存を止める）、初めからなら
  「見つかりません」。ほかの失敗は前の内容のまま知らせる。要望を移ると作り直す（`RequestDataProvider` の key）
  ブラウザでの確認（2026-10-12、Chromium、serve の監視は効かない状態のまま。外での変更は CLI とファイルの直接編集）:
  - 「再読み込み」で、同じ要望の2回の置換保存・タスクの追加・アーカイブ・関係の追加・要望のフォルダの削除・設定の説明の変更が、
    ブラウザのリロードなしに（同じ document のまま）反映し、POST /api/reload は1回。URL と開いているタスクはそのまま
  - タブが隠れて見えたときも同じく反映する。続けて5回戻る・フォーカスが行き来しても読み直しは2回（実行中の分 + もう1回）。
    戻らなければ 10 秒待っても問い合わせない
  - 要望のタイトルの入力中に外で変わると、入力を残して知らせ、Enter で保存すると競合（サーバの値は外の値のまま）。
    「入力を捨てて最新にする」で最新になる。タスク詳細の本文も同じで、タスクがアーカイブされると「見つかりません」を出し、
    入力を残して保存を止める。設定の説明・新しい要望の入力・Preflight のメモも残り、要望のフォルダを消すとメモを残したまま
    知らせて保存のボタンを止める（未処理の例外は無い）

1人1つのサーバで画面からプロジェクトを切り替える形（決定済み）は、次の段階で入れる。

## 役割

```
            ┌──────────── 各メンバーのマシン ────────────┐
  人 ──┐    │                                            │
       ├─▶  pcube CLI ──┐                                │
  AI ──┘                ├─▶ <データのフォルダ>/*.md ◀── 読み直し ── pcube serve ──▶ ブラウザ（ビューア）
  人 ─────▶ ブラウザ ───┘        ▲                         │
                                 │ ファイル契約             │
            Codex（自分のアカウント, コンテナ内で /workspace = repo, /data = データのフォルダ）
            └────────────────────────────────────────────┘
                         │ 共有は同期だけ（git）
                         ▼
                    GitHub などのリモート
```

| 部品 | 位置付け |
| --- | --- |
| データのフォルダ（Markdown / YAML / JSON） | 正。タスク・要望・Preflight の記録。人も AI も直接読める |
| CLI（`pcube`） | 主な操作口。人も AI も使う。ファイルを直接読み書きするので **認証が要らない** |
| `pcube serve` + ブラウザ | ローカルのビューア兼エディタ。ファイルを読んで画面に流す（外での変更は「再読み込み」で取り込む。監視は補助）。データは持たない |
| Codex（`@infodb/codex-workspace`） | 操作する人のマシンで、その人のアカウントで動く。リポジトリとデータのフォルダだけを見せたコンテナの中 |

CLI は serve を経由せずファイルに直接書く（serve が常に動いている前提にしない。プロジェクトを跨いでも書き先の制御が増えない）。
serve の中で起きたこと（画面からの保存、Preflight の進み具合と終了）は SSE で画面に届く。外での変更は、画面の「再読み込み」と
タブ・ウィンドウに戻ったときの読み直し（POST /api/reload）で取り込む。ファイル監視は補助で、届かないことがある
（NFS。Node v24.21.0 の再帰的な監視は、置き換えて保存したファイルの2回目以降の変更を通知しないことを確かめた）。

REST API はブラウザのためのローカル API として残すが、AI には CLI を使わせる。
CLI がファイルを直接触る形なら、API ごとに認証を持たせる問題はそもそも起きない。

## サーバに置かない理由

1. **Codex の置き場所が決まらない。** サーバ側で Codex を動かすと共有アカウントになる（OpenAI の規約上も避けたい）。
   ユーザーごとにサーバへ認証情報を預けるのは運用が重い。ローカルなら各自のアカウントで動き、何も預けない。
2. **プロジェクトのドキュメントがサーバに寄ってしまう。** Preflight はリポジトリのコードとドキュメントを読んで判断する。
   サーバ側で判断するなら、それらをサーバへ複製し続ける必要がある。ローカルならリポジトリをそのまま見せればよい。
3. **認証・運用のコスト。** Cognito を使っても、CLI・AI・ブラウザそれぞれのトークン管理が残る。

外部に出ていくのは、各自が自分の Codex で OpenAI に送る内容だけになる（これは Codex を使う以上避けられない）。

## Codex の使い方

- Preflight は **実行した人のマシン** で、`codex-workspace` のコンテナの中で動く。コンテナには管理対象リポジトリを
  `/workspace`、データのフォルダを `/data` としてマウントする。データのフォルダはリポジトリの外にあってよい。
  認証情報は各自の ChatGPT の接続か `auth.json`（個人の場所に置き、プロジェクトには置かない）。
- 結果は戻り値ではなく **ファイル**（要望のフォルダの `preflight/<RUN>/assessment.json`, `drafts/*.md`）。
  同期すればチームの全員が同じ評価とタスク案を見られる。誰が実行したかは `run.json` とタスクの `updatedBy` に残る。
- 同じ要望を複数人が Preflight しても、run ごとに別ディレクトリ（ID に乱数を含む）なので衝突しない。
  「直近の run」は開始時刻の新しい順で決めるが、時計は戻ることがある（WSL2 の時刻の補正など）ので、前回を引き継いだ run
  （`previous`）は引き継いだ相手より必ず新しいとする（`preflightStore.ts` の `newestFirst`）
- Codex との会話は続けない（1 run = 新しいコンテナ・新しいスレッドで1往復）。確認事項への回答や方針の変更は
  **メモ**（要望のフォルダの `notes/N-....md`。1件1ファイル、書いた人と日時つき）として書き足し、次の run に
  前回の結果と一緒に渡す。経緯がファイルに残り、別の人が続きから Preflight できる。
  - 前回: 直近の run が完了していて評価を読めるときだけ引き継ぐ。失敗・欠損なら古い成功 run に戻らず「前回なし」
  - メモ: 前回を引き継ぐなら、引き継ぎの経路（`run.json` の `previous` を辿った run）で渡し済みのものを除く。
    失敗した run に渡しただけのメモは渡し済みにしない。前回を引き継がないなら全部渡す
  - 選んだものは開始の時点で `carryover.md` に固定し、`run.json` に `previous` と `notes`（メモの ID）を残す。
    実行中に書き足したメモは次の run に回る
  - 再評価のプロンプトには `carryover.md` の内容を資料として入れる。メモは尊重するが、書き込み先などの制約は変えさせない
  - 操作は `p3 preflight <要望> --note "..."`（書き足してから実行）、`--note-only`（書くだけ）、`p3 notes <要望>`（一覧）。
    実行を始められなくてもメモは残るので、再試行でメモを書き直さない
  - 画面のメモ欄は評価の下に1つだけ置く（評価を読んでから書くため）。評価が無い間（実行中・失敗）も同じ並びの位置にあり、
    入力中の文は保つ（別の要望に移ると消える）。評価の確認事項の「メモ欄で答える」から入力欄に移れる
  - まだ一度も実行していなければメモ欄は出さない。CLI などで先に保存したメモがあればそれだけを見せ、最初の Preflight に渡す
    （API と CLI は最初の実行の前のメモも受け付ける）
  - 入力中のメモがある間は、上の通常の実行を止める（入力が渡らないまま実行されないように）。「保存して再実行」で保存してから
    実行するか、入力を消す。保存済みのメモだけなら通常の実行でも渡る
  - 実行中も「メモだけ保存」はでき、実行中の評価ではなく次の Preflight に渡る。保存してから始められなかったときは、保存済みと
    伝え、書き直さずに再実行できる。過去の run を表示していても、引き継ぎ元は直近の run なので、何を引き継ぐかを入力欄の上に出す。
    run ごとに、引き継いだ前回の run（クリックで移る）と渡したメモを表示する
- Codex に書かせてよいのは run ディレクトリ（`/data/requests/<要望ID>/preflight/<RUN>/`）だけ。それ以外の変更は検出して警告する（git 差分による検出は今後）。

### 置き換えられたタスク

再評価でタスク化すると、新しい案が同じ要望の古いタスクを置き換える（`supersedes`）ことがある。
タスクの状態は 未着手 / 作業中 / 完了 の3つのままにし、置き換えは関係として扱う（`src/server/supersede.ts`）。

- **タスク化で知らせる候補**: 評価の `impacts` と **採用した** 案の `relations` にある `supersedes` のうち、
  同じ要望にある未完了（未着手・作業中）のタスク。不採用の案だけにある関係・完了したタスク・無いタスク・
  別の要望・要望そのものは候補にしない。
- **アーカイブは選んだものだけ**（既定はどれも残す）。確定の時点で候補を読み直し、候補でない・rev が変わった
  ものがあれば何も変えずに失敗する（もう一度確認してもらう）。作業中のタスクをアーカイブしても、作業そのものは止まらない。
- **順序と再試行**: 新しいタスクと関係を保存してからアーカイブする（古いタスクを先に外さない）。途中経過は
  `run.json` の `materialization`（作った案とタスク、選んだもの、アーカイブ済み）に残し、途中で失敗したら同じ
  タスク化をもう一度行えば、作った案は作り直さず、アーカイブも重ねずに続きから終える。
- **印**: 保存済みの要望とタスクの `relations` にある直接の `supersedes` から導く。評価にだけあった置き換えは
  タスク化で要望の関係として残るので「要望単位の置き換え」として出し、特定の新しいタスクへ推測して配らない。
  案に書かれた置き換えは、その案から作ったタスクの関係として残る。
- **進捗**: 残したタスクは進捗に数える（完了しないと要望の全タスクは終わらない）。アーカイブしたものだけが外れる。
- タスク化の結果は `{ tasks, archived, kept }`（作ったタスク、アーカイブしたもの、置き換えられるが残したもの）。
  以前は作ったタスクの配列だった（CLI の `accept --json` と API の POST materialize。利用者は `.tasks` を読む）。
- **着手の警告**: 置き換えられたタスクが作業中に変わったとき（CLI の `move` / `set`、API の PATCH、画面のボードと詳細）、
  操作は行ったうえで `warnings`（code・対象・置き換えた側・文言）を返す。作業中のままの再指定では出さない。
- API: `GET .../preflight/:run/materialize` で確認（何も変えない）、`POST` に `{archive: [{id, rev}]}`。
  要望の詳細と タスクの GET は印 `superseded` を返す。

### codex-workspace の依存

Codex をコンテナで動かす部品は npm の `@infodb/codex-workspace`（llmcs の codex-workspace-ts）。package.json では
公開版の版の範囲（`^0.2.0`）で指定し、手元のフォルダへのリンク（`link:` / `file:`）は置かない。新しくチェックアウトしても
隣に llmcs が無くて構わない。新しく公開された版は、pnpm の `minimumReleaseAge`（公開から1日）を過ぎるまで入れない。
待たずに入れるための例外（`minimumReleaseAgeExclude`）はリポジトリに残さない。

P3 が使う公開 API と約束:

- `dockerCommand(workspace, { accessTokenEnv | authVolume, authFile })` が作る `docker run` は、作業場所を
  `/workspace` にマウントする。P3 はそのマウントの直後に、データのフォルダを `/data` にマウントする引数を足す
- `WorkspaceSession.open(command, { model, effort, env, clientInfo, onEvent })` で app-server を起動する。ChatGPT の
  トークンは `env`（`ACCESS_TOKEN_ENV`）で渡し、`docker run` の引数や記録には値を出さない
- `UsageLimitError` は使用量の上限（ChatGPT プランの `subscription_sharing_usage_limit_exceeded` を含む）
- `ensureImage({ maxAgeMs })` はイメージが無いか `maxAgeMs` より古ければ作り直し、中の Codex の版を返す。作り直すたびに
  `CODEX_REFRESH`（その時刻）が変わるので、Codex を入れる段はキャッシュを使わず、その時点の最新が入る
  - いつもの Preflight: 既定の1日より古ければ作り直す（個人設定 `codex.ensureImage: false` か `PCUBE_CODEX_ENSURE_IMAGE=0` で止める）
  - 強制更新（`p3 codex update`）: `maxAgeMs` を -∞ にして、作った日時によらず作り直す。プロジェクト・認証を決める前に動き、
    個人設定の自動更新の停止（`codex.ensureImage: false`）とも関係しない。前に `docker version` でデーモンを確かめ、
    失敗した段（docker が無い / デーモン / 作成 / 版の取得）ごとに次にすることを出す（`src/server/preflight/codexImage.ts`）
  - テストは偽の docker（`test/fixtures/fake-docker.mjs`）で行い、本物の Docker では次で確かめる:
    `XDG_CONFIG_HOME=$(mktemp -d) p3 codex update --json`（未登録・未認証のまま。2026-10-11 に codex-cli 0.162.1 で約40秒）

手元の llmcs の変更を P3 で試すときは、一時的にリンクに替え、試し終えたら公開版に戻す（リンクはコミットしない）:

```bash
pnpm add @infodb/codex-workspace@link:../llmcs/codex-workspace-ts   # 一時的に手元の llmcs を使う
# …試す…
git checkout package.json pnpm-lock.yaml pnpm-workspace.yaml && pnpm install   # 公開版に戻す
```

`npm pack` やコミットの前に、`package.json` と `pnpm-lock.yaml` に `link:` が無いことを確かめる。
llmcs の変更を P3 で使うには、llmcs 側で新しい版を公開し、P3 の版の範囲を上げる。

## プロジェクトのドキュメントの扱い

- ドキュメントは **リポジトリに置いたまま**（`docs/`, README, コードのコメント）。pcube は複製も同期もしない。
- Codex はコンテナの中から、それらをリポジトリのファイルとして直接読む。
- pcube が作る記録（要望・評価・タスク案・タスク）もリポジトリ内の Markdown なので、それ自体がドキュメントになる。
  「なぜこのタスクがあるのか」は、タスク → 要望 → Preflight の評価と文脈（`context.md`）を辿れば分かる。
- Preflight で最初に読ませるドキュメント（設計方針・用語集など）は、参照先の主なフォルダ（`repos.<名前>.map`）に書き、
  そのフォルダで最初に読むファイルを入口（`entry`）にする。参照先ごとに書くので、どの参照先のファイルかが曖昧にならない
  （以前のプロジェクトの `docs` は、名前を付けないと先頭の参照先のパスになり分かりにくかったので外した。構成の説明の
  Markdown `mapFile` も入口と重なるので外した。どちらも保存のときに project.yaml から消す）。
  `preflight.instructions` にはプロジェクト固有の評価の観点・制約を書く。どちらも Codex への指示に加わる。

## 共有（同期）の方法

同期の手段は **git**（またはファイル共有）。要望のフォルダ単位で push / pull すれば、その要望の状況を共有できる。
開発者はすでに認証済みで、履歴（誰がいつ状態を変えたか）、PR による Preflight 結果のレビュー、
1タスク1ファイルによる小さな差分がそのまま使える。排他制御は人が行う（同じ要望を同時に触らない）。

### 解決したこと

- **ID の衝突** — 要望は作成日 + 乱数、タスクは要望の中の連番にしたので、別々の人が作った要望どうしは衝突しない
- **状態がブランチごとに分岐する** — データはリポジトリの外のデータのフォルダに書く（リポジトリの中の `.pcube/` の場合も
  git のメインの作業ツリーのものに書く）。要望の作業ツリーの中で実行しても書き込み先は1か所で、今の要望は今いる参照先のブランチから決まる

### 残っている課題

1. **データのフォルダの共有方法（保留）。** データのフォルダ自体を git リポジトリにして `p3 sync`（pull → commit → push）で
   同期する案があるが、使い勝手を見てから決める
2. **rev による偽の衝突。** frontmatter の `rev` は、同じタスクの別々の項目を変えただけでも git のマージで衝突する。
   ファイル内容のハッシュによる楽観ロックに変えれば、`rev` をファイルに書かずに済む。要望単位で人が排他するので優先度は低い（今後）
3. **git を使わないメンバー。** 閲覧だけなら、静的な HTML に書き出して共有する（`pcube export`、今後）

## AI エージェントへの指示（`p3 init --agents` で AGENTS.md / CLAUDE.md に追記する内容）

手順の詳しい版は同梱のスキル（`skills/p3/SKILL.md`。`.claude/skills/p3/SKILL.md` に置く）で、役割と終わり方は両方でそろえる
（`src/cli/project.ts` の `AGENTS_SNIPPET`。`test/agents.test.ts` が確かめる）。

```markdown
## タスク管理（infodb p3）

- 作業の単位は要望。タスクは `p3` CLI（入っていなければ `pnpx @infodb/p3`）で操作し、`--json` で結果を読むこと（データのフォルダを直接編集しない）。
  詳しい手順は `.claude/skills/p3/SKILL.md`
- 変更するときは環境変数 `PCUBE_ACTOR=ai:<エージェント名>` を付ける
- 操作する要望は `--req <要望ID>` で指定する（要望の作業ツリーの中なら省ける）。まず `p3 whoami` で確かめる
- 新しい作業を頼まれたら `p3 request new "<タイトル>" --body "..."` で要望を登録し、ID を伝えて終える。
  Preflight（`preflight`）とタスク化（`accept`）は人が行う（AI は実行しない。結果を `p3 drafts` で読むのと、頼まれたメモの保存 `--note-only` はよい）
- 着手する前に `p3 show T003 --brief --json` で本文・依存とその状態（`dependencies`）・置き換えの注意（`warnings`）を読む
- 着手する前に、`--brief --json` の `work`（作業先のリポジトリとブランチ）を見て、そのリポジトリでブランチに入る（作業先なしなら移動しない）
- 着手するときは `p3 move T003 doing`、終えたら `p3 move T003 done --output <PR の URL など>`。複数のリポジトリにまたがるときは最後のタスクに `--repo-output <参照先>=<PR の URL>` で全部の PR を残す
- 要望のタスクを全部終えたら `p3 request set <要望ID> status=resolved`（対応済）にする。完了済（done）・見送り（rejected）とタスクの済み（check）は人が決める
- 置き換えられたタスク（`p3 ls` の `※置換`、`--json` の `superseded`）からは始めない。`move` が `warnings` を返したら止めて人に確かめる
- 作業中に新しく必要になった作業は `p3 new "<タイトル>" --body "..."` でタスクにする（人への質問はタスクにしない）
- 関係と影響範囲を調べるときは `--brief` を付けずに `p3 show T003 --json` で確認し、`p3 link T004 depends_on T003` で張る
```
