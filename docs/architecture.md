# 構成の方針: ローカルで完結させる

> この文書は **設計と規則**（なぜそうするか・どこで守っているか）を書く。コマンド・画面の操作・設定の項目など **使い方** は
> [導入ガイド](installation.md) と [使い方ガイド](how-to-use.md) に書き、ここでは繰り返さない（文書の分担は [開発ガイド](development.md#文書を直すとき)）。確認作業の記録（どの幅・どのブラウザで確かめたか）は書かず、PR と
> タスクの成果物に残す。

p3 は **ファイルが唯一の正（source of truth）で、すべてローカルで完結する** ことを前提にする。
サーバ（S3 / API Gateway / Cognito など）にデータを置く案も検討したが、採らない。以下はその判断と、
残っている課題の整理。

## 作業の単位は要望

Preflight で扱う要望が、プロジェクトで行う作業の粒度になる。そこで **要望ごとにフォルダを作り**、
そこから生まれたタスクや評価の記録はすべてその下に置く。要望 = フォルダ。ブランチ（作業ツリー）は作業先のリポジトリごとに1つ。

```
<データのフォルダ>/requests/<作成日-乱数>/request.md
                              tasks/T001.md ...
                              preflight/<run>/...
```

- **要望の ID は作成日 + 乱数5文字**（例: `261009-k7m3x`）。時刻順に並び、人が読み書きでき、
  複数人が別々に作っても実用上衝突しない。タイトルは後から変わるので含めない（ULID は人が扱うには長い）
- **一覧の並び**は日時だけで決めず、同じ日時のときの第2キー（ID）を必ず持つ（[使い方ガイド](how-to-use.md#データの持ち方) の「一覧の並び」）。
  乱数を含む ID の順は作った順ではないので、「作った順」が要るところは日時で比べる。
- **タスクは要望をまたいで移動しない** ので、要望の中の素直な連番（T001, T002, ...）で採番できる。
  `tasks/.archive/` にある ID も使用済みとして扱い、再利用しない（アーカイブしたタスクへの関係が新しいタスクを指さないように）。
  守れるのはアーカイブのファイルが残っている範囲まで。消したアーカイブの ID や、既に再利用された ID は直さない。
  同じ要望を複数人が同時に触ることは少なく、触る場合の排他は人が行う
- タスクの関係（依存・置き換え）は同じ要望の中だけ。要望をまたぐまとまりは、要望の親子（[大きい要望の分割](#大きい要望の分割親と子の要望)）で表す
- タスクボード（V 字: 未着手 → 作業中 → 完了。済みにすると消え、対応済みの一覧へ）は要望の中で見る。進捗は要望ごとの状況を横断して見る
- 日程は要望の単位で持つ（期限）。リリースは複数の要望をまとめることがあるので、マイルストーンで束ねる
- タスクは予定の日付・見積り・進捗%を持たない。AI が実施する作業の量や期間は人の感覚では見積もれず、
  AI に自己申告させても正確にはならないため。代わりに、ステータスを変えた日時（作業中にした＝着手を指示した目安、
  完了にした）を p3 が記録する
- タスクは AI か人が実施する。人から見て要るのは「まだ動いていない / AI が処理中 / 処理が終わった」だけなので、
  状態は 未着手 / 作業中 / 完了 で固定する（保留・取りやめは持たない）。終わったもの（PR・MR・ドキュメント）のレビューは成果物の側で行い、タスクとしては完了にする
- 担当者（メンバー）は持たない。誰が変えたか（`ai:claude` / `human:<git の user.name>`）だけを記録する
- AI が作業中に見つけた追加の作業は、AI がそのままタスクとして足す。人への質問（Human in the Loop）は
  タスクにせず、Claude Code などのチャットで行う

## 大きい要望の分割（親と子の要望）

> 要望 261022-8s1k5 の設計。ここに書いた契約を T002〜T006 で実装する（実装が済むまで、ここに書いたコマンド・キー・API は
> まだ無い。使い方は実装したときに [使い方ガイド](how-to-use.md) に書く）。

大きい要望を1回の Preflight でタスクにすると、フロントエンド・バックエンド・基盤のように別々に評価・レビュー・リリースしたい
作業が1つのブランチと1つのタスクボードにまとまってしまう。そこで要望は **子の要望** を持てるようにし、子ごとに Preflight・
タスク・ブランチを持たせる。タスクの関係（`depends_on`・`supersedes`）は増やさず、同じ要望の中のままにする
（261013-4j9wr で減らした要望をまたぐ関係を戻さない）。親子は要望の間の構造で、タスクの実行の順は表さない。

### 分割の基準

数は目安で、決めるのは作業の境界。Preflight（エンジン）が分割するか・しないかとその理由を評価に書き、人が採否を決める。

- **想定タスク数が 6 以上** なら、分割するか・しないかの説明を必ず評価に書く（`shared/` の定数 `SPLIT_HINT_TASKS = 6`。
  設定の項目や画面は足さない。運用で合わなければ定数を変える）。数を出すためだけに大きいタスク案を書かせない（概算でよい）
- **6 未満でも分割の候補**: 独立したインフラ（基盤・Lambda・IaC など）、権限や運用の担当が違う、リリースの境界が違う
  （別のマイルストーン・別の公開手順）、別のリポジトリで別にレビューしたい
- **6 以上でも分けない**: 同じ契約（API の型とその呼び出し側、保存の形とその読み書き）を一緒に直さないと途中が壊れる、
  1つの PR でしかレビューできない
- 小さいプロジェクトのフロントエンドとバックエンドは機械的に分けない（一気通貫で直す方が速く、壊れにくい）
- 分割は人が採用したときだけ。採用した子は作るだけで、子の Preflight は人が子ごとに始める（自動で再帰的に実行しない）

| 例 | 判断 |
| --- | --- |
| 想定 5 件・画面と API を一緒に直す | 分けない（説明は任意） |
| 想定 6 件・画面 / API / 通知の Lambda | 分ける: 画面と API の子、通知の基盤の子（境界は Lambda の入出力） |
| 想定 6 件・保存の形を変えて、全部の読み書きを直す | 分けない（同じ契約。理由を評価に書く） |
| 想定 3 件・小さいアプリのフォームと API | 分けない（一気通貫） |
| 想定 3 件・うち 1 件が別の運用担当の IaC | 分ける候補: IaC の子を作る（数より運用の境界） |

### データの形

子は親のフォルダの下ではなく、ほかの要望と同じ `requests/<作成日-乱数>/` に置き、`request.md` の frontmatter に親を1つだけ書く。
子の一覧は保存せず、親を指す要望を引いて作る（両側に書くと食い違うため）。

```yaml
---
id: 261023-q2w8e
title: 通知の Lambda を作る
status: draft
parent: 261022-8s1k5            # 親の要望 ID（1つだけ。無ければ親なし）
splitFrom: PF-20261023-010203-ab12/C2   # 分割で作ったときだけ: 採用元の run と子案のキー
milestone: 0.5.0                # 作成のときだけ親から写す（後は別々に変えてよい）
tags: [feature]
---
```

- 親子は多段にしてよい（孫まで・それ以上も）。自分自身・自分の子孫・無い要望・アーカイブした要望・形の違う ID は親にできない。
  別のプロジェクトの要望は ID の形で指せない（プロジェクト名を含む参照は受け付けない）
- `parent` の無い今のファイルはそのまま読め、書き換えない。保存のキーの順は `status` の後
- 既存のタスク・履歴・添付・Preflight の run は親から子へ動かさない。タスクの ID も振り直さない
- 子の `due`・`milestone`・`tags` は作るときだけ親から写し、後で親を変えても子は変えない（逆も）。`areas`・`workstreams` は写さない
  （子のブランチは子のタスク化で、子の ID から `branchPattern` どおりに割り当てる）。添付は写さず、子の本文に出典（親の ID）を書く
- 直接編集で循環・無い親（孤児）・アーカイブした親・読めない親になったら、読み込みでは止めずに **関係の問題**
  （`hierarchyIssues`。`code` は `parent_missing`・`parent_archived`・`parent_cycle`・`parent_invalid`・`parent_unreadable`）として
  一覧・詳細・進捗に出す。祖先を辿るときは訪れた ID を覚え、循環でも止まる。問題のある要望とその祖先は完了の判定で通さない
- 親の付け替え・外す・子の作成は、プロジェクトの中の関係の操作の排他（`requests/.hierarchy.lock`。リリースノートの保存と同じ
  プロセス間のロック）の中で、ディスクから読み直して循環を確かめ、`rev` で書く。2人が同時に逆向きに付け替えても循環にならない。
  ロックを使わない直接編集までは防げない（読み込みの関係の問題で見つける）

### 操作の契約（CLI・API）

規則は `core/` の1か所（`requestOps.ts` から呼ぶ親子の規則）に置き、CLI と API はそれを呼ぶだけ。

| 操作 | CLI | API |
| --- | --- | --- |
| 子を作る | `request new "<題>" --parent <ID>`（`--due`・`--milestone`・`--tag` を省くと親から写す） | `POST /api/requests` に `parent` |
| 付け替え・外す | `request set <ID> parent=<ID>` / `parent=`（`--rev` で楽観ロック） | `PATCH /api/requests/:rid` に `parent`（外すのは `null`） |
| 子の一覧 | `request ls --parent <ID>`（直下の子） | `GET /api/requests?parent=<ID>` |
| 親子を読む | `request show <ID> --brief --json` | `GET /api/requests/:rid` |

`show --brief --json` と要望の詳細には、今の項目に次を足す:

```json
{
  "parent": "261022-8s1k5",
  "ancestors": [{ "id": "261022-8s1k5", "title": "大きい要望をサブ要望に分割する", "status": "active" }],
  "children": [
    { "id": "261023-q2w8e", "title": "通知の Lambda を作る", "status": "active", "tasks": { "total": 3, "done": 1 } }
  ],
  "hierarchyIssues": []
}
```

`ancestors` は根から順、`children` は直下だけ（作成日時の古い順 → ID）。

失敗の返し方（CLI は終了コード、API は HTTP の状態と `code`）:

| 場合 | CLI | API | 次にすること |
| --- | --- | --- | --- |
| 親が無い・自分・子孫・アーカイブ済み・形が違う | 1 | 409 `hierarchy_invalid`（`reason`: `not_found`・`self`・`cycle`・`archived`・`invalid_id`） | 親を選び直す |
| rev が違う | 3 | 409 `rev_conflict` | 読み直してやり直す |
| ほかの操作が関係のロックを持っている | 3 | 409 `hierarchy_busy` | そのままやり直してよい（何も書いていない） |
| 子のある要望のアーカイブ | 1 | 409 `has_children`（子の ID） | 子の親を外すか、子を先に片付ける |
| 親のある要望のアーカイブ | 1 | 409 `has_parent` | `request set <ID> parent=` で外してからアーカイブ |

アーカイブで未完了の子を暗黙に外さない（外すのは人の明示の操作だけ）。

### Preflight の分割の案

1つの run は **タスク案（`drafts/D*.md`）か子の案（`children/C*.md`）のどちらか** を出す。両方があれば読み込みで run の問題にし、
どちらも採用させない。今までの run（`children/` が無い）はタスク案の run として読む。

評価（`assessment.json`）に分割の判断を足す:

```json
{
  "split": {
    "decision": "split",
    "estimatedTasks": 9,
    "reasons": ["通知の Lambda は別の運用担当で、リリースも別", "画面と API は同じ型を直すので1つにまとめた"]
  }
}
```

`decision` は `split` / `keep`。想定 6 件以上か、境界の候補があるときは必ず書く（`keep` でも理由を残す）。

子の案（`children/C2.md`）:

```markdown
---
key: C2
title: 通知の Lambda を作る
estimatedTasks: 3
requires: ["C1"]        # 前提にする他の子の案（タスクの関係ではない。子の本文に書く）
overlaps: ["T002"]      # 親の既存タスクと重なりうるもの（レビューで見せる）
include: true
---

## 目的
## 範囲
## 範囲外
## 完了条件
## 分割の理由
## 他の子との前提と契約
## 出典
```

キー・題・目的・完了条件が無い、キーが重なる、`requires` が無い案を指す、`overlaps` が親に無いタスクを指すものは読み込みで問題にする。

- **採用**（CLI は `accept`。子の案の run なら子を作る。`--only C1,C2` / `--skip C3` は今までと同じ。API は今の materialize の
  確認と実行を、子の案の run では子を作る操作として返す）: 選んだ子の案ごとに `draft` の子の要望を作る。子の本文には、親の目的
  （採用のときの親の題と本文）と、案の範囲・完了条件・前提を書いて固定する。子のタスク化・Preflight は始めない。親は開始前
  （`reviewed`）なら進行中にし、親のタスク・履歴は変えない
- **古い評価**: 採用の直前に親をディスクから読み直し、評価対象（題・本文）が違う、採用する案の版が確認のときと違う、
  run を始めたときの親の子の集合（`run.json` の `input.children`: ID と題・本文の hash）が今と違う（別の run から分割を採用した・
  子を足した・外した）なら、何も書かずに `stale_input` で断る（`inputMatch` に `children` を足す）。子の Preflight でも、始めるときに
  親の目的を `input.parent` に固定し、子のタスク化の直前に親の題・本文が変わっていれば同じく断る
- **やり直せること**: 親ごとの採用は関係のロックの中で行う。書く前に子の ID を予約して `run.json` の `adoption`
  （`{ reserved: { C1: "<ID>" }, created: [...], done }`）に残し、子は `splitFrom` を付けて作る。途中で落ちても、もう一度同じ採用を
  頼めば予約した ID を使い、`splitFrom` が一致する子は作り直さずに続ける。予約した ID の子が外で編集されていた（`splitFrom` が違う・
  rev が進んだ）ら上書きせず、その案を競合として返す
- **結果**: `{ created: [{ key, id }], failed: [{ key, error }], pending: [key] }`。全部を取り消すために作った子を消さない
- **既存のタスクのある親**: 作業中のタスクがあっても、残りの作業を子に分けてよい。既存のタスクは親に残り、重なりは `overlaps` で
  レビューに出す。既存のタスクを置き換えたいときは、親の中で今までどおり再評価し `supersedes` で置き換える（子は親のタスクを置き換えない）

### 状態と完了の判定

親は自分のタスクと子の両方を持てる。判定は `core/requestStatus.ts` の1か所で、CLI・API・画面・リリースノートの一括完了が同じ理由を返す。

| 判定 | 規則 |
| --- | --- |
| 対応済（`resolved`）にできる | 自分のタスクが全部完了で読めないものが無い、見送り以外の子が全部 対応済か完了済（さらにその子の配下も同じ条件を満たし、外で編集された子の未完了も見つける）、配下に関係の問題が無い、自分のタスクか見送り以外の子が1件以上ある |
| 完了済（`done`）にする（人） | 対応済と同じ条件を満たすときだけ（配下に未完了があれば断る） |
| 見送りの子 | 判定の対象外。理由に「対象外: <ID>（見送り）」と出す。子が全部見送りで自分のタスクも無ければ空の要望として断る |
| 自動の変更 | 対応済・完了済には自動でしない |
| 戻す | 配下に未完了ができた（子を足した・子のタスクを足した・完了から戻した・子を進行中に戻した）ら、対応済の祖先を全部進行中に戻す。完了済の祖先は変えずに警告（`ancestor_done`）を返し、人に再開（`status=active`）を促す。途中の祖先で失敗したら、戻したものと失敗したものと直し方（`request set <ID> status=active`）を返す |

単独の要望（親も子も無い）は今までどおり（タスクが1件以上で全部完了）。

| 例 | 結果 |
| --- | --- |
| 自分のタスク無し・子 2 件が対応済 | 親を対応済にできる |
| 自分のタスク 2 件完了・子 1 件が進行中 | できない（子が未完了） |
| 子 A 対応済・子 B 見送り | できる（B は対象外と出す） |
| 子が全部見送り・自分のタスク無し | できない（空の要望） |
| 子が対応済だが、外の編集で子のタスクが作業中 | できない（配下の未完了） |
| 親が対応済のときに子のタスクを足した | 子と親が進行中に戻る |
| 親が完了済のときに子を進行中に戻した | 親は完了済のまま、警告で再開を促す |

### 進捗とリリースノート

- **進捗**: 要望ごとに自分の値（自分のタスクの数）と配下の集計（自分と子孫のタスクの合計、子の数と状態）を分けて返す。全体の合計は
  各タスクを1回だけ数える（自分の値の合計）。親の最終更新は配下の更新も見る。関係の問題は警告にし、完了と見せない
- **リリースノート**: 材料に入るのは各要望の自分の変更の記録だけで、1件は1回だけ収録する（親に子の記録を写さない）。子だけの親は
  「構造の要望」として収録の判定に入る（自分のタスクが無くても警告にしない。材料は空）。子が別のマイルストーンなら、子の記録は子の
  マイルストーンにだけ入り、親の完了の条件からは外さない（親の一括完了は、その子が終わるまでできない）
- `materialHash` と一括完了の `basedOn` には、完了を左右する配下の状態・タスク・関係を入れる（マイルストーンの外の子が変わっても
  古い `basedOn` を断る）。一括完了は子から親の順に判定・更新し、済み・ノートは変えない

### 画面

- **分割の案のレビュー**（要望の概要・Preflight）: タスク案と子の案を見分け、分割の理由・想定の数・各子の目的・範囲・完了条件・前提・
  既存のタスクとの重なりを出す。子の案の題・本文・採否を直せ、未保存や競合の間と、選んだ案が0件・実行中は採用しない。採用の確認で
  「親は残す・子だけ作る・子の Preflight はまだ」と示し、途中で失敗したら作った子へのリンクと残りの再開を出す
- **親子の移動と進捗**: 詳細の見出しに祖先へのリンク、概要に子の一覧（状態・自分のタスクの数）。進捗は親を開いて子を見る。絞り込みで
  条件に合う子の祖先は文脈として出すが、件数には数えない。完了・アーカイブを断られたら、対象の子と次の操作を出す

## プロジェクトの置き場所と個人設定

管理したいシステムは、本体・ドキュメント・基盤のように **複数のリポジトリに分かれている** ことが多い。
プロジェクトのデータは **データのフォルダ** に置き、操作するプロジェクトはその場所ではなく個人設定の登録で決める。
`p3 init` の既定は本体のリポジトリのルート（git のメインの作業ツリー）の `.p3/` で、ふつうのプロジェクトはそれでよい。
公開できない要望を含むときや、横断するリポジトリのどれとも別に管理したいときは、`--dir` でリポジトリの外
（例: `~/p3-data/myapp`、チームで同期するフォルダ）に置く。どちらでも同じに動く（既定は `init` の入口だけが持つ）。

| 何を | どこに | 共有 |
| --- | --- | --- |
| プロジェクトのデータ（要望・タスク・Preflight の記録、`project.yaml`） | データのフォルダ | する（方法は下の「共有」） |
| 個人設定（参加しているプロジェクトとフォルダの場所、手元のリポジトリの場所、画面の設定、マシンごとの設定（Codex の認証の選び方・パスの対応・serve の待ち受けなど）） | `~/.config/infodb-p3/config.yaml` | しない |
| ChatGPT の接続（トークン） | `~/.config/infodb-p3/chatgpt.json`（所有者だけが読める） | しない |
| コード・ドキュメント | 各リポジトリ | 今までどおり |

### 個人設定とプロジェクトの決め方

- 手元のリポジトリの場所はマシンごとに違うので、プロジェクトのデータではなく個人設定に持たせる
- **操作するプロジェクトは環境変数では決めない**（同じ人が複数のプロジェクトを行き来するため）。
  `--project <名前>` → 今いる場所（登録したリポジトリ・作業ツリー・データのフォルダの中）→ 登録が1つならそれ、の順で決め、
  決まらなければ登録済みの一覧と選び方を出す（`src/core/store/locate.ts`）
- プロジェクトを開く共通の入口（`core/context.ts` の `openProject`。CLI も `serve` の `startServer` もここを通る）で、
  データのフォルダと `project.yaml` があるかを確かめる（`locate.ts` の `checkDataDir`）。無ければ空のプロジェクトとして続けず
  `DataDirError`（終了コード 1）。何も作らない。無い（ENOENT）と読めない（権限・入出力）は分けて伝える。`init`（作成）・`join`（参加）と
  `project` は開かないので妨げない。起動した後の切断は、画面の「再読み込み」の `ReloadError`（状態は変えない）が受け持つ
- 登録が1つだけで決まった（`via: only`）ときは、今いる場所と関係なく当たるので読むだけにする。CLI の入口（`cli/main.ts`）で、
  プロジェクトを開く前に、読むだけの操作（`cli/readOnly.ts` の `readsOnly`。載っていない操作は変える操作として扱う）以外を止める。
  案内の文は `locate.ts` の `onlyRegistrationNotice`（明示の方法と移る先を示す）
- 使う人はフォルダや実行パスを意識しない前提で、セットアップは2段階まで・エラーは次にすることを示す、を守る
- 個人設定に登録していないリポジトリの中の `.p3/` も、今いる場所から上へ辿って読める（`via: legacy`。デモ・テスト・登録前の clone）。
  登録していれば今いる場所（`cwd`）で決まる
- 個人設定の書き換えは、ロック（`config.yaml.lock`）の中で最新のファイルを読み、対象の項目（プロジェクト1つの登録・
  `ui.theme`）だけを変えて書く（`updateUserConfig`）。init・project add / rm・テーマの保存が同じ経路を通るので、
  CLI と serve が同時に書いても消し合わない。壊れた YAML・読めないファイルは書かずにエラーにする（無いのとは区別する）。
  ChatGPT の接続（`chatgpt.json`）は別のファイル・別のロックのまま
- 1人1つのサーバで画面からプロジェクトを切り替える形（決定済み）は、次の段階で入れる

### 要望・タスクのデータ

- タグ（要望の `tags`）は外部 ID・分類のための自由な文字列。仕様（用途・対象外・入力の決まり・絞り込み・URL）は
  [使い方ガイド](how-to-use.md#タグ期限マイルストーン) の「タグ・期限・マイルストーン」にまとめた。保存の形（文字列の配列）は変えない。
  - 入力（`components/TagInput.tsx`、`shared/tags.ts`）: 値ごとに足す・外す。要望の管理情報では足す・外すたびに編集を始めた
    ときの rev で保存し（保存中は次の操作を待たせる）、下書き（`web/lib/draft.ts`）で持つので取り直しても入力中の値は残る。
    入力欄のまだ足していない文字は、新しい要望では作成のときに足す
  - 進捗の絞り込み（`components/TagFilter.tsx`、`web/lib/requestFilter.ts`）: ヘッダーにはボタンだけを置き、開いた中
    （画面に固定。ボタンの下で画面の幅に収める）に検索・選択中（高さを決めてスクロール）・候補（同じ。一度に 200 件まで）を
    出す。URL は `tags`（ルーターが JSON の配列で書く）。以前の `tag` は読むだけで、選び直すと外す
- タスクの成果物（`outputs: string[]`）は URL・文章・パスを1項目ずつ混ぜてよい。画面は `components/Outputs.tsx` で、
  項目全体が絶対の http(s) URL（`web/lib/outputs.ts` の `outputHref`。前後の空白は判定でだけ除く）ならリンク、ほかは文字。
  保存の形を変えないので、既存のデータの移し替えはしない
- 全件の読み直し（`Workspace.reloadAll`、`POST /api/reload`）: project.yaml・要望・全タスクをディスクから読み、読み終えて
  から同期でまとめて入れ替える（`MarkdownCollection.prepareLoad` → `commit`。読んでいる途中の空や半分の状態は見せず、
  要望だけ新しくタスクは古い、ということもない）。読み込みの間に作成・更新・アーカイブ・1件の読み直し（監視）があった ID は、
  読んだ結果ではなくその時点の状態を残す（タスク化や画面からの保存を、先に読んだ古い内容で戻さない）。タスクのコレクションは
  作り直さない（処理中の操作が持っている参照に書いた結果も残る）。同時には走らせず、読み込み中の呼び出しは終わってから
  もう1回にまとめる。project.yaml とデータのフォルダが読めなければ ReloadError（503）で何も変えない。終えたら変更通知
  `changed`/`reload` を出す。Preflight の履歴・メモ・リリースノートは問い合わせのたびに
  ディスクを読むので扱わない。応答は読み直しを終えた後（画面はその後に取り直す）。ほかの serve・CLI が同時に書いている
  最中のファイルは、読んだ時点の内容になる（次の読み直しで追いつく）

### リリースノートのデータ

マイルストーンごとに1件、`<data>/release-notes/<マイルストーンID>.md` に置く（`core/releaseNotes/`）。要望のフォルダの外に
置くのは、複数の要望をまとめるものだから。

- **材料**（`releaseNotes/material.ts`）: マイルストーンに属する要望（アーカイブしたものは除く）を全部返し、収録するかを決める。
  収録するのは、要望が対応済か完了済で、タスクが1件以上あり、全部が完了で、読めないタスクが無いもの（完了済でもタスクの
  実態を確かめる）。見送りは理由だけ、ほかの状態は未完了として警告する。要約の材料は、収録する要望の **変更の記録のある
  完了したタスク** だけで、記録の無いものは警告し、要望やタスクの本文・タイトルで補わない。読めない要望は所属が分からないので
  全体の警告に残す。並びは要望が作成日時の古い順 → ID、タスクが ID（ID は数字の部分を数として比べる。`8nda1` が `88d8b` より先、`T2` が `T10` より先。`material.ts` の `byId`）。並びは `hash` にも入るので、変えると材料が変わったことになる。抽出のたびにディスクから読み直した別の `Workspace` を使い、
  その時点を固定する。`hash` は所属・状態・タイトル・収録の可否と材料（記録まで）から作り、生成や保存のあとの変更を見つける
- **ファイル**: frontmatter に `milestone`・`title`・作成と更新の日時と変更者・`materialHash`・`sources`（保存したときの材料:
  要望とタスクの ID・タイトル・状態・変更の記録）、本文に公開する Markdown を書く。出力（`p3 release-notes export` など）は
  本文だけで、frontmatter と出典は出さない
- **保存**（`releaseNotes/store.ts`）: 明示的に保存したときだけ書く。要望・タスクが後で変わっても、保存した本文と出典は
  変えない（詳細で `materialChanged` として知らせる）。新規は排他作成で、既にあれば（読めないファイルでも）上書きしない。
  更新は読んだときの **版**（ファイル全体の sha256）が必須で、プロセス間のロック（`release-notes/.<ID>.lock`）の中で
  ディスクの今のファイルと照らし、違えば競合で何も書かない。rev のような番号ではなく中身で照らすので、番号を増やさない
  直接編集も見つかる。マイルストーンの ID は project.yaml と同じ形（英数字と `. _ -`、`.` と `..` は不可）で、保存先の外を
  指すものは断る。キャッシュを持たず問い合わせのたびに読むので、再読み込みは要らない。監視は `changed`/`release-note` を出す
- **要望の一括完了**（`releaseNotes/completeRequests.ts`）: 判定は材料と同じ収録の条件で、見送りを除く全要望が収録でき、
  マイルストーンが project.yaml にあり、所属の分からない読めない要望が無いときだけできる。変えるのは対応済 → 完了済だけ
  （完了済・見送り・アーカイブ・タスク・ノート・マイルストーンは書かない。記録・ノート・済みは条件にしない）。詳細の
  `completion` に判定（対象・既に完了済・見送り・できない理由・`basedOn`）を出し、CLI・API・画面はそれを見せて `basedOn` を添えて
  頼むだけ（画面で条件を作り直さない）。実行はディスクから読み直した材料で判定し直し、hash が違う・できないなら何も書かない。
  複数のファイルをまとめて書く仕組みは無いので1件ずつ書き、直前にタスクを読み直して確かめ、要望は判定したときの rev で書く
  （`updateRequest`。変更の通知もそこから）。途中で止まったら戻さず（外の変更を上書きしない）、完了済にしたもの・失敗・未実行を
  返す。rev を増やさない直接編集や、確かめた直後の別のプロセスの書き込みまでは防げない（保存層の限界）
- **マイルストーンとの関係**: ノート（読めないファイルも含む）のあるマイルストーンは消せない（`requestOps.ts` の
  `checkMilestoneRemoval`。CLI の `milestone rm` と画面のマイルストーンのタブの保存で同じ）。保存は要望・マイルストーンの状態を変えない
- **直接編集の限界と直し方**: ロックを使わない外部のエディタとの完全な排他は保証しない（保存の直前に照らすので、
  照らした後・書く前の一瞬の書き込みは失われうる）。frontmatter を壊す・`milestone` をファイル名と違えると「読めない」と
  示し、空のノートとして扱わない（直すまで新規保存もしない）。直すときは frontmatter を戻すか、本文を退避してファイルを
  消してから保存し直す。project.yaml を直接編集してマイルストーンが消えても、ノートは一覧・閲覧・出力でき、孤立を警告する
  （マイルストーンを足し直すか、不要ならファイルを消す）

### 参照先と作業先

- Preflight の参照先（`shared/repos.ts`・`core/repoRefs.ts`）: 共有の定義は project.yaml の `repos`（名前をキーにした対応。
  名前・役割・readFirst・writable・主なフォルダ map。入口 entry がそのフォルダで最初に読むファイル）、このマシンのパスは個人設定の `projects.<p>.repos`。
  `Workspace.refs()` が始めるたびに合わせ、`ok / unregistered / missing / notdir` を決める。`p3 init` が本体を参照先として
  登録する。`p3 repo` は project.yaml の `repos` の1件だけを書き（`writeRepoEntry`。コメント・知らない項目は残す）、
  設定の保存（画面・`p3 config`）は `repos` を書き換えない。コンテナの中の名前（mount）は論理名から英数字と `. _ -` だけで作り、
  重複は番号で分ける。参照の書き方 `<名前>:<パス>`（`parseRepoPath`）は areas・evidence で共通。名前なしは先頭の参照先。
  - マウント（`withMounts`）: dockerCommand の `/workspace` の bind を tmpfs に替え、参照先を `/workspace/<mount>` に
    `readonly` で、データを `/data` に置く。Codex の cwd は `/workspace` のまま。変更のパスは参照先の対応で戻す
  - 調べた範囲（`run.scope`）は P3 が始めるときに決めて残す（パスは入れない）。根拠（`assessment.evidence`）は Codex が書き、
    P3 が `parseEvidence` で確かめる（verified は読めた参照先の中の、ある相対パスを指すときだけ）
- タスクの作業先とリポジトリごとのブランチ（`shared/workTarget.ts`・`core/workTargets.ts`）: タスクとタスク案の `repo`
  （名前 / null = 作業先なし。書かずに足すと、作業先にできる参照先が1つならそれ）、要望の `workstreams`（名前 → branch。
  作業ツリーの置き場所は記録しない）、タスクの `repoOutputs`。作業先は writable の参照先だけで、API・CLI・タスク化の
  前に `checkRepoTarget` で確かめ、変える前に断る。割当は `planWorkstreams`（既存は残す・git でないフォルダはブランチなし・
  同じ git の実体を指す2つの名前は断る。git の実体は `--git-common-dir` で見る）で決め、タスク化では計画を run の
  materialization に残してやり直しでも同じにする。今の要望（`cli/project.ts` の `currentRequest`）は、今いる参照先
  （`locateHere`）の割当のブランチ → ブランチ名の要望 ID の順で、パスの中の要望 ID だけでは決めない（detached HEAD では決めない）。
  git のブランチ・作業ツリーは作らない
- 参照先の登録・変更・削除は `core/repoAdmin.ts` に集め、CLI（`p3 repo`）と設定画面（`/api/repos`・`components/ReposPanel.tsx`）が
  同じものを使う。このマシンのパスは `localOnly` でローカルの画面にだけ返し、変えられるのもローカルの画面（Origin）からだけ。
  パスつきで足すときは、共有の定義を書く前にフォルダかを確かめる
  - 設定画面はほかの画面と同じく画面の横幅いっぱいに使う。入力欄のラベルは短くし、補足は `Field` の `hint` で入力欄の下に出すので、
    ラベルの折り返しで横に並んだ入力欄の高さがずれない
  - 主なフォルダの行は、広い画面ではフォルダ・役割・入口を3等分し（見出しの行を上に置く）、狭い画面では縦に並べる。構成の説明
    （`mapFile`）の欄は無い（以前の `mapFile` とプロジェクトの `docs` が残った project.yaml で参照先を保存すると、どちらも消える）
  - 設定画面はタブで「個人」（ChatGPT の接続・テーマ）・「プロジェクトの基本」（project.yaml）・「参照先」（共有の定義と
    このマシンのパス）に分ける。選んだタブは `?tab=personal|project|repos`（既定は個人）に持ち、読み直しても同じタブを開く。
    ほかの画面から設定へのリンク（説明が無いときの案内）は `tab=project`。プロジェクトの基本のタブの保存は基本の項目（名前・説明・
    Preflight の観点・ブランチ名）だけを送り、マイルストーン・参照先を送らない（ほかの画面での変更を巻き戻さない）。マイルストーンは
    設定に無く、リリースノートの画面のタブ（`/release-notes?tab=milestones`。`components/releaseNotes/MilestoneEditor.tsx`）で
    `milestones` だけを送って保存する。マイルストーンを作る案内（要望の概要・ノートが無いとき）はそのタブへ。タブの部品は
    `components/Tabs.tsx` を設定とリリースノートで共通に使う。選んでいないタブは消さずに
    `hidden` で隠すので、タブを移っても書きかけの入力は残り、保存していない変更があるタブには印（●・読み上げは「未保存」）を
    付ける（参照先は各参照先の編集・このマシンのパス・「足す」の欄の入力を `onDirtyChange` で集める）。保存のバーは
    プロジェクトの基本のタブだけに出す。タブは矢印キー・Home・End で移る

### マシンごとの設定と Codex の起動

- マシンごとの設定は、項目ごとに CLI の明示 → 環境変数（`P3_*`）→ 個人設定 → 既定値 で決める（`src/core/machineSettings.ts`）。
  CLI と serve・Codex エンジンが同じ解決を使い、`process.env` を個人設定の値で書き換えない。`.env` はどこからも読まない
  （P3 は pnpx などで入れるので、パッケージの場所は利用者が触らない）。項目と環境変数の対照は [導入ガイド](installation.md#設定の決まり) の「設定の決まり」
- マシンごとの設定の書き換え（`p3 user-config set`。`src/core/machineSettingsEdit.ts`）: `キー=値` で書き、`キー=` で消し、
  パスの対応は `codex.pathMap+=A=B` / `codex.pathMap-=A` で1件ずつ足し・外す（全部の置き換えは受けない。書き間違いで全部を
  失わないように）。`updateUserConfig` の中で変更を当ててから、環境変数を見ずに `resolveMachineSettings` で確かめ、読めなければ
  何も書かない（テーマを含めて一括）。表示（`describeSettings`）は項目ごとの効いている値と出どころ（環境変数 / 個人設定 / 既定）。
  空の環境変数は既定に戻すので出どころも既定。プロジェクトの登録（projects）は表示しない（`p3 project ls`）
- パスの対応のエラー（`bind source path does not exist`）には、直し方（`pathMapHowTo`）として設定するコマンド・例・ホストの
  パスの調べ方を添える。共有の記録に残るので、このマシンのパスは例のパスで示す。対応が当たっていたなら行き先の誤りとして案内する
- 旧来の認証の auth.json は、P3 のイメージの中の Codex（`CODEX_HOME=/codex`）で `codex login --device-auth` すれば、ボリュームの
  一番上にでき、そのまま `authVolume`（`volume-subpath=auth.json`）で使える（サインインそのものは人が行う）。`authFile` は Docker のホストのパスで
  渡すので `codex.pathMap` は効かない
- serve の Codex と Preflight の設定は `SettingsSource`（`machineSettingsSource`）から、Preflight を始めるたび・エンジンの状態を
  見るたびに読み直す（`loadUserSettings` で厳密に読み、形が違えば空にせずエラー）。Codex エンジンは `snapshot()` で始めるときの
  設定に決めたエンジンを作り、その run の間はそれを使う。既定のエンジンも始めるたびに決める。読めなければ、その run を
  設定のエラーで失敗にする（`PreflightService` の failing エンジン。Docker は起こさない）。エンジンの状態のため込み（1分）は、
  ChatGPT の接続のファイルと設定の中身が変われば確かめ直す。待ち受けとプロジェクトは起動のときに決めたまま。CLI の1回の
  操作は起動のときに一度だけ読む。テストは MachineSettings をそのまま渡して決まった設定にする
- app-server の診断（`preflight/launcher.mjs`・`launch.ts`・`diagnose.ts`）: codex-workspace は子の stderr を捨てるので、
  docker run の前に中継を挟む（`node launcher.mjs <一時フォルダ> -- docker run ...`）。中継は stdin / stdout をそのまま通し、
  stderr（先頭 8KB と末尾 56KB。間は省略を明示）と `{code, signal}` か `{spawnError}` を一時フォルダ（所有者だけが読める）に
  書く。初期化で失敗したら（stopIfRunning で応答しない中継を止めてから）、途中で「app-server が終わりました」となったら、
  その内容で診断する。中止（signal.aborted）とほかの失敗には付けない。うまくいったときは stdin を閉じて中継から子へ伝わる。
  最後に中継が残っていれば止め、一時フォルダを消す。伏せるのは今までどおり Codex エンジンの log とエラーの包みで行う
  （チャンクをまたいだ値も、まとめてから伏せる）
- Preflight の記録（run.json のログ・エラー）は共有するので、このマシンのパス・Docker のホストのパス・個人設定のファイルの
  場所を入れない（`diagnose.ts` の `describeMapping` は名前とコンテナの中のパスだけ、`hidePaths` で Docker の出力の中のパスを
  参照先の名前に置き換える。個人設定のエラーは `hideConfigPath` で「個人設定（config.yaml）」にする。想定外の変更は
  `<参照先>:<パス>`）。画面のエンジンの状態（共有しない）には個人設定の場所を出してよい

### プロジェクトを跨ぐ serve（`p3 serve --all-projects`）

通常の serve は1つのプロジェクト（今いる場所・`--project`・`--dir` で決めたもの）だけを開く。`--all-projects` を付けると、個人設定に
登録したプロジェクトを跨いで扱う（`--project` / `--dir` とは一緒に使えず、serve 以外には付けられない。通常の serve の決め方は変えない）。
閲覧専用にはせず、通常の serve と同じ操作（作成・編集・添付・設定・Preflight・タスク化・リリースノート）をプロジェクトごとにできる。

- 対象は個人設定に登録した名前だけ（`core/projectRegistry.ts` の `ProjectRegistry`）。任意のパスは開かず、名前は登録名の形
  （`PROJECT_NAME`）で確かめる。API はプロジェクトごとに `/api/projects/<名前>/...` で、中身は通常の serve の `/api/...` と同じ
  （`server/api/projectsRoutes.ts` が名前を外して `apiRoutes(ctx)` へ渡す。接続元の情報はそのままなので、ローカルだけの操作の
  確かめ方も同じ）。プロジェクトを書かないデータの API は 404（`project_required`）、無い API は画面ではなく 404 の JSON
- 一覧は `GET /api/projects` のたびに個人設定を読み直す（`inspectUserProjects`）。読めない・壊れた個人設定は登録0件と分けて
  `configError` に出し、それまでの一覧と開いている文脈を残す。形の違う登録は `invalid` に理由を付け、ほかは使える。登録0件でも起動する
- 文脈（Workspace・PreflightService・ReleaseGenerator・変更通知）はプロジェクトごとに、使うときに開く。同時に開こうとしたら1回に
  まとめ、失敗は覚えずに次でやり直す（フォルダを戻せば使える）。1つが開けなくてもほかは使える。`process.chdir` や「今の
  プロジェクト」は持たないので、タブごとに別のプロジェクトを同時に操作できる
- 同じデータのフォルダ（実体のパス）を複数の名前で登録していたら、どれも開かない（Preflight・生成を二重に動かさないため。
  どれを残すかは人が決める）
- 登録世代（`generation`）: 一覧を読み直したときに、登録が無くなっていた・データのフォルダが変わっていた・重なりを解いたら変わる
  （読み直すまでの間に外して同じフォルダで付け直したものは同じ登録として扱う。書き込む先は同じなので取り違えは起きない）。
  変える操作には `x-p3-project-generation` が要り、違えば 409（`changed`）で何も書かない（古い画面の保存を新しい登録先へ流さない。
  自動で送り直さない）。参照先のパスだけの変更は世代を変えずに今の文脈へ反映し、次の Preflight から使う
- 登録から外れた文脈には新しい要求を渡さない。始めていた Preflight・生成は元のプロジェクトで終わるまで待ってから閉じる（取り消さない）
- ChatGPT の接続（サインインの待ち受け）は全プロジェクトで1つ（`openProject` の `chatgpt`）。接続・テーマの変更は開いている
  全プロジェクトの画面へ知らせる。プロジェクトを選ばない入口（`/api/chatgpt`・`/api/user-theme`・`/api/events`）もある。
  エンジンの状態はプロジェクトごと
- 画面（`web/Boot.tsx`・`web/lib/scope.ts`）: ページを開いたときに `/api/mode` と URL（`/projects/<名前>`）からこの画面の対象を
  一度だけ決め（`fixScope`）、API の基点（`/api/projects/<名前>`）・登録世代のヘッダー・ルーターの basepath に使う。ページの間は
  変えない。切り替えはページごと移る（`components/ProjectSwitcher.tsx`）ので、前のプロジェクトの取得・SSE・タイマー・キャッシュ・
  遅い応答は新しいプロジェクトに混ざらない（文脈を差し替える仕組みを持たない）。保存していない入力は各画面が `useUnsaved` で、
  送っている保存は `api.ts` が数え（`lib/unsaved.ts`）、切り替えの前に確かめる・待つ。API が登録の変化（`changed` など）で断ったら
  知らせを出し、選び直しを案内する。対象が決まらない・開けないときは一覧（`components/ProjectChooser.tsx`）で理由を出す。入口（`/`）は登録が1つで開けるなら
  一覧を飛ばす（`location.replace`。`/?list` なら飛ばさない）。一覧は戻ったとき（`pageshow` の保存から）・タブに戻ったときに読み直す
- 止める（SIGTERM・SIGINT。通常の serve も同じ）: 新しい接続を断り、開いている接続（SSE）を閉じ、実行中の Preflight・生成を取り消して
  （記録は「中止しました」）終わるまで待つ（10 秒まで）。監視を外す。2回目の信号ではすぐ終わる

### 画面

- 画面のテーマ（`ui.theme`）の反映: index.html の先頭（CSS より前）で `/api/user-theme.js` を同期で読み、
  html 要素に `data-theme`・class `dark`・`color-scheme` を付ける（Tailwind の `dark:` は class `dark` を見る
  `@custom-variant`。OS のメディアクエリでは切り替えない）。応答はテーマだけを埋め込み `no-store`。その後は画面の
  `web/lib/theme.ts` が持ち、`system` の間だけ `prefers-color-scheme` の変化を購読する。保存先は個人設定だけで、
  localStorage は使わない。ほかのプロセスでの変更は読み直しで反映する
- 設定画面のテーマの選択は、選んだらすぐ `PUT /api/user-theme` で保存し、保存できてから画面に反映する
  （`web/lib/themeSave.ts`。保存中に続けて選んだら、終わってから最後の選択だけを保存する。失敗したら保存済みの表示に戻す）。
- 進捗のスケジュールの狭い画面: 左の一覧の幅を枠の幅から決める（`web/lib/timeline.ts` の `leftWidth`。640px 未満で
  枠の 36%・112〜380px、640px 以上は 380px）。スケジュールの見える幅（`scheduleSpan`）・描く期間の右端・見える範囲の判定・
  今日への移動・ズームの中央の日付は、すべてこの幅から計算する（測る前は幅 0 で、見える幅は負にならない）。行の高さと
  縦の仮想スクロールは変えない。
- 画面の取り直し（`web/lib/appData.tsx`）: `reload` は API から取り直すだけ（変更通知・保存の後）、`refresh` はサーバに
  全件を読み直させてから取り直す（`web/lib/refresh.ts`。ヘッダーの「再読み込み」と、タブが見えた・ウィンドウにフォーカスが
  戻ったとき。離れてから戻ったときだけで、両方続けて起きても1回）。実行中に頼まれたら終わってからもう1回だけ。取得は
  `web/lib/latest.ts` で最後に始めたものの応答だけを使う（読み直しより前に始めた取得の遅い応答で上書きしない）。自分の
  再読み込み中に届いた `reload` の通知では取り直さない。どの通知でも全件の読み直しは呼ばない
- 入力の保持（`web/lib/draft.ts`）: 要望のタイトル・タグとタスク詳細は下書き（値・編集を始めたときの値と rev・外の最新）で
  持つ。編集していなければ追従し、編集中は上書きせず知らせる。保存は編集を始めたときの rev。古い rev の応答は無視する。
  済み・関係の操作のように入力欄以外を自分で変えたときは、入力欄の項目が変わっていなければ自分の上げた rev に合わせる。
  要望の取り直し（`web/lib/requestLoad.ts`）: 404 は表示中なら gone（前の内容と入力を残して保存を止める）、初めからなら
  「見つかりません」。ほかの失敗は前の内容のまま知らせる。要望を移ると作り直す（`RequestDataProvider` の key）
- 要望の画面の見出し（`routes/requests/$requestId.tsx` の RequestFrame）は要望 ID とコピー・タイトル・タスクの完了数だけ。
  ステータス・ブランチの印は外した（ステータスは概要・Preflight の管理情報で選ぶ。ブランチはデータに残り、CLI で見る）。見出しと
  タブは本文のスクロールの外に置き、要望 ID はタイトルの上に、どのタブでも1組だけ出す（`components/RequestIdCopy.tsx`。概要の
  管理情報（RequestMeta）には出さない。本文を下へ送ってもコピーできる）。コピーは
  `web/lib/copy.ts` の `copyText`（ボタンは枠つきでコピーのアイコンと文字。成功したらアイコンをチェックにする）: Clipboard API が無ければ unavailable、拒まれたら denied（例外は外へ出さない）、書き込みが
  終わってから copied。知らせは role="status" で、どの ID の結果かを持ち、別の要望の結果は出さない。ボタンは mousedown で
  フォーカスを奪わないので、入力中のタイトルを保存させない。ID は select-all で、コピーできないときは手で選ぶ
- 進捗の画面の絞り込み（`web/lib/requestFilter.ts`）: 未完了（既定）は下書き・Preflight・レビュー済・進行中で、対応済は
  含めない（リリース前のものは対応済のまましばらく残るため）。確認待ちは対応済だけ、完了・見送りは完了済・見送りだけ、
  すべては7つとも。左の一覧とスケジュールは同じ行（`filterRequests`）から描く。CLI の `progress` は今までどおり既定でも
  対応済を出す（完了済・見送りだけを隠す）。`CLOSED_STATUSES`（人が閉じたもの）に対応済は入れない
- 要望の画面（概要・Preflight）の幅: 内容はブラウザの幅をそのまま使う（上限なし。以前は 1024px）。左右の余白は
  画面の幅で縮める（16 / 24 / 32px）。並びは変えない（評価 → メモ → タスク案）。文脈とログは 1024px 以上で
  左右、妥当性と実現可能性・リスクと確認事項は 640px 以上で左右。長い語（パス・参照・ログ・本文）は折り返し、ページ全体を
  横にスクロールさせない（タスク案の段の列とログだけが中でスクロールする）。
- タスク案の題（`web/lib/draftTitle.ts`、カードの `TitleField`）: 案には rev が無いので、題の値で比べる下書きにする（基準の題・
  入力・外の最新・保存中の値）。下書きは 要望 / run / 案のキー の組で持ち、別の run の入力や遅い応答を混ぜない（run を替えたら
  持ち越さない）。保存は編集を始めたときの題を `expectedTitle` に添え、`PreflightService.updateDraft` が案のファイルを読み直して
  今の題と比べ、違えば `DraftConflictError`（409 `rev_conflict`、`current` に今の案）で書かない。期待値はファイルに書かない。
  画面から題を変えるときは必ず渡し、CLI・内部の呼び出しは渡さない（確かめない）。読み直してから書くまでの間に外のプロセスが
  書くことまでは防げない。保存の応答は、表示中の run が同じときだけ、その案だけを入れる（そのあいだに取り直したほかの案・項目を
  巻き戻さない）。未保存・保存中・競合中の題があればタスク化を止める
- タスク案の詳細（`components/request/DraftDetail.tsx`）: カードの「内容を見る」で開くネイティブの dialog（最大 960px、
  狭い画面では画面の中に収め、見出しと「閉じる」を残して本文だけ縦にスクロール）。読むだけで、採否・題・作業先は一覧で直す。
  開いている案は run と案のキーの組で持ち（`lib/markdown.ts` の `selectedDraft`）、run が切り替わる・案が無くなると閉じ、
  外で更新されたら最新を見せる。閉じたら開いたボタンへフォーカスを戻す
- 画面で Markdown を読むのは、今はタスク案の本文だけ（`components/Markdown.tsx`。react-markdown + remark-gfm）。安全のため、
  生の HTML は要素にせず文字で見せ（HTML を差し込むプラグインは使わない）、リンクは絶対の http(s) URL だけ（成果物と同じ判定。
  別のタブ・`noopener noreferrer`。ほかは文字）、画像は取りに行かず代替テキストを出す。チェックリストは読むだけ。
  要望の本文・タスクの詳細などほかの欄には広げていない

## 役割

```
            ┌──────────── 各メンバーのマシン ────────────┐
  人 ──┐    │                                            │
       ├─▶  p3 CLI ─────┐                                │
  AI ──┘                ├─▶ <データのフォルダ>/*.md ◀── 読み直し ── p3 serve ──▶ ブラウザ（ビューア）
  人 ─────▶ ブラウザ ───┘        ▲                         │
                                 │ ファイル契約             │
            Codex（自分のアカウント, コンテナ内で /workspace = repo, /data = データのフォルダ）
            └────────────────────────────────────────────┘
                         │ 共有は同期だけ（git）
                         ▼
                    GitHub などのリモート
```

| 部品 | 位置付け |
| --- | --- |
| データのフォルダ（Markdown / YAML / JSON） | 正。タスク・要望・Preflight の記録。人も AI も直接読める |
| CLI（`p3`） | 主な操作口。人も AI も使う。ファイルを直接読み書きするので **認証が要らない** |
| `p3 serve` + ブラウザ | ローカルのビューア兼エディタ。ファイルを読んで画面に流す（外での変更は「再読み込み」で取り込む。監視は補助）。データは持たない |
| Codex（`@infodb/codex-workspace`） | 操作する人のマシンで、その人のアカウントで動く。リポジトリとデータのフォルダだけを見せたコンテナの中 |

CLI は serve を経由せずファイルに直接書く（serve が常に動いている前提にしない。プロジェクトを跨いでも書き先の制御が増えない）。
serve の中で起きたこと（画面からの保存、Preflight の進み具合と終了）は SSE で画面に届く。外での変更は、画面の「再読み込み」と
タブ・ウィンドウに戻ったときの読み直し（POST /api/reload）で取り込む。ファイル監視は補助で、届かないことがある
（NFS や、Node の再帰的な監視が置き換えて保存したファイルの2回目以降の変更を通知しないことがある）。

画面は定期的には問い合わせない、の例外を1つだけ置く: 要望の「概要・Preflight」を開いている間だけ、その要望の最新の Preflight を
軽く確かめる（`GET /api/requests/:rid/preflight-status`、`PreflightService.pulse`）。CLI など外で始めた run とその進み・終わりは
serve の SSE に乗らず、監視も届かないことがあるため。返すのは要望の `lastPreflight` と、指定した run の `run.json` の状態・日時と
更新を見分ける値（`version`）だけで、要望と run.json をディスクから読む（読み込んだ内容・索引・ファイル・rev は変えず、古い
キャッシュに戻すこともない。`MarkdownCollection.peek`）。run の状態は ready / pending（フォルダはあるが run.json がまだ無い）/
missing / broken、要望は ok / gone（削除・アーカイブ）/ broken。全件の読み直し・全 run・案・ログの走査はしない。ID は形を確かめ、
パスは受け取らない。

画面の側（`web/lib/preflightWatch.ts`、要望の概要の `RequestPanel`）: 確かめるのは 3 秒ごと（`PULSE_INTERVAL_MS`）で、前の確かめが
終わってから次を予約する。タブが隠れたら止め、見えたらすぐ1回。ページを離れたら止める。SSE の `preflight-status` は速い経路として
残し、届いたら今すぐ1回（確かめ中なら終わってから1回にまとめる）。表示する run は `?run=` で決め、無ければ開いたとき（と `?run=` が
無くなったとき）の最新に留める。新しい run ができても表示は変えず、知らせ（`PreflightNotice`）から人が開く（自分で実行したときは
今までどおりその run を開く）。表示中の run の版・状態が変わったら取り直す。run の取得は最後に頼んだものだけを使い、表示中の
run でない応答は捨てる。要望が消えた・読めないときは要望の枠の扱い（gone・読めない）に任せる

REST API はブラウザのためのローカル API として残すが、AI には CLI を使わせる。
CLI がファイルを直接触る形なら、API ごとに認証を持たせる問題はそもそも起きない。

## 規則の置き場所

同じ規則を入口（CLI・API・画面）ごとに書かない。足すときは次の1か所を直す。

src は5つの層に分け、依存の向きを `test/layers.test.ts` で確かめる:

| 層 | 中身 | 読み込んでよいもの |
| --- | --- | --- |
| `shared` | 型と判定（サーバと画面で共通） | なし（node: も外のパッケージも使わない。画面のビルドに入るので I/O を置かない） |
| `core` | CLI と serve の共通の中核（保存の層・規則・変更の手順・Preflight・設定・ChatGPT の接続） | `shared`（HTTP の hono は使わない） |
| `server` | HTTP の API と配信（`p3 serve`） | `core`・`shared` |
| `cli` | CLI | `core`・`shared`（serve の起動の `server/server.ts` だけ） |
| `web` | 画面 | `shared`（node: は使わない） |

| 何を | どこに |
| --- | --- |
| 要望・タスクの変更の手順（確かめる → 保存 → ブランチの割り当て・進行中に戻す → 変更通知） | `core/requestOps.ts`（CLI の各コマンドと API はここを呼ぶだけ） |
| Preflight（開始・評価対象の固定・タスク化） | `core/preflight/service.ts`（`PreflightService`） |
| 個々の規則（対応済・置き換え・作業先とブランチ・評価対象の比べ方） | `core/requestStatus.ts`・`core/supersede.ts`・`core/workTargets.ts`・`shared/preflightInput.ts` |
| サーバと画面の両方で使う判定・表示名 | `shared/` |
| 画面の API の失敗の扱い（rev の競合・評価対象の変更・無い） | `web/lib/api.ts` の `failureOf` |
| リリースノートの本文の下書き（外の変更・削除・読めないときに入力を残す・編集を始めた版で保存） | `web/lib/releaseNoteDraft.ts` |
| 読み取り（一覧・参照の解き方・進捗） | `core/ops.ts` |
| リリースノート（材料の規則・保存・出力・要約の生成・要望の一括完了） | `core/releaseNotes/`（`material.ts`・`store.ts`・`service.ts`・`generate.ts`・`completeRequests.ts`） |
| タスクの関係（`depends_on`・`supersedes` だけ。同じ要望の中。Preflight のタスク化だけが張る） | `shared/types.ts` の `RELATION_TYPES`・`core/preflight/service.ts` の `materialize` |
| プロジェクトを跨ぐ serve（登録の一覧・登録世代・文脈の開閉） | `core/projectRegistry.ts`（API は `server/api/projectsRoutes.ts`） |
| Preflight を通さずにタスクを作る道の案内（付かないものの言い方・失敗と取消の見分け。取消は `PREFLIGHT_CANCELLED` で残す） | `shared/directTask.ts`（CLI の案内文は `cli/output.ts` の `directTaskHint`） |
| マイルストーンの表示の順（ID のバージョンの降順。CLI・API・画面の一覧と選ぶ欄。project.yaml の順は変えない） | `shared/milestoneOrder.ts` |

CLI は `cli/main.ts`（振り分け・プロジェクトと変更者の決定・終了コード）と、種類ごとのコマンド（`taskCommands.ts`・
`requestCommands.ts`・`preflightCommands.ts`）に分ける。大きい画面は、ルートのファイルを組み立てだけにして部品を
`web/components/<ページ>/` に分ける。

## サーバに置かない理由

1. **Codex の置き場所が決まらない。** サーバ側で Codex を動かすと共有アカウントになる（OpenAI の規約上も避けたい）。
   ユーザーごとにサーバへ認証情報を預けるのは運用が重い。ローカルなら各自のアカウントで動き、何も預けない。
2. **プロジェクトのドキュメントがサーバに寄ってしまう。** Preflight はリポジトリのコードとドキュメントを読んで判断する。
   サーバ側で判断するなら、それらをサーバへ複製し続ける必要がある。ローカルならリポジトリをそのまま見せればよい。
3. **認証・運用のコスト。** Cognito を使っても、CLI・AI・ブラウザそれぞれのトークン管理が残る。

外部に出ていくのは、各自が自分の Codex で OpenAI に送る内容だけになる（これは Codex を使う以上避けられない）。

## Codex の使い方

- Preflight は **実行した人のマシン** で、`codex-workspace` のコンテナの中で動く。コンテナには管理対象リポジトリを
  `/workspace`、データのフォルダを `/data` としてマウントする。データのフォルダはリポジトリの外にあってよい。
  認証情報は各自の ChatGPT の接続か `auth.json`（個人の場所に置き、プロジェクトには置かない）。
- 結果は戻り値ではなく **ファイル**（要望のフォルダの `preflight/<RUN>/assessment.json`, `drafts/*.md`）。
  同期すればチームの全員が同じ評価とタスク案を見られる。誰が実行したかは `run.json` とタスクの `updatedBy` に残る。
- 画面資料（`preflight/<RUN>/ui/`）もファイル契約にする（`src/core/preflight/uiMaterials.ts`）。エンジンは画像と
  `ui/index.json` を書き、P3 が取り込む前に確かめて `run.json` の `ui` に記録する。画像の形式と大きさは拡張子ではなく
  中身から読み、配信のときも同じ確かめ方をもう一度する（取り込んだ後に差し替えられた画像は返さない）。画像は
  要望 / run / 資料 ID で決め、パスを受け取らない。応答には `X-Content-Type-Options: nosniff` と
  `Content-Security-Policy: default-src 'none'` を付け、HTML / SVG は配信しない。資料が不正でも評価は残し、
  必要な画面イメージが足りないときだけ go を clarify にする（新しい承認の状態は作らない）
- 同じ要望を複数人が Preflight しても、run ごとに別ディレクトリ（ID に乱数を含む）なので衝突しない。
  「直近の run」は開始時刻の新しい順で決めるが、時計は戻ることがある（WSL2 の時刻の補正など）ので、前回を引き継いだ run
  （`previous`）は引き継いだ相手より必ず新しいとする（`preflightStore.ts` の `newestFirst`）
- Codex との会話は続けない（1 run = 新しいコンテナ・新しいスレッドで1往復）。確認事項への回答や方針の変更は
  **メモ**（要望のフォルダの `notes/N-....md`。1件1ファイル、書いた人と日時つき）として書き足し、次の run に
  前回の結果と一緒に渡す。経緯がファイルに残り、別の人が続きから Preflight できる。
  - 前回: 直近の run が完了していて評価を読めるときだけ引き継ぐ。失敗・欠損なら古い成功 run に戻らず「前回なし」
  - メモ: 前回を引き継ぐなら、引き継ぎの経路（`run.json` の `previous` を辿った run）で渡し済みのものを除く。
    失敗した run に渡しただけのメモは渡し済みにしない。前回を引き継がないなら全部渡す
  - 選んだものは開始の時点で `carryover.md` に固定し、`run.json` に `previous` と `notes`（メモの ID）を残す。
    実行中に書き足したメモは次の run に回る
  - 再評価のプロンプトには `carryover.md` の内容を資料として入れる。メモは尊重するが、書き込み先などの制約は変えさせない
  - 操作は `p3 preflight <要望> --note "..."`（書き足してから実行）、`--note-only`（書くだけ）、`p3 notes <要望>`（一覧）。
    実行を始められなくてもメモは残るので、再試行でメモを書き直さない
  - 画面のメモ欄は評価の下に1つだけ置く（評価を読んでから書くため）。評価が無い間（実行中・失敗）も同じ並びの位置にあり、
    入力中の文は保つ（別の要望に移ると消える）。評価の確認事項の「メモ欄で答える」から入力欄に移れる
  - まだ一度も実行していなければメモ欄は出さない。CLI などで先に保存したメモがあればそれだけを見せ、最初の Preflight に渡す
    （API と CLI は最初の実行の前のメモも受け付ける）
  - 入力中のメモがある間は、上の通常の実行を止める（入力が渡らないまま実行されないように）。「保存して再実行」で保存してから
    実行するか、入力を消す。保存済みのメモだけなら通常の実行でも渡る
  - 実行中も「メモだけ保存」はでき、実行中の評価ではなく次の Preflight に渡る。保存してから始められなかったときは、保存済みと
    伝え、書き直さずに再実行できる。過去の run を表示していても、引き継ぎ元は直近の run なので、何を引き継ぐかを入力欄の上に出す。
    run ごとに、引き継いだ前回の run（クリックで移る）と渡したメモを表示する
- 過去の経緯は p3 が選ばず、Codex が調べる（`codexEngine.ts` の `historySection`）。以前は TF-IDF と areas（パス）の
  重なりで選んだ10件を渡していたが、リファクタリングでパスが変わる・ファイルを分割すると外れ、読み替えの表では分割や
  移動の繰り返しを扱えない。git は行ごとに履歴を追え（`blame -C -M`）、マージのコミットのブランチ名に要望 ID があるので、
  コード → コミット → 要望 → `/data` の記録と辿れる。p3 を入れる前の経緯も分かる。全件はプロンプトに入れず、Codex が
  rg と git で必要な分だけ読む（件数が増えて探しにくくなったら、ベクトル検索を検討する）
- 参照先ごとに git の履歴が使えるか（`repoRefs.ts` の `gitHistory`）を始めるときに決め、`scope` の `history` と指示に出す。
  コンテナには参照先のフォルダだけを読むだけでマウントするので、`.git` がフォルダの中にあるときだけ使える（作業ツリーの
  `.git` ファイルが指す本体・サブフォルダの上の `.git` はマウントの外）。浅い clone は途中まで
- Codex に書かせてよいのは run ディレクトリ（`/data/requests/<要望ID>/preflight/<RUN>/`）だけ。それ以外の変更は検出して警告する（git 差分による検出は今後）。
  Codex のスレッドは `danger-full-access`・`approvalPolicy: never` で動く（コンテナを囲いにするため）が、これは何かを
  追加で許す保証ではない。コマンドの実行は禁止していない。参照先は読むだけのマウントで書けない。データのフォルダ（`/data`）は
  書けるマウントなので、「run の中だけ」は指示と事後の警告で守っている（書き込みを run に閉じ込める囲いは今は無い）。
  画面イメージの描画は、この Codex のコンテナではなく別のコンテナで行う
- ファイル契約なので、Mock エンジンでも人手で書いても同じ取り込み処理になる。案の `supersedes` のうち同じ要望に無いタスクはタスク化のときに捨てる
- テストは偽の app-server で、マウントの引数・指示文・記録・根拠の扱いを確かめる。本物の Codex が実際にどこまで読むか、
  読むだけのマウントへの書き込みが拒まれることは、偽の app-server では確かめられない

### 評価対象の固定と、評価のあとの要望の変更

要望のタイトルと本文は、Preflight の前後・実行中・完了済を含め、いつでも書き換えられる（`p3 request set --body` / `title=`、
API の PATCH。`rev` で楽観ロック）。書き換えても状態・既存のタスク・過去の run は変えない。そのかわり、古い評価からはタスク化しない
（`src/core/preflight/input.ts`）。

- **固定**: Preflight を始めるとき、要望をディスクから読み直し（監視していない外部の編集も取り込む）、タイトルと本文を
  `run.json` の `input` に固定する。人が読む `request.md` とエンジンに渡す要望も同じ内容にする。実行中に要望が書き換えられても、
  この run は固定した内容で評価し、終わったときに要望の本文を戻さない（ステータスだけを部分更新する）
- **比べるもの**: 保存されたタイトルと本文そのもの。`rev` や `lastPreflight` では比べない（Preflight 自身の状態の更新や、
  タグ・期限・ステータスだけの変更では古くならない）。本文を元に戻せば一致に戻る。正規化は「改行を LF にそろえ、前後の空白・空行を
  除く」だけ（要望のファイルは保存するときに本文の前後を除くので、保存の形の違いで変わったことにしない）。行末の空白（Markdown の改行）
  や途中の空行は違いとして扱う
- **run ごとの判定**（`inputMatch`）: `same`（同じ）/ `changed`（`changed` に `title`・`body`）/ `unknown`（評価対象が読めない）。
  `input` の無い以前の run は `request.md`（`# <要望ID> <タイトル>` の後に空行と本文）から読み、無い・形が違うときは unknown にする
  （一致とはみなさない）。以前の run のファイルは書き換えない。API の run（一覧・詳細・要望の詳細の `runs`）と `p3 drafts` に添える
- **タスク化**: `previewMaterialize` は `inputMatch` を返し、`materialize` は直前に要望をディスクから読み直して same でなければ
  `StaleInputError` で断る（API は 409 `code: "stale_input"`、rev の競合は 409 `code: "rev_conflict"`。CLI の `accept --json` は
  `{ error, code, inputMatch }` を出して終了コード 1）。断るときはタスク・関係・アーカイブ・ブランチの割り当て・`materialization` を書かない。
  途中で失敗したタスク化のやり直しも同じ規則で、変わっていれば断る（評価した時点の内容に戻せば、作ったタスクを作り直さずに続ける。
  自動で巻き戻しはしない）。タスク化済みの run・過去の run・評価・案・画面資料はそのまま読める
- **再評価**: いつもどおり前回の結果とメモを引き継ぎ、前回の評価のあとでタイトル・本文が変わっていれば、`carryover.md` に
  「前回の評価のあとで変わった要望」として前回の時点の内容を書く。評価の基準は今の要望で、前回の評価・案・メモとの食い違いは
  確認事項に入れさせる。白紙の再評価や履歴の消去は作らない（前回を引き継がせたくなければ、メモでそう書く）
- **限界**: 比べるのは「始めたとき」と「タスク化の直前」。タスク化の途中に別のプロセスが本文を書き換えることまでは排他しない
  （同じ要望を同時に触るときの調整は、これまでどおり人が行う）
- **戻し方**: 古い評価でタスク化したいときは、要望を評価した時点の内容（`request.md`）に戻す。今の内容でよければ再評価する
- **画面**（`web/components/request/BodyEditor.tsx`、`web/lib/requestDrafts.ts`、`web/lib/requestEdit.ts`）: 本文は明示の保存だけ。
  タイトル・タグ・本文の下書きは要望の画面（`useRequestDrafts`）が持ち、取り直しは項目ごとに比べる（`syncFieldDraft`: その項目が変わって
  いなければ baseRev を進め、変わっていれば競合として知らせる）。未保存のタイトル・本文がある間は Preflight の実行とタスク化を止める。
  タスク化の 409 は `code` で分ける（`stale_input` はサーバの理由をそのまま、`rev_conflict` は置き換えの候補の読み直し）

### 置き換えられたタスク

再評価でタスク化すると、新しい案が同じ要望の古いタスクを置き換える（`supersedes`）ことがある。
タスクの状態は 未着手 / 作業中 / 完了 の3つのままにし、置き換えは関係として扱う（`src/core/supersede.ts`）。

- **タスク化で知らせる候補**: **採用した** 案の `supersedes` のうち、同じ要望にある未完了（未着手・作業中）のタスク。
  不採用の案だけにあるもの・完了したタスク・無いタスクは候補にしない。
- **アーカイブは選んだものだけ**（既定はどれも残す）。確定の時点で候補を読み直し、候補でない・rev が変わった
  ものがあれば何も変えずに失敗する（もう一度確認してもらう）。作業中のタスクをアーカイブしても、作業そのものは止まらない。
- **順序と再試行**: 新しいタスクと関係を保存してからアーカイブする（古いタスクを先に外さない）。途中経過は
  `run.json` の `materialization`（作った案とタスク、選んだもの、アーカイブ済み）に残し、途中で失敗したら同じ
  タスク化をもう一度行えば、作った案は作り直さず、アーカイブも重ねずに続きから終える。
- **印**: 保存済みのタスクの `relations` にある `supersedes` から導く。案に書かれた置き換えは、その案から作ったタスクの
  関係として残る（今あるタスクを指すものだけ）。
- **進捗**: 残したタスクは進捗に数える（完了しないと要望の全タスクは終わらない）。アーカイブしたものだけが外れる。
- タスク化の結果は `{ tasks, archived, kept }`（作ったタスク、アーカイブしたもの、置き換えられるが残したもの）。
  以前は作ったタスクの配列だった（CLI の `accept --json` と API の POST materialize。利用者は `.tasks` を読む）。
- **着手の警告**: 置き換えられたタスクが作業中に変わったとき（CLI の `move` / `set`、API の PATCH、画面のボードと詳細）、
  操作は行ったうえで `warnings`（code・対象・置き換えた側・文言）を返す。作業中のままの再指定では出さない。
- API: `GET .../preflight/:run/materialize` で確認（何も変えない）、`POST` に `{archive: [{id, rev}]}`。
  要望の詳細と タスクの GET は印 `superseded` を返す。

### リリースノートの要約（生成の境界）

マイルストーンのリリースノートの機能の要約は、Preflight と同じ Codex の接続（個人設定・認証・イメージの確かめ・起動の診断）で頼む
（`CodexWorkspaceEngine.ask`、`core/releaseNotes/generate.ts`）。Preflight の評価・タスク化は行わない。

- **渡すもの**: 始めるときに固定した材料（[リリースノートのデータ](#リリースノートのデータ)）のうち、マイルストーンのタイトルと、
  収録する要望とタスクの ID・タイトル・変更の記録だけを依頼文に入れる。要望やタスクの本文・成果物・参照先・データのフォルダは
  渡さず、コンテナには何もマウントしない（`/workspace` は空の tmpfs で、終われば消える。パスの対応も要らない）
- **受け取るもの**: 最後の応答の JSON（項目ごとの文と出典）。P3 が形・件数（100）・長さ（1項目 600 文字・合計 2 万文字）・
  出典が依頼文に入れた要望とタスクにあるかを確かめ、だめなら `invalid_output` で失敗にする。ローカルのパス・秘密らしい文字列・
  メールアドレスは `suspicious_content` の警告にする。本文の案（Markdown）は確かめた項目から P3 が組み立て、出典は本文に入れない
- **頼まないとき**: 材料（記録のある完了したタスク）が無ければ Codex を呼ばずに断る（本文は手で書いて保存できる）。
  入力（記録とタイトルの合計）が 12 万文字を超えたら、黙って切らずに断る
- **生成と保存は別**: 生成は保存したノートを変えない。結果（実行 ID・生成中・完了・失敗・取消、失敗の種類 `unavailable`・
  `usage_limit`・`timeout`（既定 15 分）・`invalid_output`・`error`）はこのプロセスのメモリにだけ置き、変更通知
  `release-generation` を出す。同じマイルストーンでは1つずつ。終わったら材料を読み直し、変わっていれば `material_changed`
  （古い材料からの生成）を付ける。作り直しも上書きもしない
- ChatGPT のトークンは Preflight と同じく、ログとエラーから伏せる

### llmcs の部品の依存（codex-workspace・chatgpt-plan）

llmcs の部品を npm の公開版で使う:

- `@infodb/codex-workspace`（codex-workspace-ts）: Codex をコンテナで動かす
- `@infodb/chatgpt-plan`（chatgpt-plan-ts）: Sign in with ChatGPT のサインイン・トークンの保存と更新・解除（[docs/chatgpt-sign-in.md](chatgpt-sign-in.md)）

package.json では公開版の版の範囲（`^0.2.0` など）で指定し、手元のフォルダへのリンク（`link:` / `file:`）は置かない。
新しくチェックアウトしても隣に llmcs が無くて構わない。新しく公開された版は、pnpm の `minimumReleaseAge`（公開から1日）を
過ぎてから入れる。待たずに入れる例外（`pnpm-workspace.yaml` の `minimumReleaseAgeExclude`）は、自分たちが公開した
`@infodb/*` の部品を、版を固定して書くときだけ置く（`@infodb/chatgpt-plan@0.1.1` の形。`test/package.test.ts` が確かめる）。
公開から1日を過ぎたら外してよい。

`@infodb/codex-workspace` について P3 が使う公開 API と約束:

- `dockerCommand(workspace, { accessTokenEnv | authVolume, authFile })` が作る `docker run` は、作業場所を
  `/workspace` にマウントする。P3 はそのマウントの直後に、データのフォルダを `/data` にマウントする引数を足す
- `WorkspaceSession.open(command, { model, effort, env, clientInfo, onEvent })` で app-server を起動する。ChatGPT の
  トークンは `env`（`ACCESS_TOKEN_ENV`）で渡し、`docker run` の引数や記録には値を出さない
- `UsageLimitError` は使用量の上限（ChatGPT プランの `subscription_sharing_usage_limit_exceeded` を含む）
- `ensureImage({ maxAgeMs })` はイメージが無いか `maxAgeMs` より古ければ作り直し、中の Codex の版を返す。作り直すたびに
  `CODEX_REFRESH`（その時刻）が変わるので、Codex を入れる段はキャッシュを使わず、その時点の最新が入る
  - イメージの中身（Dockerfile）は `@infodb/codex-workspace` が同梱し、Python 版と同じ名前のイメージを共有する。
    中身が変わる版が出たら P3 も上げる（古い版のままだと、1日ごとの作り直しで共有のイメージを古い中身に戻す）
  - いつもの Preflight: 既定の1日より古ければ作り直す（個人設定 `codex.ensureImage: false` か `P3_CODEX_ENSURE_IMAGE=0` で止める）
  - 強制更新（`p3 codex update`）: `maxAgeMs` を -∞ にして、作った日時によらず作り直す。プロジェクト・認証を決める前に動き、
    個人設定の自動更新の停止（`codex.ensureImage: false`）とも関係しない。前に `docker version` でデーモンを確かめ、
    失敗した段（docker が無い / デーモン / 作成 / 版の取得）ごとに次にすることを出す（`src/core/preflight/codexImage.ts`）
  - テストは偽の docker（`test/fixtures/fake-docker.mjs`）で行い、本物の Docker では次で確かめる:
    `XDG_CONFIG_HOME=$(mktemp -d) p3 codex update --json`（未登録・未認証のままでよい）

手元の llmcs の変更を P3 で試すときは、一時的にリンクに替え、試し終えたら公開版に戻す（リンクはコミットしない）:

```bash
pnpm add @infodb/codex-workspace@link:../llmcs/codex-workspace-ts   # 一時的に手元の llmcs を使う
# …試す…
git checkout package.json pnpm-lock.yaml pnpm-workspace.yaml && pnpm install   # 公開版に戻す
```

`npm pack` やコミットの前に、`package.json` と `pnpm-lock.yaml` に `link:` が無いことを確かめる。
llmcs の変更を P3 で使うには、llmcs 側で新しい版を公開し、P3 の版の範囲を上げる（chatgpt-plan も同じ）。

### 画面イメージの描画のイメージ

画面イメージの描画（`src/core/preflight/render.ts`）は、Codex のイメージ（llmcs の Dockerfile）とは別に、P3 が持つ
Dockerfile（`src/core/preflight/render-image/`）で作る。llmcs の Dockerfile は変えない。将来 llmcs のイメージに
Playwright が入っても、それだけでは描画の安全の条件（ネットワークなし・認証情報なし・リポジトリなし・原稿は読むだけ）を
満たさないので、描画は別のコンテナで行う。

- 版: Playwright 1.63.0（Chromium の headless shell）、Node 22（`node:22-bookworm-slim`）、`fonts-noto-cjk`。
  Playwright はイメージの中で npm から入れる（P3 の依存には足さない）。版は公開から1日を過ぎたものに固定する
- イメージの名前は資材（`Dockerfile`・`fonts-ja.conf`・`render.mjs`。`render.ts` の `RENDER_IMAGE_FILES`）の中身の hash
  （`infodb-p3-render:<12桁>`）。どれかが変われば（フォントの設定だけでも）次の描画で作り直す。
  大きさは約 1.4GB（amd64 で確かめた）
- Chromium の sandbox は使わない。コンテナを囲いにする（`--network none`・`--read-only`・`--cap-drop ALL`・
  `no-new-privileges`・root ではない利用者・メモリ / CPU / プロセス数・時間の上限）。読み込みを止めるのは二重目の囲い
- 原稿は描く前に確かめる（`render.ts` の `checkHtml`）: 使えるのは `<style>` の CSS・`data:` の画像とフォント・ページの中の `#id`。
  スクリプト・`on*` 属性・`javascript:`・外のファイルや通信を指す参照（`http(s):`・`file:`・相対パス・`@import`）・
  `iframe` / `object` / `embed` / `link` / `base` / `meta http-equiv` は断る。幅は 320〜2560 px、原稿は 2MB まで、高さ 16384 px を超える
  ところは切る。DevContainer の中からは、出力先のフォルダにも `codex.pathMap` が要る
- 日本語のフォントは Debian の `fonts-noto-cjk`（SIL Open Font License 1.1）。イメージの中にだけ入り、P3 の配布物には含めない
- Playwright の依存（`--with-deps`）で WenQuanYi Zen Hei（中国語の字形）も入り、fontconfig ではそれが総称の既定に先に来る。
  `fonts-ja.conf`（`/etc/fonts/conf.d/99-p3-ja.conf` に置く）で、総称（`sans-serif`・`system-ui`・`serif`・`monospace`）と、
  イメージに無い日本語のフォント名を Noto CJK JP に寄せる（対応は how-to-use.md の「画面資料」）。`binding="strong"` にするのは、
  Chromium（Skia）が、名前で探したフォントの代わりに強く結んだものだけを受け入れるため。明示したほかのフォントと埋め込みのフォントは変えない
- Chromium の既定（フォントの指定なし）は Times New Roman（イメージでは Liberation Serif）で、欧文が明朝系になる。Codex の原稿の多くは
  フォントを指定しないので、`render.mjs` が原稿の先頭（doctype の後。無ければ先頭で、quirks の判定は変わらない）に
  `:where(html){font-family:sans-serif}` を足す。詳細度 0 で最初に置くので、原稿の指定（`html`・`body`・`*`・`:root` を含む）が必ず勝つ
- Chromium は無い字を総称に関係なく探すので、`serif` の欧文（Liberation Serif）に無いかな・漢字は Noto Sans CJK JP になる。
  `Times New Roman` を明朝体に寄せると、`sans-serif` のかな・漢字まで明朝体になったのでやめた

### 添付の確かめ方と置き場所

- 形式は拡張子ではなく中身で確かめる（PNG / JPEG の署名と大きさ、xlsx は ZIP の中央ディレクトリだけを読み、ブックであること・
  マクロが無いこと・中のパスが外を指さないこと・項目 1 万まで・展開して 200MB まで）。保存のときは展開しない
- 原本は内部の名前（`file.png` など）で `attachments/A-.../` に置き、元の名前・説明・出典・追加した人と日時を `meta.json` に残す。
  ダウンロードの名前は元の名前からパスの区切り・制御文字を外したもの
- xlsx の取り出し（`preflight/xlsx.ts`）は Preflight を始めて run に固定した原本から行う。展開後 1 項目 30MB・合計 200MB、
  セル 5 万、画像 20、10 秒で打ち切り、打ち切ったこと・扱っていないもの（図形・グラフ・リンクの画像・EMF など）を記録する。
  外部のブック・URL は取りに行かず、マクロ・OLE は動かさず、XML の DOCTYPE は読まない

## プロジェクトのドキュメントの扱い

- ドキュメントは **リポジトリに置いたまま**（`docs/`, README, コードのコメント）。p3 は複製も同期もしない。
- Codex はコンテナの中から、それらをリポジトリのファイルとして直接読む。
- p3 が作る記録（要望・評価・タスク案・タスク）もリポジトリ内の Markdown なので、それ自体がドキュメントになる。
  「なぜこのタスクがあるのか」は、タスク → 要望 → Preflight の評価を辿れば分かる。コードの経緯は git の履歴（マージのコミットの
  ブランチ名 `req/<要望ID>-...` から要望へ）で辿る。
- Preflight で最初に読ませるドキュメント（設計方針・用語集など）は、「最初に読む」（`readFirst`）参照先の主なフォルダ
  （`repos.<名前>.map`。フォルダでもファイルでもよい）に書く。指示文ではそれを「最初に読むもの」として、以前のプロジェクトの
  `docs` と同じく「評価の前に、必要な範囲で読んでください」と渡し、ほかの参照先の主なフォルダは「どこから読むかの案内」として
  分けて渡す（docs を外したときに、指示が案内だけに弱まっていたのを戻した。入口 `entry` は任意で、あればそこから読ませる）。参照先ごとに書くので、どの参照先のファイルかが曖昧にならない
  （以前のプロジェクトの `docs` は、名前を付けないと先頭の参照先のパスになり分かりにくかったので外した。構成の説明の
  Markdown `mapFile` も入口と重なるので外した。どちらも保存のときに project.yaml から消す）。
  `preflight.instructions` にはプロジェクト固有の評価の観点・制約を書く。どちらも Codex への指示に加わる。

## 共有（同期）の方法

同期の手段は **git**（またはファイル共有）。要望のフォルダ単位で push / pull すれば、その要望の状況を共有できる。
開発者はすでに認証済みで、履歴（誰がいつ状態を変えたか）、PR による Preflight 結果のレビュー、
1タスク1ファイルによる小さな差分がそのまま使える。排他制御は人が行う（同じ要望を同時に触らない）。

### 解決したこと

- **ID の衝突** — 要望は作成日 + 乱数、タスクは要望の中の連番にしたので、別々の人が作った要望どうしは衝突しない
- **状態がブランチごとに分岐する** — データは1つのデータのフォルダに書く（リポジトリの中の `.p3/` なら
  git のメインの作業ツリーのものに書き、要望の作業ツリーの `.p3/` は使わない）。要望の作業ツリーの中で実行しても書き込み先は1か所で、今の要望は今いる参照先のブランチから決まる

### 残っている課題

1. **データのフォルダの共有方法（保留）。** データのフォルダ自体を git リポジトリにして `p3 sync`（pull → commit → push）で
   同期する案があるが、使い勝手を見てから決める
2. **rev による偽の衝突。** frontmatter の `rev` は、同じタスクの別々の項目を変えただけでも git のマージで衝突する。
   ファイル内容のハッシュによる楽観ロックに変えれば、`rev` をファイルに書かずに済む。要望単位で人が排他するので優先度は低い（今後）
3. **git を使わないメンバー。** 閲覧だけなら、静的な HTML に書き出して共有する（`p3 export`、今後）

## AI エージェントへの指示（`p3 init --agents` / `p3 agents` で AGENTS.md / CLAUDE.md に足す節）

手順の詳しい版は同梱のスキル（原本は `skills/p3/SKILL.md` の1つ。選んだ先（`claude` は `.claude/skills/p3/SKILL.md`（Claude Code）、
`codex` は `.agents/skills/p3/SKILL.md`（Codex））に同じものを写す。置き先の一覧は `src/cli/project.ts` の `AGENT_TARGETS`、
選び方は `AGENT_CHOICES`。個人のスキルの場所には置かない）で、役割と終わり方は両方でそろえる
（`src/cli/project.ts` の `agentsSnippet`。節のスキルの参照は、選んだ先と既にある先だけを書く。下は両方のときの `AGENTS_SNIPPET`。
`test/agents.test.ts` が確かめる）。置き先を覚えておく共有の設定は持たない（参加の `join` は置かず、置く・最新にするのは人が明示する
`p3 agents` だけなので、消した先が戻らない）。
既にあるスキル・節は上書きしないので、原本を変えても各プロジェクトに置いたものには届かない。変えたときは、置いたプロジェクトで
`p3 agents <先>` で違いを確かめ、`--force` で選んだ先のスキルと p3 の節だけを同梱の版にする（節の前後の文は残す。節が複数・
見出しになっていなければ変えずに手で整理してもらう）。

```markdown
## タスク管理（infodb p3）

- 作業の単位は要望。タスクは `p3` CLI（入っていなければ `pnpx @infodb/p3`）で操作し、`--json` で結果を読むこと（データのフォルダを直接編集しない）。
  詳しい手順はスキル `.claude/skills/p3/SKILL.md`（Claude Code）・`.agents/skills/p3/SKILL.md`（Codex）。中身は同じ
- 変更するときは環境変数 `P3_ACTOR=ai:<エージェント名>` を付ける
- 操作する要望は `--req <要望ID>` で指定する（要望の作業ツリーの中なら省ける）。まず `p3 whoami --json` で確かめる
- `whoami` の `via`（プロジェクトの決まり方）が `cwd` でなければ（`dir` / `project` / `legacy` / `only`）、それ以上 p3 を操作せず、対象のプロジェクトでよいか人に確かめる（推測した `--project` / `--dir` で避けない。人が指定・確認した後はその対象のまま続ける）
- プロジェクトが無い・未登録のときは `p3 init` / `p3 join` を自分から実行せず、新しく作る（`init`）のか共有されたものに参加する（`join`）のかを人に確かめる
- 新しい作業を頼まれたら `p3 request new "<タイトル>" --body "..."` で要望を登録し、ID を伝えて終える。
  Preflight（`preflight`）とタスク化（`accept`）は人が行う（AI は実行しない。結果を `p3 drafts` で読むのと、頼まれたメモの保存 `--note-only` はよい）
- 着手する前に `p3 show T003 --brief --json` で本文・依存とその状態（`dependencies`）・置き換えの注意（`warnings`）を読む
- 着手する前に、`--brief --json` の `work`（作業先のリポジトリとブランチ）を見て、そのリポジトリでブランチに入る（作業先なしなら移動しない）
- 着手するときは `p3 move T003 doing`。テストを通したら、コミットする前に `p3 move T003 done --output <今ある成果物（変えたファイルや説明）> --record -` で完了にする（変更の記録は必須: 何を変えたか・なぜ・入れた決まり・やめたもの を標準入力から Markdown で。まだ無い URL は書かない）
- 要望のタスクを全部終えたら、コミットする前に `p3 request set <要望ID> status=resolved`（対応済）にする。完了済（done）・見送り（rejected）とタスクの済み（check）は人が決める
- データのフォルダがこの作業ツリーの中で git 管理されているなら、要望のフォルダ（`requests/<要望ID>/`）の変更も実装と同じコミットに入れる（ほかの要望・関係ない変更は入れない。外・無視・worktree のときは入らないので、移動や `git add -f` はしない）。push に失敗したら完了の記録は残し、公開できていないことを伝える
- コミットや PR の URL は後から `p3 move T003 done --output <URL>` で足す（完了・記録はそのまま。データをコミットしているなら追記もコミットして push）。複数のリポジトリにまたがるときは最後のタスクに `--repo-output <参照先>=<PR の URL>` で全部の PR を残す
- 置き換えられたタスク（`p3 ls` の `※置換`、`--json` の `superseded`）からは始めない。`move` が `warnings` を返したら止めて人に確かめる
- 作業中に新しく必要になった作業は `p3 new "<タイトル>" --body "..."` でタスクにする（人への質問はタスクにしない）
```
