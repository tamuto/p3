# 構成の方針: ローカルで完結させる

pcube は **ファイルが唯一の正（source of truth）で、すべてローカルで完結する** ことを前提にする。
サーバ（S3 / API Gateway / Cognito など）にデータを置く案も検討したが、採らない。以下はその判断と、
残っている課題の整理。

## 作業の単位は要望

Preflight で扱う要望が、プロジェクトで行う作業の粒度になる。そこで **要望ごとにフォルダを作り**、
そこから生まれたタスクや評価の記録はすべてその下に置く。要望 = フォルダ = 作業ツリー（ブランチ）。

```
<データのフォルダ>/requests/<作成日-乱数>/request.md
                              tasks/T001.md ...
                              preflight/<run>/...
```

- **要望の ID は作成日 + 乱数5文字**（例: `261009-k7m3x`）。時刻順に並び、人が読み書きでき、
  複数人が別々に作っても実用上衝突しない。タイトルは後から変わるので含めない（ULID は人が扱うには長い）
- **タスクは要望をまたいで移動しない** ので、要望の中の素直な連番（T001, T002, ...）で採番できる。
  同じ要望を複数人が同時に触ることは少なく、触る場合の排他は人が行う
- 要望をまたぐ関係（影響・依存）は `<要望ID>/T003` の絶対参照で書き、インテリジェンス層が要望を横断して辿る
- タスクボード（V 字: 未着手 → 作業中 → 完了。済みにすると消え、対応済みの一覧へ）は要望の中で見る。進捗は要望ごとの状況を横断して見る
- 日程は要望の単位で持つ（期限）。リリースは複数の要望をまとめることがあるので、マイルストーンで束ねる
- タスクは予定の日付・見積り・進捗%を持たない。AI が実施する作業の量や期間は人の感覚では見積もれず、
  AI に自己申告させても正確にはならないため。代わりに、ステータスを変えた日時（作業中にした＝着手を指示した目安、
  完了にした）を pcube が記録する
- タスクは AI か人が実施する。人から見て要るのは「まだ動いていない / AI が処理中 / 処理が終わった」だけなので、
  状態は 未着手 / 作業中 / 完了 で固定する（保留・取りやめは持たない）。終わったもの（PR・MR・ドキュメント）のレビューは成果物の側で行い、タスクとしては完了にする
- 担当者（メンバー）は持たない。誰が変えたか（`ai:claude` / `human:<git の user.name>`）だけを記録する
- AI が作業中に見つけた追加の作業は、AI がそのままタスクとして足す。人への質問（Human in the Loop）は
  タスクにせず、Claude Code などのチャットで行う

## プロジェクトの置き場所と個人設定

管理したいシステムは、本体・ドキュメント・基盤のように **複数のリポジトリに分かれている** ことが多い。
要望・Preflight・タスクはそれらを横断するので、プロジェクトのデータはどのリポジトリにも属さない
**データのフォルダ** に置く（場所は自由。例: `/mnt/assets/pcube`）。

| 何を | どこに | 共有 |
| --- | --- | --- |
| プロジェクトのデータ（要望・タスク・Preflight の記録、`project.yaml`） | データのフォルダ | する（方法は下の「共有」） |
| 個人設定（参加しているプロジェクトとフォルダの場所、手元のリポジトリの場所、画面の設定、いずれ Codex のログイン） | `~/.config/infodb-p3/config.yaml` | しない |
| コード・ドキュメント | 各リポジトリ | 今までどおり |

- 手元のリポジトリの場所はマシンごとに違うので、プロジェクトのデータではなく個人設定に持たせる
- **操作するプロジェクトは環境変数では決めない**（同じ人が複数のプロジェクトを行き来するため）。
  `--project <名前>` → 今いる場所（登録したリポジトリ・作業ツリー・データのフォルダの中）→ 登録が1つならそれ、の順で決め、
  決まらなければ登録済みの一覧と選び方を出す（`src/server/store/locate.ts`）
- 使う人はフォルダや実行パスを意識しない前提で、セットアップは2段階まで・エラーは次にすることを示す、を守る
- リポジトリの中の `.pcube/` も以前の置き方として読める（デモ・テスト）

複数のリポジトリへの対応（`project.yaml` の `repos`、タスクの作業先、リポジトリをまたぐ Preflight）と、
1人1つのサーバで画面からプロジェクトを切り替える形は、次の段階で入れる（TODO）。

## 役割

```
            ┌──────────── 各メンバーのマシン ────────────┐
  人 ──┐    │                                            │
       ├─▶  pcube CLI ──┐                                │
  AI ──┘                ├─▶ <データのフォルダ>/*.md ◀── 監視 ── pcube serve ──▶ ブラウザ（ビューア）
  人 ─────▶ ブラウザ ───┘        ▲                         │
                                 │ ファイル契約             │
            Codex（自分のアカウント, コンテナ内で /workspace = repo）
            └────────────────────────────────────────────┘
                         │ 共有は同期だけ（git）
                         ▼
                    GitHub などのリモート
```

| 部品 | 位置付け |
| --- | --- |
| データのフォルダ（Markdown / YAML / JSON） | 正。タスク・要望・Preflight の記録。人も AI も直接読める |
| CLI（`pcube`） | 主な操作口。人も AI も使う。ファイルを直接読み書きするので **認証が要らない** |
| `pcube serve` + ブラウザ | ローカルのビューア兼エディタ。ファイルを監視して画面に流す。データは持たない |
| Codex（`@llmcs/codex-workspace`） | 操作する人のマシンで、その人のアカウントで動く。リポジトリだけを見せたコンテナの中 |

REST API はブラウザのためのローカル API として残すが、AI には CLI を使わせる。
CLI がファイルを直接触る形なら、API ごとに認証を持たせる問題はそもそも起きない。

## サーバに置かない理由

1. **Codex の置き場所が決まらない。** サーバ側で Codex を動かすと共有アカウントになる（OpenAI の規約上も避けたい）。
   ユーザーごとにサーバへ認証情報を預けるのは運用が重い。ローカルなら各自のアカウントで動き、何も預けない。
2. **プロジェクトのドキュメントがサーバに寄ってしまう。** Preflight はリポジトリのコードとドキュメントを読んで判断する。
   サーバ側で判断するなら、それらをサーバへ複製し続ける必要がある。ローカルならリポジトリをそのまま見せればよい。
3. **認証・運用のコスト。** Cognito を使っても、CLI・AI・ブラウザそれぞれのトークン管理が残る。

外部に出ていくのは、各自が自分の Codex で OpenAI に送る内容だけになる（これは Codex を使う以上避けられない）。

## Codex の使い方

- Preflight は **実行した人のマシン** で、`codex-workspace` のコンテナ（管理対象リポジトリだけを `/workspace` に
  マウント）の中で動く。認証情報は各自の `auth.json`（pcube 本体の `.env` で場所を指定。プロジェクトには置かない）。
- 結果は戻り値ではなく **ファイル**（要望のフォルダの `preflight/<RUN>/assessment.json`, `drafts/*.md`）。
  同期すればチームの全員が同じ評価とタスク案を見られる。誰が実行したかは `run.json` とタスクの `updatedBy` に残る。
- 同じ要望を複数人が Preflight しても、run ごとに別ディレクトリ（ID に乱数を含む）なので衝突しない。
- Codex に書かせてよいのは run ディレクトリだけ。それ以外の変更は検出して警告する（git 差分による検出は TODO）。

## プロジェクトのドキュメントの扱い

- ドキュメントは **リポジトリに置いたまま**（`docs/`, README, コードのコメント）。pcube は複製も同期もしない。
- Codex はコンテナの中から、それらをリポジトリのファイルとして直接読む。
- pcube が作る記録（要望・評価・タスク案・タスク）もリポジトリ内の Markdown なので、それ自体がドキュメントになる。
  「なぜこのタスクがあるのか」は、タスク → 要望 → Preflight の評価と文脈（`context.md`）を辿れば分かる。
- `project.yaml` の `docs` に、Preflight で最初に読ませるドキュメント（設計方針・用語集など）を列挙する。
  `preflight.instructions` にはプロジェクト固有の評価の観点・制約を書く。どちらも Codex への指示に加わる。

## 共有（同期）の方法

同期の手段は **git**（またはファイル共有）。要望のフォルダ単位で push / pull すれば、その要望の状況を共有できる。
開発者はすでに認証済みで、履歴（誰がいつ状態を変えたか）、PR による Preflight 結果のレビュー、
1タスク1ファイルによる小さな差分がそのまま使える。排他制御は人が行う（同じ要望を同時に触らない）。

### 解決したこと

- **ID の衝突** — 要望は作成日 + 乱数、タスクは要望の中の連番にしたので、別々の人が作った要望どうしは衝突しない
- **状態がブランチごとに分岐する** — データはリポジトリの外のデータのフォルダに書く（リポジトリの中の `.pcube/` の場合も
  git のメインの作業ツリーのものに書く）。要望の作業ツリーの中で実行しても書き込み先は1か所で、今の要望はブランチ名から決まる

### 残っている課題

1. **データのフォルダの共有方法。** データがリポジトリの外に出たので、データのフォルダ自体を git リポジトリにして
   `pcube sync`（pull → commit → push）で同期する案が有力（コードの履歴にタスクの更新が混ざらない）。ファイル同期でもよい（TODO）
2. **rev による偽の衝突。** frontmatter の `rev` は、同じタスクの別々の項目を変えただけでも git のマージで衝突する。
   ファイル内容のハッシュによる楽観ロックに変えれば、`rev` をファイルに書かずに済む。要望単位で人が排他するので優先度は低い（TODO）
3. **git を使わないメンバー。** 閲覧だけなら、静的な HTML に書き出して共有する（`pcube export`、TODO）

## AI エージェントへの指示（`p3 init --agents` で AGENTS.md / CLAUDE.md に追記する内容）

```markdown
## タスク管理（infodb p3）

- 作業の単位は要望。タスクは `p3` CLI で操作し、`--json` で結果を読むこと（データのフォルダを直接編集しない）
- 変更するときは環境変数 `PCUBE_ACTOR=ai:<エージェント名>` を付ける
- 操作する要望は `--req <要望ID>` で指定する（要望の作業ツリーの中なら省ける）。まず `p3 whoami` で確かめる
- 着手するときは `p3 move T003 doing`、終えたら `p3 move T003 done --output <PR の URL など>`
- 作業中に新しく必要になった作業は `p3 new "<タイトル>" --body "..."` でタスクにする（人への質問はタスクにしない）
- 関係と影響範囲は `p3 show T003 --json` で確認し、`p3 link T004 depends_on T003` で張る
```
