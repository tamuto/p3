# 使い方ガイド

P3 で要望を1件、作るところから人が確認して閉じるところまで進める手順と、その後に引くためのリファレンス。
導入（Docker・ChatGPT の接続・パスの対応）が済んでいる前提で書く。まだなら [導入ガイド](installation.md) から。

- 前半「1件の要望を最後まで」: 同じ例の要望で、順に手を動かす
- 後半「リファレンス」: 状態・データ・画面・CLI の決まり

例に出てくる要望 ID（`261009-k7m3x`）・URL・ファイル名は架空のもの。自分の環境で出たものに置き換える。

## 役割と言葉

P3 では、人と AI エージェント（Claude Code・Codex など）が同じ CLI を使い、役割を分ける。

| すること | 誰が |
| --- | --- |
| 要望を書く | 人（AI も書ける） |
| Preflight（評価・細分化）を実行し、タスク案を選んでタスク化する | **人** |
| タスクに着手し、作業し、成果物と変更の記録を残して完了にする | AI（人でもよい） |
| 要望のタスクを全部終えたら、要望を「対応済」にする | 作業した側（AI など） |
| 成果物を確かめてタスクを「済み」にし、要望を「完了済」（か「見送り」）にする | **人** |

似た言葉を取り違えないように:

| 言葉 | 何の | 意味 |
| --- | --- | --- |
| 完了（`done`） | タスク | 作業した側が終えた（成果物がある） |
| 済み（`checkedAt`） | タスク | 人が成果物を確かめた。タスクボードから消え、「対応済み」の一覧に移る |
| 対応済（`resolved`） | 要望 | 作業した側が全タスクを終えた。人の確認待ち |
| 完了済（`done`） | 要望 | 人が確かめて閉じた |

## 1件の要望を最後まで

### 1. 要望を書く

CLI では（本文の箇条書きは、Preflight がタスク案を作るときの手がかりになる）:

```bash
p3 request new "通知機能を追加したい" --body "- メール送信基盤
- 通知設定画面"
# 作成: 261009-k7m3x  通知機能を追加したい
```

画面では、ヘッダーの「新しい要望」から書く。要望 ID は「作成日-乱数」で、後ろの5文字（`k7m3x`）だけでも指せる。

今の画面のスクリーンショットや仕様書の Excel があれば添付する（Preflight に渡す。後の「添付と画面資料」）:

```bash
p3 attach add 今の画面.png --description "今の一覧" --req k7m3x
```

### 2. Preflight を実行する

```bash
p3 preflight k7m3x          # Codex がリポジトリと過去の経緯を調べて評価し、タスク案を書く（終わるまで待つ）
```

画面では、要望の概要の「▶ Preflight を実行」。実行ログが流れ、終わると評価とタスク案が出る。

CLI など画面の外で Preflight を実行したときは、開いている要望の「概要・Preflight」が3秒ごとに最新の Preflight を確かめ、
実行ボタンの下に「新しい Preflight があります」（run の ID と、実行中・評価済み・失敗）を出す（再読み込みは要らない）。
表示中の評価・入力中のタイトル・本文・メモ・開いているタスク案の詳細はそのままで、「新しい run を開く」を押したときだけ
切り替わる（履歴の選択で選んでもよい）。`?run=` で前の run を開いているときは「表示中の評価は最新ではありません」。
確かめるのはこの画面を開いて、タブが見えている間だけ。確かめられなかったときは知らせと「もう一度確かめる」が出る
数分かかることがある。要望は「評価中」→「開始前」になる。

**止める・途中で止まった run**: 実行中の run は、画面の「中止」か `p3 preflight <要望> --cancel --run PF-...` で止める（最新でなくても、
履歴で選んだ run を止められる。成果物・ログは残る）。

- この serve で動いている run はすぐ止まる。別の serve・CLI で動いている run には中断を頼み、そのプロセスが止める（数秒待って、
  止まらなければ「中断を頼みました」のまま。`p3 drafts` と画面に「中断を頼んでいます」と出る）
- serve・CLI が途中で落ちると、run は実行中のまま残る。実行していたプロセスが終わったと確かめられれば、P3 が中断にする（serve を
  開いたとき・次に Preflight を始めるとき・`--cancel` のとき）。要望は評価中から元に戻り、すぐもう一度実行できる（画面には
  「中断した run」と理由が出る）
- 確かめられない run（以前の版で始めた run、別のマシン・コンテナで始めた run、Docker のコンテナを起動し直す前の run）は、動いて
  いないことを確かめてから、画面の「止まっていることを確かめて中断にする」か `--cancel --run PF-... --acknowledge-stopped` で中断に
  する。記録を残すだけで、プロセスやコンテナは止めない（動いているなら先にそちらを止める）。動いていると分かる run には使えない
- 完了した run は中断にしない。新しい run があるときに古い run を中断にしても、最新の run と要望の状態は変わらない
- 再実行のボタンは、表示している run ではなく要望の最新の run で決まる（古い run を見ていても、最新が実行中なら始めない）

### 3. 評価とタスク案を読む

```bash
p3 drafts k7m3x             # 評価（判定・妥当性・実現可能性・リスク・確認事項）、調べた範囲、判断の根拠、タスク案（D1, D2 ...）
```

画面では評価の下に、画面資料（UI を伴う案の画面イメージ）、メモ欄、調べた範囲・判断の根拠、タスク案が並ぶ。

- **判定**: go（着手できる）/ clarify（確認が要る）/ no_go（勧めない）
- **調べた範囲**: どのリポジトリ（参照先）を読めたか、git の履歴が使えたか。見ていない参照先に関わる判断は推測
- **判断の根拠**: 「確かめた」（読んだファイル・箇所・コミット）と「推測」を分けて出す
- **タスク案**: 1つの成果物（PR など）で終わる粒度。依存（← D1）と作業先のリポジトリが付く。案のファイル
  （`preflight/<run>/drafts/D1.md`）を直接直してもよい。画面でも題・作業先・採否を直せる。本文（作業内容・完了条件・
  判断の根拠・未確認）は、カードの「内容を見る」で開く詳細に、整形した Markdown で全文出る（読むだけ。見出し・箇条書き・
  コード・表・チェックリスト）。Escape か「閉じる」で一覧に戻る。不採用の案・タスク化した後・前の run の案も読める
- **受け入れ基準**: 案ごとに、完了したと確かめられる条件（`acceptanceCriteria`。A1, A2, ...）が付く。タスク化の前に
  `p3 criteria D1 --req k7m3x [--run <run>]`（`add` / `edit` / `rm` / `order`）か、案のファイルで直せる。タスク化すると
  採用した案の基準が ID ごとタスクに写る（[受け入れ基準と証拠](#受け入れ基準と証拠)）。基準が読めない案（空の文・重複した
  ID など）は理由が出て、直すまでタスク化できない。基準の無い前の run の案は、基準なしのタスクになる
- **題の直し方（画面）**: カードの題は、欄から離れると保存する（変えていなければ送らない）。ファイルや CLI など外で題が
  変わったら、再読み込み・タブに戻ったときに取り込む。直していない欄はそのまま最新になり、直している途中なら入力は残して
  「編集中に題が他で変わりました」と外の最新の題を出す。そのあいだは欄から離れても保存せず、「入力を捨てて最新にする」で
  最新から直し直す。画面が取り込む前に外で変わっていたときも、保存は断られて同じ知らせが出る（外の題は上書きしない）。
  保存していない題・保存中の題・競合中の題がある間はタスク化できない（見えている題と違う題でタスクを作らない）。
  タスク化した後の題は最新を出したまま直せない

### 4. 確認事項に答えて再評価する

確認事項に答えたいとき・方針を変えたいときは、**メモ** を書いて再評価する。前回の評価・案（人の直しと採否を含む）とメモが
資料として渡る。

```bash
p3 preflight k7m3x --note "対象は CLI だけ。Web は不要"      # メモを書いてから再評価
p3 preflight k7m3x --note - --note-only < answer.md          # メモを書くだけ（次の Preflight に渡す）
p3 notes k7m3x                                               # メモの一覧と、次に渡すもの
```

画面では評価の下のメモ欄に書いて「保存して再実行」。要望の本文そのものを直してもよい（後の「要望の本文を変えたとき」）。

### 5. 案を選んでタスクにする

```bash
p3 accept k7m3x --skip D3          # D3 以外をタスクにする（--only D1,D2 で選ぶこともできる）
# タスク化 (261009-k7m3x / PF-...):
#   T001  メール送信基盤
#   T002  通知設定画面  ← T001
```

画面では、案のチェックで採否を決めて「n 件をタスク化」。

- タスクは要望の中で連番（T001, T002, ...）になり、案の依存（`depends_on`）が付く
- 要望は「進行中」になり、作業先のリポジトリごとに **ブランチ名** が割り当てられる（例 `req/261009-k7m3x-notify`）。
  P3 は名前を決めるだけで、git のブランチや作業ツリーは作業する人・AI が作る。名前は `p3 request show k7m3x --brief` で見る
- 再評価で古いタスクを置き換える案があれば、置き換えられるタスクが出る。アーカイブするかは選べる（既定は残す。
  `--archive-superseded` か画面のチェック）
- 大きい要望は、タスク案ではなく **子の要望の案**（C1, C2, ...）が出ることがある（[親と子の要望](#親と子の要望)の「分割の案」）

### 6. 作業する（主に AI）

割り当てられたブランチ（作業ツリーでもよい）で作業する。**そのブランチの中で CLI を使うと、その要望が「今の要望」になり**、
`--req` を省ける。状態は常にデータのフォルダに書かれるので、ブランチごとに分かれない。

```bash
git switch -c req/261009-k7m3x-notify          # request show で見た実際の名前を使う。git worktree でもよい
export P3_ACTOR=ai:claude                      # 変更者の記録（AI は ai:<名前>）
p3 show T001 --brief --json                    # 本文・依存とその状態・作業先とブランチ・置き換えの注意
p3 move T001 doing                             # 着手
# ... 作業し、テストを通す ...
p3 move T001 done --output "src/notify.ts（送信）" --record - < record.md   # コミットする前に完了にする
p3 request set k7m3x status=resolved           # 最後のタスクなら、これもコミットの前に（7.）
git add src/notify.ts .p3/requests/261009-k7m3x   # データを git で管理していれば、要望のフォルダも同じコミットに
git commit -m "通知の送信" && git push
p3 move T001 done --output https://github.com/me/myapp/commit/<sha>   # URL は後から足す（完了・記録はそのまま）
git add .p3/requests/261009-k7m3x && git commit -m "成果物の URL" && git push
```

- **完了を記録してからコミットする**: テストを通したら、コミットの前に完了（と最後なら対応済）を保存する。データのフォルダが
  リポジトリの中にあって git で管理していれば、要望とタスク・変更の記録が実装と同じコミットに入り、PR / MR を見る人は
  「何を頼まれ、何をしたか」をコードと一緒に読める（後の AI のレビューでも、コードだけでなく目的とやったことを精査できる）
  - 親子でつながる要望のフォルダも、まだ入っていない変更があれば入れる。子の要望のコミットには祖先の要望のフォルダ（分割の採用・
    子の順・状態は親に残る）、親を対応済にするコミットには子孫の要望のフォルダ（見送りにした子など、実装の無い要望）。
    それ以外の要望の変更は入れない
  - 要望のフォルダは、マージするまで要望のブランチにしか無い。既定のブランチに切り替えると、その要望は一覧・進捗・親の子の一覧の
    どこにも出なくなる（作業ツリーから消える。データはブランチにある）。分割で作った子なら、親の詳細と `show` に「分割で作った子が
    見つかりません」（`hierarchyIssues` の `child_missing`）が出る。マージするか、そのブランチに切り替えれば戻る
- 成果物は、完了にする時点で今あるもの（変えたファイル・ドキュメントのパス・短い説明）。まだ無い URL や仮の SHA は書かない。
  コミット・PR / MR の URL は push してから `move … done --output <URL>` で足す（完了・記録・前の成果物・完了の日時は変わらず、
  要望も進行中に戻らない）。この追記は次のコミットに入れる（追記のコミット自身の URL は要らない）
- データのフォルダがリポジトリの外・別のリポジトリ・git で無視されているときは、同じコミットには入らない。git の作業ツリー
  （worktree）で作業していても、データは登録したフォルダ（既定はメインの作業ツリーの `.p3`）に書かれ、その作業ツリーのコミットには
  入らない。どちらもデータを移したり写したり `git add -f` したりせず、コードとは成果物の URL で結ぶ
- push に失敗しても、完了の記録はそのまま。公開できていないだけなので、直して push し直す

- 依存の相手が終わっていないタスクや、置き換えられたタスク（`※置換`）からは始めない
- **変更の記録**（`--record`）は、何を変えたか・なぜ・入れた決まり・やめたものを Markdown で短く書く。AI が完了にするときは必須。
  後の Preflight が経緯を調べるとき、タスクの解析・リリースノートの材料になる
- 作業中に見つかった別の作業は `p3 new "<題>" --body "..."` でタスクにする（人への質問はタスクにしない。チャットで聞く）

### 7. 要望を対応済にする

全タスクを完了にしたら、作業した側が要望を **対応済** にする（人に確認を頼む印）。最後のタスクのコミットの前にしておけば、
対応済も同じコミットに入る（6.）。

```bash
p3 request set k7m3x status=resolved
```

完了していないタスクがあると断られる（終わらせるか、不要なら人の了承を得てアーカイブする）。

### 8. 人が確認して閉じる

成果物（PR）を確かめ、マージする。

```bash
p3 check T001 --req k7m3x                      # タスクを「済み」にする（--off で外す）
p3 request set k7m3x status=done               # 要望を完了済にする（見送るなら rejected）
```

画面では、タスクボードの完了のカードの「✓ 済み」と、要望の概要のステータス。対応済の要望は、進捗の「確認待ち」で一覧できる。

## リファレンス

### プロジェクトと今の要望

**操作するプロジェクト** は、今いる場所と個人設定から決まる（環境変数では決めない）。上から順に見て、最初に当たったもの。
どれで決まったかは `p3 whoami` の「決まり方」（`--json` の `via`）に出る。

| 順 | `via` | 決まり方 |
| --- | --- | --- |
| 1 | `dir` | `--dir <データのフォルダ>` を付けた |
| 2 | `project` | `--project <名前>` を付けた |
| 3 | `cwd` | 登録した参照先（サブフォルダ・その git の作業ツリーを含む）か、データのフォルダの中 |
| 4 | `legacy` | 個人設定に登録していないリポジトリの中の `.p3/`（登録する前の clone など。登録すれば 3 で決まる） |
| 5 | `only` | 登録が1つだけなので、どこからでもそれ（今いる場所とは関係なく決まる） |

決まらなければ、登録済みのプロジェクトと選び方を出す。AI 向けの指示では、`via` が `cwd` でなければ操作を止めて人に確かめる。

`only`（登録が1つだけ）は p3 を使わないフォルダでも当たるので、そのときは **読むだけ** にする。変える操作は何も読み書きする前に
止まり（終了コード 1）、`--project <名前>` での明示と、リポジトリ・データのフォルダの中に移る方法を案内する。読むだけの操作は
標準エラーに同じ案内の警告を出して続ける（`--json` の標準出力には混ぜない）。

| 登録が1つだけで決まったとき | コマンド |
| --- | --- |
| 警告して続ける | `whoami`・`progress`・`ls`・`show`・`find`・`notes`・`drafts`、`request ls / show`、`milestone`（一覧）、`config`（表示）、`repo`（一覧）、`attach`（一覧）、`release-notes ls / show / export` |
| 止まる | 上のほか全部。要望・タスク・マイルストーン・設定・参照先の変更、`preflight`（`--note-only` も）、`accept`、`attach add / get / rm`（`get` はファイルを書く）、`release-notes generate / save`（`generate` は保存しなくても生成を始める）、`serve`（画面から変えられる） |

`init`・`project`・`user-config`・`chatgpt`・`codex`・`render` はプロジェクトを選ばないので対象外。

決まったプロジェクトの **データのフォルダと `project.yaml` が無い** と、CLI のどのコマンドも `serve` も、空のプロジェクトとして
開かずに終了コード 1 で止まる（何も作らない。`--json` でも空の結果は返さず、案内は標準エラーに出る）。フォルダの移動・共有ドライブの
切断・パスの誤りで、別の場所に書いてしまわないため。`requests/` は無くてよい。直し方は
[導入ガイド](installation.md#うまくいかないとき) の「うまくいかないとき」。

`p3 project` で一覧、`p3 project add <名前> <フォルダ>` で init せずに登録、`p3 project rm <名前>` で登録を外す（データは消さない）。

**今の要望** は `--req <要望>` → 環境変数 `P3_REQUEST` → 今いる参照先に割り当てたブランチ → ブランチ名の要望 ID の順で決まる
（パスに要望 ID が入っているだけでは決めない。detached HEAD では決めない）。`p3 whoami` で今の判定を見る。

**変更者** は `--actor` → `P3_ACTOR` → `human:<git の user.name>` の順。AI は `ai:<名前>` を名乗る。

### プロジェクトの設定

`p3 config`、画面の「設定」→「プロジェクトの基本」、`project.yaml` の直接編集のどれでも変えられる（コメントは残る）。

| 設定 | 使われ方 |
| --- | --- |
| `name` / `description` | 画面の表示と、Preflight の前提（説明が空だと画面に警告を出す） |
| `instructions`（`preflight.instructions`） | プロジェクト固有の評価の観点・制約。Codex への指示に加わる |
| `preflight.runner` | Preflight の担当: `codex`（既定。未設定もこれ）か `agent`。下の「Preflight の担当」 |
| `branchPattern` | 要望のブランチ名（既定 `req/{id}-{slug}`。作業先のリポジトリごとに同じ名前で割り当てる） |

#### Preflight の担当

誰が Preflight を実行するかを、プロジェクトで1つ決める（`project.yaml` の `preflight.runner`。`p3 init` で尋ね、Enter・`--yes` は
`codex`）。AI エージェント向けの使い方（スキルと AGENTS.md の節）は `p3 whoami --json` の `preflight.runner` を読んで手順を選ぶ。

| 担当 | 向いている環境 | Preflight の実行 |
| --- | --- | --- |
| `codex` | Codex（ChatGPT のプランと Docker）を使える | 人が `p3 preflight` か画面から実行し、Codex が評価する。AI は、人が対象の要望の手元の評価をはっきり頼んだときだけ評価する |
| `agent` | Codex を使えない（準備していない・ChatGPT のプランが無い） | 人がチャットで「Preflight して」と頼むと、手元の AI エージェントが評価する（下の「手元の対話エージェントで Preflight する」） |

```bash
p3 config set preflight.runner=agent     # codex に戻すなら preflight.runner=codex
p3 whoami                                 # Preflight     agent（手元の AI エージェントが評価する（頼まれたとき））
```

- どちらでも、AI が自分から Preflight を始めたり勧めたりはしない。タスク化（`accept`）は人が行う。Preflight を通さずにタスクを作る
  道も今までどおり使える
- 担当は AI 向けの手順を選ぶための方針で、`p3 preflight` のエンジン（このマシンの `preflight.engine`）や `--prepare` / `--complete`
  の動きは変えない。`codex` でも手元の評価はでき、`agent` でも人が `p3 preflight` を実行すれば Codex で評価する
- 個人（マシン）の設定での上書きは設けない（担当を共有の方針として1つに読めるようにする）。Codex を使えない人が `codex` の
  プロジェクトに参加しているときは、手元の評価をはっきり頼めば同じように評価できる
- `project.yaml` に読めない値が書いてあると、`whoami` は担当を決めずに（`runner: null`）直し方を出す。AI は `agent` と推測しない

マイルストーンは `p3 milestone add|set|rm` か画面のリリースノートの「マイルストーン」タブ（下の「リリースノートの画面」）、参照先は下の「参照先と作業先」。

### 参照先と作業先

**参照先** は Preflight の Codex が読むリポジトリ・フォルダで、数と名前は自由。`p3 init` が本体を登録する。ドキュメント・基盤・
依存しているライブラリなど、ほかのリポジトリも読ませたいときに足す。

- 共有の定義（`project.yaml` の `repos`）: 名前・役割・最初に読むか（`readFirst`）・作業先にできるか（`writable`）・主なフォルダ（`map`）
- このマシンのパス（個人設定）: 人によって違うので共有しない

```bash
p3 repo add docs /workspaces/docsrepo/guide role=ドキュメント   # リポジトリの中のサブフォルダでもよい
p3 repo add infra /workspaces/infrarepo role=基盤 writable=true
p3 repo ls                                      # このマシンのパスが無いものは「未登録」
p3 repo path docs ~/src/docsrepo/guide          # ほかの人が足した参照先に、自分のマシンのパスだけを登録する
p3 repo set infra role=基盤（Terraform）           # 共有の定義を変える
p3 repo rm infra --local                        # このマシンのパスだけ外す（rm だけなら共有の定義ごと消す。フォルダは消さない）
```

```yaml
# project.yaml（共有）
repos:
  app:
    role: システム本体
    readFirst: true
    writable: true
    map:                               # 主なフォルダ: どこから読むかの案内（全部を読む指示ではない）
      src/server: API とデータ
      src/web: { role: 画面, entry: src/web/main.tsx }   # 入口: そのフォルダで最初に読むファイル
  infra: { role: 基盤 }
```

- 「最初に読む」参照先の主なフォルダは、Preflight が評価の前に必要な範囲で読む（方針・設計・README など）
- 設定画面の「参照先」のタブでも同じことができる。このマシンのパスは、P3 を動かしているマシンのローカルの画面でだけ見え、変えられる
- Codex のコンテナでは、読める参照先を `/workspace/<名前>` に **読むだけで** マウントする。git の履歴が使えるのは、参照先が
  リポジトリの最上位のメインのチェックアウトのとき（git の作業ツリー・リポジトリの中のサブフォルダでは使えない）

**作業先**（タスクの `repo`）は、作業するリポジトリ（`writable` の参照先）か `none`（調査・人の判断など）。1つのタスクの作業先は1つ。
タスク化で、採用した案の作業先の分だけブランチ名を割り当てる。

```bash
p3 new "基盤の設定" --req <要望> --repo infra     # 作業先（none で作業先なし）。足りないブランチは割り当てる
p3 set T004 --req <要望> repo=app                 # 作業先を変える
p3 ls --req <要望> --repo infra                   # 作業先で絞る
p3 move T005 done --repo-output app=https://…/pull/1 --repo-output infra=https://…/pull/2   # 全部の PR を最後のタスクに
```

`areas` と根拠の参照は `<参照先>:<パス>`（例 `docs:guide/`）で書ける。名前なしは先頭の参照先の中のパス。

### Preflight を通さずにタスクを作る

小さく内容のはっきりした要望なら、Preflight を通さずにタスクを直接作ってよい。Docker や ChatGPT の接続が無い・Preflight が
止まる間も、同じ道で進められる（要望・タスク・変更の記録・マイルストーンは Docker も ChatGPT も使わない）。直接作ったタスクには、
Preflight の評価・細分化・根拠の調査・画面イメージは付かない。必要な調査と完了条件は、作る人が整理して本文に書く。

流れ: 要望を書く（1.）→ タスクを直接作る（下）→ 作業を始めるなら要望を進行中にする → いつもどおり作業・変更の記録・確認（6.〜8.）。

- **画面**: 要望のタスクボードの「＋ タスクを追加」（タスクが無くても出る）。題（必須。空白だけは不可）・本文（作業内容・
  完了条件）・作業先を書いて「作成」で、未着手のタスクになる。作業先は作業先にできる参照先か「作業先なし」から選び、
  既定は CLI と同じ（作業先にできる参照先が1つならそれ）。Enter で作成、Escape か「取消」で保存せずに閉じる。
  保存に失敗したときは入力が残り、タスクの一覧を読み直す（保存できたあとで失敗したこともあるので、同じタスクが未着手に
  できていないか確かめてから、もう一度作成する）
- **CLI**: `p3 new "<題>" --req <要望> --body "<作業内容と完了条件>"`（作業先は `--repo`。後の「参照先と作業先」）
- 関係（依存・置き換え）は張らない。順序が要るなら本文に書く
- 要望の状態は、下書き・評価中・開始前のときは変わらない。作業を始めるときは、概要のステータスを「進行中」にする
  （CLI は `p3 request set <要望> status=active`）。対応済の要望に足したときは進行中に戻る（後の「状態」）

**Preflight を使えないときの案内**: Docker が無い・デーモンに繋がらない・権限が無い、ChatGPT に未接続、使用量の上限、そのほかの
Codex の失敗のどれでも、止まった理由と直し方に並べて、この道を案内する。

- 画面: 概要のエンジンの状態が ✕ のとき・失敗した run に「Preflight を通さずにタスクを作成」（タスクボードのフォームが開く）。
  個人設定の ChatGPT の欄には、要望を開いてタスクボードで作る手順。エンジンの状態を確かめられなかった（通信の失敗）ときは、
  使えるとも使えないとも言えないので案内しない
- CLI: `p3 preflight` が始められなかった・失敗したときに、実際の要望 ID で `p3 new "タスクの題" --req <要望> --body "作業内容と完了条件"`
  を stderr に出す（`--project` / `--dir` を付けていればそのまま付ける）。終了コードと `--json` の stdout は変えない
- 取り消しただけの run（「中止しました」）・実行中は失敗と扱わず、案内しない

**後から Preflight を使えるようになったら**: その要望にも `p3 preflight <要望>`（画面は概要の「▶ Preflight を実行」）で評価できる。
実行しても既にあるタスクは変わらない。案をタスク化すると新しいタスクが増えるので、直接作ったタスクと重なる案は採らない
（5. で採否を選ぶ）。案が既にあるタスクを置き換えるとき（`supersedes`）は、同じ要望の中で人が採否とアーカイブを選ぶ
（後の「タスクの関係と置き換え」）。自動で置き換えたりまとめたりはしない

### 手元の対話エージェントで Preflight する

Codex（ChatGPT の接続と Docker）を使えないときは、手元の対話エージェント（Claude Code など）に評価させられる。P3 はモデルを
呼ばない（`claude -p` や API も使わない）。評価の指示は Codex と同じ原本から P3 が作り、エージェントはそれを読んで run のフォルダに
成果物を書き、P3 が通常と同じ取り込みをする。タスク化（accept）は今までどおり人が行う。

```bash
p3 preflight k7m3x --prepare --json
# → run（PF-...）・指示のファイル instructions・成果物のパス outputs・次のコマンド next
#   エージェントが instructions を読み、参照先を調べ、outputs（assessment.json・drafts/ など）を書く
p3 preflight k7m3x --complete --run PF-... --json    # 確かめて取り込む
p3 drafts k7m3x                                       # 評価とタスク案（人が読む）
p3 accept k7m3x                                       # 人がタスク化
```

- 準備（`--prepare`）は、評価対象・参照先・親子・添付・メモ・前回の結果を通常の Preflight と同じに固定し、要望を「評価中」にする。
  run は「実行中」（エンジン `local`）のまま、エージェントの評価を待つ。CLI を終えても残り、別のプロセス（画面・別の端末）から
  見える。待っている間は、同じ要望の Preflight（`--prepare`・通常の実行・画面の実行）を始められない
- 取り込み（`--complete`）は、その run の成果物だけを確かめる: 評価が JSON として読めるか、タスク案・子の案の形（キー・題・依存・
  作業先・混在）、成果物がシンボリックリンクでないか。問題があれば何も確定せず理由を出し（`--json` では `code: invalid_result` と
  `problems`、終了コード 1）、run は待ったまま。直して同じ `--complete` をやり直す。取り込み済みの run にもう一度 `--complete` しても
  何も変えない（`already: true`）
- 画面イメージの原稿（`ui/src/*.html`）があるときだけ、取り込みのときに P3 が描画のコンテナ（Docker）で PNG にする。Docker が
  使えなくても評価は残し、必要な画面イメージが足りなければ go を clarify にする（Codex のときと同じ）。原稿が無ければ Docker は使わない
- やめるとき・放置した run は `p3 preflight <要望> --cancel --run PF-...`（取り消し。成果物のファイルは残る）。要望の状態は元に戻る。
  手元のエージェントの run は、P3 がプロセスの終わりを見て中断にすることはない（プロセスを跨いで評価を待つため）
  どの run が待っているかは `p3 drafts <要望>`（最新の run）か、始められなかったときのメッセージに出る
- 評価のあとで要望を変えたら、通常の Preflight と同じくその評価からはタスク化できない（後の「要望の本文を変えたとき」）
- 手元のエージェントにはコンテナの囲いが無い。参照先を読むだけにすること・書き込みを run の成果物に限ることは指示で伝えるだけで、
  P3 は止められない（エージェントの権限の設定で守る）。どの程度の利用枠を使うかはエージェント側の契約による

**Claude Code のチャットで頼む**: 上の手順は、同梱のスキル（`.claude/skills/p3/SKILL.md`。後の「AI エージェントから使う」）に書いてある。
頼み方はプロジェクトの Preflight の担当（上の「Preflight の担当」）で変わる。エージェントは `p3 whoami --json` で担当を読む。

```text
# 担当が agent のとき（Codex を使えない環境）: 対象の要望を挙げて頼めばよい
要望 261009-k7m3x の Preflight をして

# 担当が codex のとき: 手元で評価してほしいことをはっきり頼む（「Preflight して」とだけ頼むと、p3 で実行するのか手元で評価するのかを聞き返す）
要望 261009-k7m3x の Preflight を Claude Code のこのチャットで実行して
```

- どちらの担当でも、エージェントは評価を取り込んで `p3 drafts` の要約を伝えたところで止まる。タスク化（`accept`）と着手は人が案を
  確かめてから。要望の登録やタスクの作業のついでに、エージェントから Preflight を始めたり勧めたりはしない。子の要望も同じ
- 担当を変えても、置いたスキルと AGENTS.md の節は置き直さなくてよい（実行のたびに `whoami` で読む）。以前の版のスキルを置いている
  リポジトリは、`p3 agents claude|codex|both` で同梱の版との違いを確かめ、最新にするなら選んだ先だけ `--force` で置き換える
  （ほかの文は残す。後の「AI エージェントから使う」）

- Claude Code はスキルに従って `--prepare` → 指示のファイルを読んで評価し、成果物を書く → `--complete` → `p3 drafts` の要約を返す、
  までを同じチャットで行う。タスク化（`accept`）とタスクの着手はしない（人が `p3 drafts` か画面で案を確かめてから `p3 accept`）。
  明示の依頼が無ければ（要望の登録だけなど）Preflight は始めない
- 要るもの: `p3` の CLI を実行できること（Bash）、データのフォルダと参照先を読めること、run のフォルダに書けること。データのフォルダや
  参照先がリポジトリの外にあるなら、Claude Code に読む場所として足す（`/add-dir <フォルダ>`・起動時の `--add-dir`・設定の
  `permissions.additionalDirectories`）。足さなければ、外のファイルを読む・書くたびに許可を求められる。参照先に書かせない設定
  （`permissions.deny` の `Edit(...)` など）にしておくと、指示だけに頼らずに済む
- スキルは、置いた後なら会話の途中でも読み直される。既に古いスキルを置いたプロジェクトは `p3 agents claude` で違いを確かめ、手で
  直していなければ `p3 agents claude --force` で最新にする（後の「AI エージェントから使う」）
- P3 は `claude -p` も API キーも使わない。今の対話セッションでエージェントが調べて書くので、Claude Code の契約の利用枠を使う
  （無料になるわけではない）。いつもの Codex の Preflight（Docker・ChatGPT）とは別の経路で、どちらで評価した run も同じに読める（エンジンは `local`）

### 要望の本文を変えたとき

要望のタイトル・本文は、いつでも書き換えられる（画面の「本文を編集」→「本文を保存」、CLI の `request set`）。

```bash
p3 request show k7m3x --brief --json            # rev を見る
p3 request set k7m3x --body - --rev 3 < body.md  # rev で楽観ロック（ほかで変わっていれば競合）
```

Preflight は始めたときの内容を固定して評価する。**評価のあとでタイトル・本文を変えると、その評価からはタスク化できない**ので、
もう一度 Preflight を実行する（前回の結果とメモは引き継がれ、変わった点も渡る）。タグ・期限・ステータスだけの変更は関係ない。
元の内容に戻せば、その評価からタスク化できる。既存のタスク・成果物は、本文を変えても消えない。

### 状態

**タスク** は 未着手（`todo`）/ 作業中（`doing`）/ 完了（`done`）の3つだけ。保留や取りやめの状態は持たず、手を付けないなら未着手の
まま、マージしないなら完了のまま（成果物の側で閉じる）。作業中にした・完了にした日時は P3 が記録する。予定の日付や見積りは持たない。

**要望**:

| 値 | 表示 | 誰が・いつ |
| --- | --- | --- |
| `draft` | 下書き | 作ったとき |
| `preflight` / `reviewed` | 評価中 / 開始前 | Preflight の実行中 / 評価が済みタスク化の前（自動） |
| `active` | 進行中 | タスク化したとき（自動）。対応済の要望に未完了のタスクができたときも戻る |
| `resolved` | 対応済 | 作業した側が全タスクを終えたら |
| `done` / `rejected` | 完了済 / 見送り | 人が決める |

- 対応済にできるのは、タスクが1件以上あり全部が完了のときだけ（人の「済み」や PR のマージは条件にしない）
- 対応済の要望にタスクを足した・完了から戻した・再評価をタスク化したときは、進行中に戻る
- 子のある要望は、自分のタスクと、見送り以外の子（その下も）が全部終わっているときだけ対応済・完了済にできる。自分のタスクが
  無く子だけでもよい（見送りの子は対象外）。子に未完了ができると対応済の親は進行中に戻り、完了済の親は変わらず警告が出る（[親と子の要望](#親と子の要望)）
- Preflight で状態が動くのはタスク化の前の要望だけ。進行中・完了の要望を再評価しても状態は変わらない

### タスクの関係と置き換え

関係は同じ要望の中の2つだけで、どちらも Preflight のタスク化が張る（手では張らない）。

| 種類 | 意味（A → B） | A に出る | B に出る |
| --- | --- | --- | --- |
| `depends_on` | A は B が先に終わっている必要がある | 依存先 B | 依存元 A |
| `supersedes` | A は B を置き換える（B は古い案） | 旧案 B | 新案 A |

置き換えられて残したタスクには、一覧（`※置換`）・ボードのカード・詳細に印が付き、作業中にすると警告が出る（移動はする）。
不要ならアーカイブする（`p3 archive T001`）。過去の経緯や別の要望とのつながりは、関係ではなく git の履歴と過去の要望・タスクの
ファイルから調べる。

### アーカイブしたタスクを見る

タスクの題・本文は `p3 set` や画面で直せるが、要らなくなった・やり方を変えるときは、アーカイブして新しいタスクを作る。
アーカイブしたタスクは、明示したときだけ読める（読むだけ。戻す・直すことはできない）。

画面では、要望の「アーカイブ」タブに一覧（ID・タイトル・アーカイブ前の状態・最終更新）が出る。行を押すと閲覧専用の詳細
（本文・変更の記録・成果物・作業先・日時・保存された関係）が開き、URL は `?archived=T003`（通常のタスクの詳細は `?task=T003`）。
詳細には保存・状態の変更・済み・作業先の変更・復元の操作は無い。通常のタスクの関係の相手（旧案など）がアーカイブされていれば、
関係の欄に「アーカイブ」と出て、そこから詳細を開ける（表示だけで、依存の完了扱いは変わらない）。読めないアーカイブのファイルは
一覧の上に件数と理由が出る。

CLI では:

```bash
p3 ls --archived --req <要望>        # 一覧（ID の順。読めないファイルは「読めない」に出る）
p3 show T003 --archived --req <要望>  # 本文・変更の記録・成果物・保存された関係
```

アーカイブしたタスクは、通常の一覧・タスクボード・進捗・対応済の判定・新しく作るレビューとリリースノートの材料には入らない
（どこで見えて、どこで見えないかは [設計](architecture.md#アーカイブしたタスク)）。表示される状態・最終更新はアーカイブする前の
最後の値で、アーカイブした日時ではない。

### 成果物と変更の記録

- **成果物**（`outputs`）: 1項目ずつ、PR / MR の URL・文章・ドキュメントのパスのどれでもよい。完了にするときは今あるもの
  （変えたファイルや説明）を書き、URL は push してから `move <T> done --output <URL>` で足す（完了のまま追記する）。項目全体が `http(s)://` の URL なら
  画面でリンクになる（文章の中の URL は拾わない）。足すのは `move <T> done --output 値`（繰り返し可。カンマで分けない）か画面の
  「成果物を編集」。`set <T> outputs=a,b` はカンマで分けて置き換える
- **リポジトリごとの成果物**（`repoOutputs`）: `--repo-output <参照先>=<URL>`。複数のリポジトリにまたがるときに最後のタスクに残す
- **変更の記録**（`record`）: 何を変えたか・なぜ・入れた決まり・やめたもの（Markdown）。`move <T> done --record 本文|-`、後から直すなら
  `set <T> --record ...`、画面のタスク詳細。`P3_ACTOR=ai:...` で完了にするときは必須（人は無くてもよい）

### 品質基準

プロジェクトとして守る最低限の水準（規約・構成・検証・文書・lint など）を、ID の付いた項目として project.yaml に書いておける。
未設定でも作業は続けられる。

```bash
p3 quality                          # 今の設定（未設定・設定済み・読めない）
p3 quality templates                # 同梱のテンプレート（basic@1 共通の基本 / typescript@1 TypeScript の例）
p3 quality template typescript      # 中身を見る
p3 quality adopt basic              # 写して採用する（編集できる実体になる）。空のまま設定するなら p3 quality init
p3 quality add --text "lint が警告なしで通る" --repo app --command "pnpm lint" --success "終了コード 0"   # 機械の検査
p3 quality add --text "画面の文言は用語集に従う" --reference "docs/glossary.md と照らす"                   # 人の確認
p3 quality exempt Q2 --reason "小さい CLI なので層が無い"   # 適用の除外（理由は必須）。unexempt で戻す
p3 quality set Q5 --repo all        # 対象を全部の参照先に戻す / rm Q4 で消す（ID は使い直さない）
```

- 画面では設定の「品質基準」のタブで、テンプレートの中身を確かめて編集中の一覧へ足し、対象・確認の方法・除外の理由を直して
  「品質基準を保存」。編集中に他で変わったら入力は残し、保存はさせない（「元に戻す」で最新を読む）
- P3 はコマンドを実行しない。確認は作業する側（人・AI・CI）が行う。テンプレートは例で、業界の標準への認証ではない
- テンプレートに新しい版が出ても採用済みの内容は変わらない。差分は `p3 quality` に出て、`p3 quality upgrade <テンプレート>` で当てる
- **タスクへの取り込み**: Preflight のタスク化と `p3 new`・「＋ タスクを追加」で、作業先に当てはまる品質基準が `[Q1] …` の受け入れ基準として
  入る（`p3 new --quality none` で入れない、`--quality Q1,Q2` で明示。作業先なしのタスクには明示したときだけ）。Preflight は始めた
  ときの品質基準を資料に固定する
- **設定を変えたとき**: 既存のタスクは自動では変わらない。`p3 criteria T003 quality` で差分を見て、`p3 criteria T003 quality import change:Q1`
  （省くと全部）で取り込む。画面ではタスク詳細の「品質基準との差分」で選んで「選んだ差分を取り込む」。変わった条件の証拠は再確認が必要になる
- 規則の詳細: [architecture.md の品質基準](architecture.md#品質基準)

### 止まっている理由

作業中のタスクが進められなくなったら（人の判断・権限が要る、前提が崩れた、テストが通らず先に進めない）、止まっている理由を付ける。
状態は作業中のまま（止まっていることは状態ではなく属性）。人は一覧・進捗で止まっているタスクを見つけ、答えて解除する。

```bash
p3 block T003 --reason "テストが通らず先に進めない" --decision "API の形を変えてよいか"   # 付ける（作業中だけ）
p3 block T003 --reason - < reason.md       # 内容を直す（止まった時刻は変えない）。- は標準入力（どれか1つ）
p3 ls --blocked --all                       # 止まっているタスクだけ（--status などと AND）
p3 progress                                 # 要望ごとに「⏸停止 n」。子のある要望は配下の停止も
p3 unblock T003 --resolution "形を変えてよい。互換の層は不要"   # 解除（回答・解決の内容は必須）
```

- 止まったままは未着手・完了へ動かせない（先に解除する）。解除しても状態は作業中のままで、自動では再開しない
- 付けた・直した・解除したことは履歴に残る（`p3 show T003` の「停止の履歴」）。同じ内容の付け直し・付いていない解除は何も変えない
- 理由・決めてほしいことは 2000 文字、回答・解決の内容は 4000 文字まで
- **画面**: タスク詳細の上部に停止の今の値（理由・いつから・付けた人・決めてほしいこと）と操作を出す。作業中なら「停止理由を付ける」、
  止まっていれば「停止内容を編集」「停止を解除」（回答・解決の内容を書いて「記録して停止を解除」）。履歴は「停止の履歴」で開く。
  タスクボードの作業中カードに「⏸ 停止中」・理由・決めてほしいことが出て、「停止中のみ」で止まっているカードだけにできる（列は増えない。
  「依存待ち」は依存先が未完了の別の印）。進捗は「停止中のみ」で止まっているタスクのある要望だけにし（親は文脈として残り、配下の停止の
  数が出る）、スケジュールの作業中の印は一時停止の形になる。条件は URL に残る。止まったまま未着手・完了へ動かすと断られ、解除を案内する
- **AI エージェント**（同梱のスキルと AGENTS.md / CLAUDE.md の節）は、続けられなくなったときだけ理由と決めてほしいことを付け、保存できた
  ことを確かめて人に伝えて作業を終える（止まったまま完了・済み・対応済に進めない）。回答を受けたら解除して再開する（人が先に解除して
  いれば履歴の回答を読む）。前に置いたスキル・節は自動では変わらないので、`p3 agents <claude|codex|both>` で違いを確かめ `--force` で更新する
- 規則の詳細・保存の形: [architecture.md の止まっている理由](architecture.md#止まっている理由停止)

### 受け入れ基準と証拠

タスクに **受け入れ基準**（何を満たせば完了か）を付けると、作業した側は完了するときに基準ごとの **証拠** を残し、人は「済み」に
する前に基準と証拠を並べて確かめられる。基準は任意で、無いタスクは今までどおり（「受け入れ基準なし」と出る）。

```bash
p3 new "通知設定画面" --criterion "設定を保存して再読み込みしても残る" --criterion "幅 375 で横にはみ出さない"
p3 criteria T004                       # 基準と証拠・不足
p3 criteria T004 add "キーボードだけで保存できる"   # ID は A1, A2, ... を振る（消した ID は使い直さない）
p3 criteria T004 edit A2 "幅 375 / 1280 で横にはみ出さない"
p3 criteria T004 rm A3                 # 証拠は「対応する基準のない証拠」として残る
p3 criteria T004 order A2 A1           # 今の ID を全部

# 完了と同時に証拠を残す（--record と標準入力を取り合わないよう、証拠はファイルか --evidence で）
p3 move T004 done --record - --evidence-file evidence.md < record.md
p3 move T004 done --evidence "A1=met:test/settings.test.ts" --evidence "A2=unverified:375 の端末が無い" --record ...
p3 evidence T004 A2 met --file a2.md   # 1項目ずつ（再記録は置き換え）。evidence T004 rm A2 で消す
```

証拠のファイルは、見出し `## <基準の ID> <結果>` ごとに次の見出しまでを本文として読む:

```markdown
## A1 met
- `pnpm -s check` が通った（test/settings.test.ts の「再読み込みしても残る」）

## A2 unverified
幅 1280 は確かめた。375 は端末が無く確かめていない
```

- 結果は `met`（満たした。本文が要る）/ `unmet`（満たせなかった）/ `unverified`（確かめていない）。証拠は作業した側の申告で、
  レビューの判定ではない
- 基準の文を変えると、その基準の証拠は「再確認が必要」になり、満たした数に入らない（記録し直す）
- 証拠なし・未達・未検証があっても完了・済み・対応済は拒まない。不足は `show` / `criteria` の「不足」、`--json` の
  `acceptance.shortfalls`、`move ... done` の stderr に出る
- 済みのタスクの基準・証拠の中身を変えると、済みが外れる（同じ値の再保存・成果物の URL の追加では外れない）
- ファイルを直接編集して読めない値になったら、`show` に「読めない」と出て、直すまで基準・証拠の操作はできない（ほかの更新では元の値が残る）
- 証拠は作業した側の申告で、レビューの判定ではない。変更の記録（`--record`）は何を変えたか・なぜ、証拠は基準ごとの確かめた材料
- AI エージェントは、着手する前に基準を読み、完了と同時に基準ごとの証拠を残し、未達・未検証を残して完了したら人に伝える
  （同梱のスキルと AGENTS.md / CLAUDE.md の節）。前に置いたスキル・節は自動では変わらないので、置いたプロジェクトで
  `p3 agents <claude|codex|both>` で違いを確かめ、`--force` で同梱の版にする
- 規則の詳細: [architecture.md の受け入れ基準と証拠](architecture.md#受け入れ基準と証拠)

### タスクの AI レビュー

完了したタスクについて、本文・受け入れ基準が成果物（コミットの差分）で満たされているかを、作業したのとは別の Codex のスレッドに
確かめさせる。人が「済み」にする前の材料で、作業した AI の能力・成績の評価ではない。結果はタスクの状態・済み・基準・証拠を変えず、
レビューだけでは済みにならない（不足があっても人は済みにできる）。

```bash
p3 review T004 --preview                                  # 今の材料（比較項目・比較対象・観点・注意・hash）を見るだけ
p3 review T004                                             # 成果物のコミットと比べる（終わるまで待つ。Ctrl-C で取り消す）
p3 review T004 --target app:1a2b3c4d                       # 比較対象を指定（カンマで複数。範囲は app:main..req/261009-k7m3x）
p3 review T004 --viewpoint app@1a2b3c4d:docs/REVIEW.md     # 観点を固定した SHA のファイルから（project で project.yaml の taskReview.viewpoints）
p3 reviews T004                                            # 履歴（アーカイブしたタスクも読める）
p3 review-show T004 TR-20261112-101500-ab12                # 1回分（項目ごとの判定・理由・根拠・不足・意図しない変更の候補・確かめる点・読めた範囲）
p3 review-cancel T004 TR-20261112-101500-ab12              # 取り消す（所有者を確かめられない run は --acknowledge-stopped）
```

- 判定は 満たしている / 不足 / 判断できない。「満たしている」はコード・差分の根拠があるときだけ（記録だけでは付かない）
- Codex には、固定した材料（差分と前後のコード）だけを読むだけで渡す。リポジトリやデータのフォルダはマウントしない。テストや
  アプリは動かさない。毎回新しいスレッドで、作業したスレッドは再開しない
- Preflight の担当が `agent` のプロジェクトでは、Codex で実行するなら `--engine codex`（画面では「Codex で実行する」）の明示が要る
- 材料が変わった（本文・基準・証拠・比較対象・観点）ら、新しい run としてレビューし直す。結果を直す操作は無い
- **画面**: タスク詳細の「タスクの AI レビュー」（作業した側の証拠とは別の欄）で、比較する対象・観点を選んで「材料を確かめる」と、
  比較項目・固定した SHA・観点の出典・注意と材料の hash が出る。「新しい Codex のスレッドでレビューを始める」はその hash で始め、
  確かめた後で材料が変わっていれば断られる（確かめ直す）。保存していない入力がある間は始められない。履歴は run ごとに選んで読み、
  実行中は取消（所有者を確かめられなければ明示の中断）、失敗・取消は理由が出る。今の本文・基準・証拠・比較対象・観点が実行したときと
  違えば「材料が変わりました」と出て、同じ指定で確かめ直せる（再レビューは新しい run）。未完了のタスクは始められず、アーカイブした
  タスクは履歴を読むだけ
- **品質**: 品質基準が設定してあれば、タスクの比較項目とは別に、レビューを始めたときの最新の品質基準ごとに「満たす・違反・判断
  できない・対象外（理由つき）」を出す。タスクに取り込んだ版と最新の差も材料と結果に出る（基準の改定による不足とコードの逸脱を
  分ける）。違反は「品質の指摘」として出る。検査のコマンドは実行しない。品質基準が未設定・古い記録では品質は評価しない
- 規則の詳細（比較対象・観点・上限・保存先）: [architecture.md のタスクの AI レビュー](architecture.md#タスクの-ai-レビュー材料)

### タグ・期限・マイルストーン

- **期限**（`due`）: 要望の期限（`--due YYYY-MM-DD`）。進捗のスケジュールに ⚑ で出る
- **マイルストーン**: まとめてリリースする単位（`p3 milestone add v0.2 --title "通知まわり" --due 2026-11-30`、要望に `--milestone v0.2`）。
  リリースノートはマイルストーンごとに作る（[リリースノート](#リリースノート)）
  - **並び**: 選ぶ欄（新しい要望・要望の概要）・進捗のまとまり・リリースノートの一覧・マイルストーンのタブ・`p3 milestone` / `progress` / `config` の
    一覧は、**ID のバージョンの降順**（新しいものが上）。比べるのは ID だけで（タイトル・期限・リリース済みかは見ない）、先頭の
    `v` / `V` は比べるときだけ外し、数字は数として比べる（`0.10.0` > `0.9.0`、`v2.0` > `v1.10` > `v1.9`）。バージョンでない ID も
    同じ規則で並べる（SemVer のプレリリースの順は持たない）。選ぶ欄の「（なし）」は先頭、進捗の「マイルストーンなし」と
    project.yaml に無いリリースノートは最後。リリースノートの画面は、指定（`?m=`）が無ければ先頭を開く
  - project.yaml の順は表示のために変えない（足した順のまま）。マイルストーンのタブは開いたときに降順に並べ、編集の間は行を動かさない
    （ID を書き換えても、足した行は最後のまま）。保存すると並べ直す
  - **目的と予定している機能・目標**: マイルストーンごとに、目指すこと（目的。複数行）と予定している機能・目標の一覧を書ける。
    どちらも任意で、片方だけでもよい。リリース済みにした後も、いつでも書き足し・直しができる。マイルストーンのレビューは、
    その時点で保存してある目的・予定機能を所属する要望と比べる（画面で書きかけの内容は使わない）

    ```bash
    p3 milestone purpose v0.2 --file 目的.md        # 目的を保存する（--body 本文|- でも。--off で外す）
    p3 milestone goal add v0.2 "通知の再送"          # 予定機能を足す（G1, G2, ... の ID が付く）
    p3 milestone goal set v0.2 G1 "通知の再送と失敗の記録"
    p3 milestone goal rm v0.2 G2
    p3 milestone show v0.2                          # 目的・予定機能を読む（--json は版 milestonesVersion も）
    ```

    予定機能の ID は足したときに振り、並べ替えや文言の変更で振り直さない（消した番号も、残っている最大の番号より小さければ
    使わない）。目的は 4000 文字、予定機能は 50 件・1件 500 文字まで。空の予定機能・重複した ID は保存を断る
- **タグ**（`tags`）: 外部 ID や分類の自由な文字列（例 `jira:PROJ-123`、`group:顧客A`）。同じ値を複数の要望に付けてグループにできる。
  要望・タスクの参照の代わりにはせず、外部のシステムとは同期しない
  - CLI: `request new --tag 値`（繰り返し可。カンマで分けない）、`request set <要望> --tag 値 ...`（この並びに置き換える）、
    `request set <要望> tags=a,b`（カンマで分ける）、`tags=` で全部外す、`request ls --tag 値`（どれかが付いている要望）
  - 画面: 値ごとに Enter で足し、× で外す（すぐ保存）。前後の空白は除き、同じ値は1つにまとめる。カンマ・空白・記号・日本語はそのまま
  - 進捗の絞り込み: 「タグ」から複数選ぶと、どれかが付いている要望（状態の絞り込みとは「かつ」）。URL は `?tags=`（JSON の配列）

### 親と子の要望

大きい要望は、子の要望に分けて、子ごとに Preflight・タスク・ブランチを持たせられる（分け方の基準と規則は
[architecture](architecture.md#大きい要望の分割親と子の要望)）。

```bash
p3 request new "通知の Lambda を作る" --parent k7m3x   # 子を作る。省いた期限・マイルストーン・タグは親から写す（後は別々）
p3 request ls --parent k7m3x                            # 直下の子（表示順）
p3 request show k7m3x --brief --json                    # parent・ancestors（根から順）・children（表示順・タスクの数つき）・hierarchyIssues
p3 request order k7m3x q2w8e a1b2c                      # 子の表示順を保存する（直下の子を全部、上から順に）。子を省くと今の並び
p3 request set q2w8e parent=a1b2c                       # 付け替え。parent= で外す
```

- 親にできないもの: 無い要望・自分・自分の子孫・アーカイブした要望・形の違う ID（終了コード 1、API は 409 `hierarchy_invalid`）。
  ほかの操作と重なったときは終了コード 3（API は 409 `hierarchy_busy`）で、そのままやり直してよい
- 子のある要望・親のある要望はアーカイブできない。子の親を外してから（`parent=`）アーカイブする
- `request.md` を直接編集して循環・無い親になったときは、`show` と画面の詳細に知らせ（`hierarchyIssues`）が出る。`parent` を直す
- **子の表示順**: 子は親の保存した表示順（親の `request.md` の `childOrder`）で並び、後ろの子を更新しても兄弟の位置は変わらない。
  保存した順に無い子（新しい子・付け替えて来た子・今までの親の子）は作成順で後ろに付く。概要・進捗・`show`・`request ls --parent`・
  API で同じ順（規則と例は [architecture](architecture.md#子の表示順)）
  - 保存は直下の子を全部並べる。同じ子が2回・無い要望は終了コード 1、直下でない子・足りない子（読んだ後に子が増えた・付け替えられた）
    と `--rev` の違いは終了コード 3（API は 409 `child_order_invalid`・`rev_conflict`）で、何も書かない。読み直して並べ直す
  - 外した子・付け替えた子は並びから消える（親のファイルは書き換えない）。同じ親に戻すと前の位置に戻るので、末尾にしたいなら
    並べ直して保存する。分割の採用で作った子は、既存の子の後ろに C1, C2, … の順で足される
  - 表示順は実行の順・着手できるかを表さない。子の前提（子の案の `requires`）は子の本文の「他の子との前提と契約」に残るので、
    着手の前に子の本文で確かめる（並びが前でも前提が済んでいるとは限らない）
- **分割の案**: 想定のタスクが 6 件以上か、独立したインフラ・運用・リリースの境界があると、Preflight は分けるか・分けないかと
  その理由を評価に書き（`p3 drafts` の「分割」）、分けるならタスク案の代わりに子の要望の案（`children/C1.md`。目的・範囲・範囲外・
  完了条件・分割の理由・他の子との前提・出典、想定のタスクの数、親の既存のタスクとの重なり）を出す。分けさせたくない・分けたいときは
  メモでそう書いて再評価する

  ```bash
  p3 drafts k7m3x                  # 分割の判断と子の案（[x] 採用 / [ ] 不採用、前提・重なり）
  p3 accept k7m3x --skip C3        # 選んだ案から下書きの子を作る（親は残す。子のタスク化・Preflight はしない）
  p3 preflight <子>                # 子ごとに Preflight → accept でタスクにする
  ```

  - 子の本文には、親の目的（採用のときの親の題と本文）と案の範囲・前提が入る。期限・マイルストーン・タグは親から写す
  - 親の題・本文が変わった、別の run から採用した・子を足したなどで子の集合が変わった run からは採用しない（`stale_input`）。
    子の Preflight も、親の題・本文が変わったら子のタスク化を断る。どちらも再評価する
  - 途中で失敗したら、作った子・失敗・まだの案が出る。直して同じ `accept` を実行すると続きから作る（作った子は作り直さず、消さない）
  - 画面: 要望の概要の Preflight に「子の要望への分割案」として、分割の判断（理由・想定のタスク数）と各案（想定のタスク数・前提・
    重なり。「目的・範囲・完了条件・前提を見る」で開閉）を出す。採否のチェック、「題・本文を直す」→「変更を保存」で直せる。
    「採用内容を確認」で作る子と親の扱い（親は残す・子は下書き・子の Preflight はまだ）を確かめてから「子の要望を n 件作成」
    （Escape・取消では何も作らない）。保存していない編集・本文や題・古い評価・案の問題・選んだ案が0件の間は押せない。作った子は
    リンクで開ける。途中で失敗したら、作った子と止まった案を出し、「続きを作る」で続ける
- 完了: 親は、自分のタスクが全部完了で、見送り以外の子（孫も）が全部 対応済か完了済のときだけ対応済（子のある要望は完了済も）に
  できる。自分のタスクが無く子だけの親もよい。子が全部見送りで自分のタスクも無い親はできない。自動では対応済・完了済にしない
- 子にタスクを足した・完了から戻した・子を進行中に戻した・対応済の親に未完了の子を足したときは、対応済の祖先が進行中に戻る
  （`reopenedAncestors`）。完了済の祖先は変えずに警告（`ancestor_done`）が出るので、再開するなら `request set <親> status=active`
- 画面: 要望の概要の「親子」で親を選ぶ・付け替える・外す（「親を保存」。失敗しても選んだ親は残る）。子の一覧（表示順・状態・
  自分のタスクの数・ボードへ）と、各子の「上へ」「下へ」で並べて「順序を保存」（保存するまでは下書きで、「取消」で戻す。保存に失敗しても
  並べた順は残る。キーボードでも操作できる）、この要望自身と配下全体のタスクの数、対応済にできない理由、見送りで対象外の子、完了済の祖先・親子の問題の知らせを出す。
  新しい要望の画面でも親を選べる。子の画面の見出しには祖先へのリンク（根から順）
- `p3 progress` は子のある要望に配下の集計（`[配下 完了/全部・子 n]`）を添える。マイルストーンの合計は各要望の自分のタスクだけを足す
- リリースノート: 子だけの親は「構造の要望」として収録の判定に入り（材料は無い）、材料は各要望の自分の変更の記録だけ。子が別の
  マイルストーンなら子の記録はそちらに入り、親はその子が終わるまで収録されない（一括完了もできない）

### リリースノート

マイルストーンごとに1件、そのマイルストーンに属する要望のタスクの **変更の記録** から機能の要約をまとめる。
生成した案は保存されず、人が確かめて直してから保存する。保存しても要望・タスク・マイルストーンの状態は変わらない。

```bash
p3 release-notes                              # マイルストーンごとのノートの有無と要望の数
p3 release-notes show v0.2                    # 対象の要望（収録 / 対象外）と警告、保存したノートと版
p3 release-notes generate v0.2 > draft.md     # 機能の要約の案（stdout は本文の案だけ。出典・材料の hash・進み具合は stderr）
# draft.md を確かめて直す
p3 release-notes save v0.2 --file draft.md --based-on <材料の hash>   # 新しく保存（--body 本文|- でもよい）
p3 release-notes show v0.2 --json             # 版（note.version）を見る
p3 release-notes save v0.2 --file draft.md --version <版>             # 直して保存し直す（版が違えば競合）
p3 release-notes export v0.2 > RELEASE.md     # 公開する本文だけ（出典は出さない）
```

- **収録する要望**: 対応済か完了済で、タスクが1件以上あり、全部が完了のもの。見送りは対象外（理由だけ）、それ以外の状態は
  **未完了** として警告して対象外。対応済・完了済でも完了していないタスクや読めないタスクがあれば、警告して対象外にする
- **要約の材料**: 収録する要望の、変更の記録のある完了したタスクだけ。記録の無いタスクは警告し、要望やタスクの本文で補わない。
  材料が1つも無ければ生成はせず（Codex を呼ばない）、本文を手で書いて保存する
- **生成**: Preflight と同じ Codex の接続（ChatGPT プラン）で頼む。渡すのはマイルストーンのタイトルと、要望・タスクの ID・タイトル・
  変更の記録だけ。結果の出典（要望・タスク）は P3 が確かめ、内部のパスらしいものは警告する。Ctrl-C で取り消せる。
  `--engine mock` は要約しない試し用（記録の1行目を並べる）
- **生成せずに手で書く**: 本文の保存は生成によらず、Docker も ChatGPT の接続も要らない。生成できない（Codex を使えない・
  使用量の上限・材料が無いなど）ときも、この手順で進める。画面では生成の欄の案内と、失敗したときの「本文を手で書く」から
  本文の欄へ進む（失敗・再生成しても入力は消えない）

  ```bash
  p3 release-notes show v0.2                    # 材料（収録する要望と変更の記録）を確かめる
  # 変更の記録を読んで、本文（Markdown）を notes.md に書く
  p3 release-notes save v0.2 --file notes.md    # 新しく保存する
  p3 release-notes show v0.2 --json             # 既にあるノートを更新するなら、版（note.version）を読む
  p3 release-notes save v0.2 --file notes.md --version <版>
  p3 release-notes export v0.2 > RELEASE.md
  ```

  `p3 release-notes generate` が始められない・失敗したときも、このコマンドを stderr に出す（取り消しただけなら出さない）
- **古い材料**: 生成や保存のあとで要望・タスクが変わると「材料が変わった」と知らせる（本文は自動では直さない）。
  必要なら生成し直して、確かめてから保存する
- **競合**: 保存したノートを直すときは、読んだときの版（`--version`）が要る。画面・エディタなど別のところで先に変わっていれば
  終了コード 3 で何も書かない。`show` で読み直してからやり直す
- **要望を一括で完了済にする**: リリースが終わったら、人がマイルストーンの要望の状態をまとめて閉じられる（対応済 → 完了済）。
  できるのは、見送りを除く全要望が収録の条件（対応済か完了済・タスクが全部完了・読めないタスクなし）を満たすときだけ。
  変えるのは対応済の要望だけで、完了済・見送り、タスク（済みを含む）、ノート、マイルストーン（リリース済み）は変えない。
  変更の記録が無い・ノートを保存していない・済みを付けていないことは条件にしない。ノートの保存・生成とは別の、明示の操作

  ```bash
  p3 release-notes show v0.2                    # 「要望の一括完了」に、できるか・できない理由・完了済にする要望と実行のコマンド
  p3 release-notes complete-requests v0.2 --based-on <材料の hash>   # show に出た hash で実行する
  ```

  - 確かめたあとで要望・タスクが変わっていれば（hash が違う）何も変えずに終了コード 3。できない（未完了がある）ときも何も
    変えずに終了コード 1。`show` で読み直してからやり直す
  - 1件ずつ書くので、途中で別の変更とぶつかる（要望が変わった・タスクが戻った）・書けないと、その要望で止まる。完了済にした
    もの・止まった要望と理由・まだ変えていないものを出す（戻さない）。直して `show` から読み直し、もう一度実行すれば残りを
    完了済にする（完了済にしたものは書き直さない）
  - 完了済にすると材料が変わるので、保存したノートには「材料が変わった」と出る（本文はそのまま）
  - 画面では、マイルストーンの「このマイルストーンの要望」の下の「要望の一括完了」。できないときは理由（要望ごと）と要望を開く
    導線を出し、ボタンは押せない。対象が無ければ「完了済にする要望はありません」。「要望を一括で完了済にする（N件）」で対象の
    要望と「タスクの済みは変えない」ことを確かめる欄を開き、キャンセルできる。実行の結果（完了済にした件数・途中で止まったときの
    完了済にした / 止まった / まだ変えていない）を出し、表示と進捗を取り直す。表示したあとで変わっていれば何も変えずに知らせる
    （自動では頼み直さない。内容を確かめてもう一度押す）。本文の入力は消えない
- **ファイル**: `<データのフォルダ>/release-notes/<マイルストーン>.md`（本文と、出典を書いた frontmatter）。エディタで直してもよい。
  壊すと「読めない」と出て、直すまで新しく保存しない。ノートのあるマイルストーンは消せない。保存の形と直し方は
  [docs/architecture.md](architecture.md#リリースノートのデータ)

### マイルストーンレビュー

マイルストーンの目的・予定している機能（[タグ・期限・マイルストーン](#タグ期限マイルストーン)）に対して、Preflight と同じく Codex が
参照先のリポジトリのコードと git の履歴を読み、実際にできあがったものが目的を果たしているか・何が足りないか・目的に無い変更
（意図しない変更）が入っていないかを確かめる。コードの品質の審査ではなく、機能の意図と目的に照らした確認。任意のときに何度でも
実行でき、実行しなくても要望の完了やリリースノートの操作には影響しない。結果は参考の記録で、リリースするかは人が読んで決める。

```bash
p3 milestone review v0.2                 # 実行して終わるまで待つ（進み具合は stderr。Ctrl-C で取り消す）。--engine mock は評価しない試し用
p3 milestone reviews v0.2                # 履歴（新しい順。状態・日時・判定の数）
p3 milestone review-show v0.2 <run>      # 1回分（評価したときの目的・材料・全体の所見・予定機能ごとの判定）
p3 milestone review-cancel v0.2 <run>    # 取り消す（ほかのプロセスの実行なら取消を頼む）
```

- **確かめる対象**: 参照先のリポジトリ（`p3 repo path` で登録したこのマシンのパス。Preflight と同じ）を、そのときの作業ツリーのまま
  読むだけで渡す。実行したときの HEAD・ブランチ・未コミットの変更の数と、タスクの成果物に残したコミット（`…/commit/<sha>`）が
  履歴にあるかを記録する。読める参照先が無ければ警告し、記録だけの点検になる（そのときは「達成」と判定しない）
- **手がかり**: 保存してある目的・予定機能（画面の書きかけは使わない）と、マイルストーンに直接属する要望の全部（見送り・未完了も）の
  本文、各タスクの本文・状態・変更の記録・成果物の参照。タスクの記録は実装した人（AI を含む）の自己申告なので、どこを見るかの
  手がかりにし、書いてあることはコードと履歴で確かめる。別のマイルストーンの親・子は文脈として渡すだけで成果に数えない。
  アーカイブした要望は含めない。成果物の URL や添付の中身は読まない
- **結果**: 全体の所見と、予定機能ごとの判定（達成・一部達成・未達成・判断材料不足）・理由・根拠・不足していること、目的・予定機能に
  無い変更（意図しない変更の候補）。根拠はコードの場所（`<参照先>:<パス>`・`<参照先>@<コミット>`）と要望・タスクの ID で、
  「達成」にはコードの根拠が要る（記録だけで達成とした結果や、参照先に無いパス・コミットを挙げた結果は使わず、失敗にする）。
  予定機能が無く目的だけなら、目的そのものを判定する。目的も予定機能も無ければ実行できない（先に書く案内が出る）。要望が 0 件でも
  実行でき、材料が無いことを記録する。タスクの完了数で達成を決めず、数値の達成率は出さない
- **確かめないこと**: テストやアプリを実際に動かすこと・公開されたか。結果の「範囲」にも書く
- **頼む先**: Preflight と同じ Codex の接続（ChatGPT プラン）。参照先は読むだけでマウントし、データのフォルダは渡さない。コードを読むので
  Preflight と同じくらい時間がかかる（上限 20 分）。失敗（認証なし・使用量の上限・時間切れ・形の違う結果）は失敗として記録し、
  前の成功結果はそのまま読める
- **同時に**: 同じマイルストーンで実行できるのは1つだけ（別の serve・CLI からも）。別のマイルストーンは同時に実行できる
- **止まった実行**: 実行していたプロセスが落ちたと確かめられれば自動で失敗にする。別のマシン・コンテナで始めたなどで確かめられない
  ときは実行中のまま残るので、止まっていると確かめてから `p3 milestone review-cancel <id> <run> --acknowledge-stopped`（画面では
  「止まっていることを確かめて中断」）で中断にする（記録を終えるだけで、ほかの環境のプロセスを止めたとは限らない）
- **履歴**: `<データのフォルダ>/milestone-reviews/<マイルストーン>/<run>/` に、比べた材料と結果をそのまま残す。後で目的や要望を
  直しても過去の記録は変わらない。履歴のあるマイルストーンは消せず、ID も変えられない

### 添付と画面資料

**添付**: 要望に PNG / JPEG / xlsx を付けて Preflight に渡す（今の画面のスクリーンショット・仕様書の Excel）。P3 は対象のアプリを
起動・撮影しないので、今の画面が要るときは撮った画像を添付する。

```bash
p3 attach add 今の画面.png --description "今の一覧" --source "本番の画面" --req <要望>
p3 request new "一覧に絞り込み" --attach 今の画面.png --attach 項目表.xlsx   # 作るときに添付する
p3 attach --req <要望>                          # 一覧
p3 attach get <A-ID> --out 項目表.xlsx          # 原本を書き出す（--run PF-... でその run に固定した原本）
p3 attach rm <A-ID>
```

- 形式は中身で確かめる。xls・xlsm（マクロつき）は扱わない。上限は1つの要望に 20 件・合計 100MB、画像 5MB（幅 4096・高さ 16384 px）、xlsx 20MB
- Preflight を始めるときに、そのときの添付を run に固定する（後で足し・消ししても過去の評価の資料は変わらない）
- xlsx は、P3 がセルの文字・保存済みの値と埋め込みの画像を取り出して渡す（数式は計算しない。図形・グラフは扱わない）

**画面資料**: UI を伴うタスク案には、Codex が画面イメージの原稿（HTML / CSS）を書き、P3 が PNG にして評価の下に出す
（提案・現状（添付）・仕様書から（xlsx の画像）に分けて並べる）。画像は「拡大」で大きく見られる。画像への意見はメモに書いて
再評価に渡す。必要な画面イメージが足りなければ、判定を go から clarify にして知らせる。原稿を自分で描くなら:

```bash
p3 render 画面.html --width 1280            # 画面.png ができる（幅 320〜2560 px・原稿 2MB まで。スクリプト・外部の参照は使えない。data: の画像はよい）
```

日本語は Noto CJK JP で描く（描画のイメージに入っているのは Noto CJK と欧文のフォントだけ）:

- ゴシック体の `sans-serif`・`system-ui` と、無いフォントの名前 `Noto Sans JP`・`Hiragino Sans`・`Hiragino Kaku Gothic ProN`・
  `ヒラギノ角ゴ ProN`・`Yu Gothic`・`游ゴシック` は Noto Sans CJK JP
- 明朝体の名前 `Noto Serif JP`・`Hiragino Mincho ProN`・`Yu Mincho`・`游明朝` は Noto Serif CJK JP、`monospace` は Noto Sans Mono CJK JP
- フォントを指定していない原稿は `sans-serif`（欧文は Liberation Sans、かな・漢字は Noto Sans CJK JP）。原稿の指定はどれもこれより優先する
- `serif` だけを指定すると、欧文は Liberation Serif、かな・漢字は Noto Sans CJK JP（ゴシック体）。明朝体にするなら上の名前を指定する
- ほかに明示したフォント（`Noto Sans CJK SC` など）と、`data:` で埋め込んだフォントはそのまま使う
- 描き方の決まりが変わると、次の描画で描画のイメージを作り直す。保存済みの PNG は描き直さない（新しく描くには Preflight をかけ直す）

### 画面

`p3 serve` で開く（既定 http://localhost:4310）。画面の状態は URL に載る。

`p3 serve --all-projects` で開くと、今いる場所のプロジェクトではなく、個人設定に登録したプロジェクト（`p3 project ls`）を跨いで
扱う。どのプロジェクトでも通常の serve と同じ操作ができる（閲覧専用ではない）。`--project` / `--dir` とは一緒に使えない。
登録を足した・外したら、画面で一覧を読み直せば反映する（serve の起動し直しは要らない）。同じデータのフォルダを複数の名前で
登録していると、どれも開かない（`p3 project rm <名前>` で1つにする）。決まりは [architecture](architecture.md#プロジェクトを跨ぐ-servep3-serve---all-projects)

- **選ぶ**: 入口（`/`）は登録したプロジェクトの一覧（行のどこを押しても開く）。登録が1つだけで開けるときは、一覧を飛ばして
  そのプロジェクトを開く（使えない登録や個人設定の読めない理由があるときは一覧に出す）。選ぶと `/projects/<名前>/...` になり、
  ほかの URL（要望・ボード・リリースノート・設定、`?task=` など）はこの下に今までどおり続く。URL を直接開く・再読み込み・戻るも効く
- **今のプロジェクト**: どの画面でも、ヘッダーのロゴの横（通常の serve でプロジェクト名を出す場所）の選ぶ欄に出る。ここで切り替える
  （選ぶ欄を開くと一覧を読み直す。狭い画面でも隠さず、長い名前は欄の幅で切る）。
  「プロジェクトの一覧…」では、登録が1つでも一覧を出す（`/?list`）。一覧は、戻ったとき・そのタブに戻ったときにも読み直すので、
  途中で足した・外した登録が出る
  作成・保存・Preflight は、ここに出ているプロジェクトにだけ届く。タブごとに別のプロジェクトを開いてもよい
- **切り替え**: ページごと移る。保存していない入力があれば「このプロジェクトに残る / 入力を破棄して切り替える」を選ぶ（破棄した
  入力はどこにも送らない）。送っている保存は、結果が決まるまで待ってから移る（待っている間はヘッダーの下に出し、選ぶ欄は押せない）。実行中の Preflight・生成は元のプロジェクトで続き、
  戻れば状態を読み直す（取消は表示中のプロジェクトの実行にだけ届く）
- **登録が変わったとき**: 開いている間にデータのフォルダを変えた・外した（CLI の `p3 project rm` / `add`）プロジェクトの画面からは
  保存しない。「登録が変わりました」と出るので、一覧から選び直す（入力は残すが、新しい登録先へ自動では送らない）
- **開けないとき**: 登録に無い・データのフォルダが無い・同じデータの重複などは、一覧に名前と理由を出す（ほかは選べる）。
  CLI で直して（`p3 project ls` / `add` / `rm`）、「一覧を読み直す」
- ChatGPT の接続とテーマはプロジェクトによらず共通（どのプロジェクトの設定画面からでも同じ）

| URL | 画面 |
| --- | --- |
| `/` | 進捗。左に要望、右にスケジュール。`?show=` で 未完了（既定）/ `resolved`（確認待ち）/ `closed`（完了済・見送り）/ `all`。`?tags=`。子の要望は親の下に字下げして、親の保存した表示順に並べ（▾ で畳む。根は更新の新しい順）、絞り込みに子だけが合うと親を「文脈」として出す。見出しの件数は絞り込みに合う要望の数で、文脈の親は数えない。子のある親には `配下 完了/全部` |
| `/requests/new` | 新しい要望（添付も） |
| `/requests/<要望>` | 要望の概要（タイトル・本文・期限・マイルストーン・タグ・親子・添付）と Preflight（`?run=PF-...` で過去の評価）。子の要望は見出しの上に祖先へのリンク |
| `/requests/<要望>/board` | タスクボード（V 字。ドラッグで列を移動。完了のカードの「✓ 済み」でボードから外す。「＋ タスクを追加」で直接作る） |
| `/requests/<要望>/done` | 対応済み（済みにしたタスクと成果物の一覧。要望の「対応済」とは別） |
| `/release-notes` | マイルストーンの管理（既定）・リリースノート（`?tab=notes&m=<マイルストーン>`）・マイルストーンレビュー（`?tab=review`、記録は `&run=<run>`）。下の「リリースノートの画面」 |
| `/settings` | 個人（ChatGPT の接続・テーマ）/ プロジェクトの基本 / 参照先（`?tab=personal|project|repos`） |

要望の中のページでは `?task=T003` でタスク詳細を重ねて開く。どのタブでも、見出しのタイトルの上に要望 ID と「コピー」が出る
（本文を下へ送っても見出しは残るので、上まで戻らずにコピーできる）。コピーできない（拒まれた・http で別のマシンから開いて
Clipboard API が無い）ときはそう出るので、ID をクリックして全体を選び、手でコピーする。

**受け入れ基準（画面）**: タスク詳細の「受け入れ基準と作業した側の証拠」に、基準ごとの結果（満たした・満たせなかった・未検証・
証拠なし・再確認が必要）と証拠が並ぶ。「済みにする」の近くに不足の数が出る（不足があっても済みにできる）。「証拠を登録 / 編集」で
1項目ずつ残し、「基準を編集 / 足す」で並び全体を直す（どちらも保存・取消）。保存していない入力がある間は済みを変えられない。
保存は編集を始めたときの rev で送り、他で変わっていれば入力を残して知らせる（「最新に合わせる」で保存し直す）。済みのタスクの
基準・証拠を変えると済みが外れ、理由が出る。タスク案の詳細（「内容を見る」）でもタスク化の前に基準を直せ、保存していない基準が
ある間はタスク化できない。「＋ タスクを追加」でも基準を入れられる。アーカイブの詳細では読むだけ

進捗のスケジュールの記号:

| 記号 | 意味 |
| --- | --- |
| ○ / ✓ | 完了にした日 / 人が確認して「済み」にしたもの |
| ◐ | 作業中にした日 |
| □ | 未着手のタスク（今日の線の右に、残りの数だけ） |
| ⚑ | 要望の期限（過ぎて未完了なら赤） |
| ◆ と縦の破線 | マイルストーン |
| 縦の線・丸囲みの日付 | 今日 |

印をクリックするとタスクの詳細が開く。ズーム（日 / 週 / 月）と「今日」ボタンで動かす。

**リリースノートの画面**（ヘッダーの「リリースノート」）: タブで「レビュー」「リリースノート」「マイルストーン」を切り替える
（`?tab=review` がレビューのタブ、`?tab=notes` がノートのタブ。無い・ほかの値はマイルストーン（管理）のタブ。タブを移っても `?m=` の選択と、書きかけの入力は残る。
保存していない変更があるタブには ● が付く）。

**マイルストーンのタブ**: ID・名前・期限・リリース済み・属する要望の数を一覧で直し、「＋ マイルストーンを追加」で足す（0 件から作れる）。
「保存」でまとめて project.yaml に書き、「元に戻す」で保存した内容に戻す。

- **リリース済み**: リリースが終わったらチェックを付けて保存する（外すのも同じ）。ノートの本文・要望・タスクは変わらない。
  ノートの保存や要望の一括完了でもリリース済みは変わらない（どれも別の操作）
- 要望が使っている・ノートのあるマイルストーンは、ID を変えられず消せない（理由が行に出る。CLI の `milestone rm` と同じ規則で、
  画面が古くても保存のときに止まり、理由が出る）。保存できなかったときは入力が残るので、直して保存し直す
- レビューの履歴のあるマイルストーンも、ID を変えられず消せない（理由が行に出る）
- 行の「目的・予定機能」を開くと、目的と予定している機能・目標を直せる（「＋ 予定機能を追加」・行ごとの「削除」。保存は
  ほかの項目と同じ「保存」）。閉じた行には目的・予定機能の有無と件数が出る
- 編集中にほかで変わったら、入力を残して知らせる（「入力を捨てて最新を読み直す」）。そのまま保存すると、編集を始めた後に
  変わったとして断られ（入力は残る）、ほかの変更を上書きしない。保存するのはマイルストーンだけで、
  設定の「プロジェクトの基本」（名前・説明など）とは互いに巻き戻さない
- project.yaml に無いマイルストーンのノートは、管理のタブでは定義として出さずに知らせる（ノートのタブで読める）

**レビューのタブ**: 左でマイルストーンを選ぶ（レビューの履歴だけが残る、project.yaml に無いマイルストーンも出る）。右に:

- **評価する内容**: 保存してある目的・予定している機能、所属する要望の件数と状態、別のマイルストーンの親子の数、確かめるコード
  （参照先ごとのブランチと HEAD・未コミットの変更・タスクに残したコミットの数。読めない参照先はその理由）、範囲と警告。
  「目的・予定機能を書く・直す」で「マイルストーン」タブへ移る。そのタブに保存していない変更があれば、レビューは保存した内容で
  行うと知らせる。目的も予定機能も無ければ書き方を案内し、「レビューを実行」は押せない
- 「レビューを実行」（履歴があれば「もう一度実行」）で始め、実行中は進み具合と「取消」が出る。実行しているプロセスを確かめられない
  実行には「止まっていることを確かめて中断」が出る（記録を終えるだけで、ほかの環境のプロセスを止めるとは限らない）
- **最新の実行**（実行中・失敗・取消のとき）と **最後の成功結果** を分けて出すので、実行中や失敗の後も前の結果を読める。結果は全体の所見と、
  予定機能ごとの判定（達成・一部達成・未達成・判断材料不足）・理由・根拠（コードの場所とコミット、今の要望・タスクへのリンク）・
  不足していること、目的・予定機能に無い変更（意図しない変更の候補）・範囲。「評価したときの材料」を開くと、そのときの目的・予定機能・
  参照先のコード（HEAD とタスクのコミット1件ずつ）・要望とタスクの文面（本文・変更の記録・成果物）を読める（後で直したり消したりしても残る）。評価した後に目的や要望、参照先の
  HEAD・未コミットの変更が変わっていれば知らせ、「今の内容でもう一度実行」できる
- **履歴**: 日時・状態・判定の数・評価した目的と予定機能を選んで読める（URL の `?run=` で開ける）。読めない記録も「読めない記録」として出す
- どの結果でも、要望の完了・リリースノートの保存・リリース済みの操作は今までどおりできる（レビューは参考の記録）

**リリースノートのタブ**: 左でマイルストーンを選ぶ（ノートの有無と要望の数）。右に:

- **このマイルストーンの要望**: 状態・収録 / 対象外（理由）・変更の記録の数・警告（未完了・記録なし・状態の食い違い）。
  タイトルで要望を開き、「変更の記録を見る」で要約の出典になるタスクの記録を確かめる（タスク名でタスクの詳細を開く）
- **機能の要約（案）**: 「機能の要約を生成」で生成する（生成中は「生成を取り消す」、失敗・取消は理由と「もう一度生成する」）。
  結果は項目ごとに出典を添えて出し、**編集欄には入れない**。「生成の結果を編集欄へ反映」で入れる（保存していない入力が
  あれば置き換えてよいか確かめる）。生成の間やあとで要望・タスクが変わると「古い材料からの案」と出る。材料が無ければ
  ボタンは押せず、手で書く案内が出る
- **本文**: 公開する Markdown を直して「保存」。保存しても要望やマイルストーンの状態は変わらない。「保存した本文を
  ダウンロード」は保存した本文だけ（未保存の変更・出典は含まない）
- **編集中にほかで保存・削除された / 読めなくなった**: 入力は残したまま赤い知らせが出て、その版では保存できない。
  「外で保存された本文を見る」で見比べ、「入力をコピー」してから「最新の本文を読み直す」で最新にして貼り直す。
  消されたときは「この入力で新しく保存する」を選べる（自動では作り直さない）。読めないときはファイルを直してから
  「もう一度読み込む」

**外での変更の取り込み**: CLI・AI・エディタ・git pull で変えたものは、ヘッダーの「再読み込み」で取り込む（タブやウィンドウに
戻ったときも1回読み直す）。ブラウザのリロードはしないので、入力中の内容は残る。画面同士の変更は自動で届く。
入力中に同じものがほかで変わったときは、入力を残して知らせ、保存は競合として止める（「入力を捨てて最新にする」で最新を見る）。

### 短い出力・JSON・終了コード

- `--json` で機械可読な出力（AI 向け）。`--brief` は作業に要る項目だけの短い出力（本文は切り詰めない）:
  - タスク: 本文・状態・rev・成果物・依存（`depends_on`）とその状態（`dependencies`）・置き換えの注意（`warnings`）・作業先とブランチ（`work`）・変更の記録
  - 要望: 本文・状態・rev・作業先ごとのブランチ（`branches`）・タスクの一覧・対応済なのに未完了のタスクがあるときの知らせ（`issue`）
- `dependencies` の相手が見つからない（アーカイブした・参照の誤り）ときは `title` と `status` が `null`（完了とは扱わない）
- `--rev <番号>` で楽観ロック（`set` / `move` / `request set`）
- 終了コード: 0 成功 / 1 使い方の誤り（次にすることが出る）/ 2 見つからない / 3 競合（読み直してやり直す）
- CLI はサーバを経由せずファイルに直接書く（serve が動いていなくてよい）

### データの持ち方

DB は無く、1タスク = 1 Markdown ファイル。人・AI・Codex が直接編集しても整合する（書き込みは直前に読み直し、古い rev なら止める）。

```
<データのフォルダ>/                     （既定はリポジトリのルートの .p3/。外に置いたなら例: ~/p3-data/myapp）
  project.yaml                          プロジェクト設定
  requests/
    261009-k7m3x/                       要望のフォルダ（作成日 + 乱数5文字。タイトルが変わっても変わらない）
      request.md                        要望
      tasks/T001.md, T002.md ...        タスク（要望の中の連番）
      tasks/.archive/                   アーカイブしたタスク（その ID は再利用しない）
      notes/N-....md                    Preflight へのメモ
      attachments/A-.../                添付
      preflight/PF-.../                 Preflight の記録（評価対象・評価・タスク案・画面資料・ログ）
    .archive/                           アーカイブした要望
  release-notes/v0.2.md                 リリースノート（マイルストーンごとに1件）
```

タスクファイルの例（`requests/261009-k7m3x/tasks/T003.md`）:

```markdown
---
id: T003
title: ファイル監視で外部編集を取り込む
status: done
areas: [src/core/store/workspace.ts]
outputs:
  - https://github.com/me/myapp/pull/42
startedAt: 2026-10-09T10:12:00.000Z         # 作業中にした日時（P3 が記録）
doneAt: 2026-10-09T15:40:00.000Z            # 完了にした日時（P3 が記録）
checkedAt: 2026-10-10T09:00:00.000Z         # 人が確認して「済み」にした日時
record: |                                    # 変更の記録
  - 外部の編集をファイル監視で取り込むようにした
  - 理由: CLI で直したタスクが画面に出なかった
acceptanceCriteria:                          # 受け入れ基準（任意。ID は P3 が振る）
  - { id: A1, text: CLI で直したタスクが画面に出る }
acceptanceEvidence:                          # 基準ごとの証拠（作業した側の申告）
  - criterionId: A1
    criterionText: CLI で直したタスクが画面に出る
    result: met
    evidence: test/watch.test.ts の「外部の編集を取り込む」
    recordedAt: 2026-10-09T15:39:00.000Z
    recordedBy: ai:claude
acceptanceSeq: 1                             # 振った最後の番号（消した ID を使い直さない）
relations:
  - { type: depends_on, target: T002, origin: preflight }
rev: 3
updatedBy: ai:claude
---

（本文: 作業内容と完了条件）
```

- 参照: 同じ要望の中は `T003`、別の要望は `<要望ID>/T003`、要望そのものは `<要望ID>`
- 要望 ID は乱数を含むので、複数人が別々に作っても衝突しない。ID の順は作った順を表さない
- 一覧の並び: 進捗は最終更新の新しい順、タスクは ID の順（T2 < T10）、Preflight の run は新しい順、メモは古い順、対応済みは済みにした新しい順

### AI エージェントから使う

AI にも CLI を使わせる（認証を持たせずに済む）。`p3 init --agents claude|codex|both`（値を省くと both）か、作った後なら
`p3 agents claude|codex|both` で、`AGENTS.md`（無ければ `CLAUDE.md`、どちらも無ければ `AGENTS.md` を作る）に短い使い方の節を足し、
詳しい手順のスキルを選んだ先に置く。どちらにも上の「役割と言葉」の役割が書いてある。置いたファイルはリポジトリに入れて共有する。

| 置く場所（リポジトリのルート） | 読む AI |
| --- | --- |
| `.claude/skills/p3/SKILL.md` | Claude Code |
| `.agents/skills/p3/SKILL.md` | Codex（今いるフォルダからリポジトリのルートまでの `.agents/skills` を読む） |

中身は同じ（同梱の原本 `skills/p3/SKILL.md` の写し）。ほかの AI が `.agents/skills` を読むかは確かめていない。
置くのはプロジェクトの中だけにする。個人のスキルの場所（`~/.claude/skills`・`~/.agents/skills`）に置くと、p3 を使わない
プロジェクトでも読まれ、関係ない作業で p3 を操作しかねない。

節のスキルの参照は、選んだ先と、リポジトリに既にある先だけを書く（無い先は書かない）。

**後から置く・最新にする（`p3 agents`）**: 今いるリポジトリのルート（サブフォルダからでも）に、選んだ先だけを扱う。プロジェクトは
決めず、データ・個人設定は変えない。選ばなかった先は作らず・変えず・消さない（チームで消した先は戻らない）。置く先は省けない。

| 今の状態 | `p3 agents <先>` | `p3 agents <先> --force` |
| --- | --- | --- |
| 無い | 作成（置く・節を足す） | 同じ |
| 同梱の版と同じ | 同一（何もしない） | 同じ |
| 違う（手で直した・古い版） | 保護（変えずに知らせる。スキルは違う行も出す） | 更新（スキルは同梱の版に、節は p3 の節だけを置き換え、前後の文は残す） |
| 節が複数・見出しになっていない | 保護（手で1つの節に整理するよう知らせる） | 同じ（変えない） |

- `--force` が上書きするのは、選んだ先のスキル（`SKILL.md`）と、`AGENTS.md` / `CLAUDE.md` の「タスク管理（infodb p3）」の節
  （その見出しから、同じか上の段の次の見出しの前まで。見出しの段はそのまま）だけ。手で直した分は消えるので、先に差分を見る
- 後から片方を足したときは、スキルは置き、節（前の参照のまま）は「保護」になる。両方を指す節にするなら `--force`
- チームで使うとき: 置いた・最新にした変更（`git diff`）をレビューしてコミットし、push して共有する。ほかの人は pull するだけで
  よい（参加の `p3 join` は AI 向けのファイルを書かない）
- 新しい版の P3 で手順が変わっても、置いたスキルと節は自動では変わらない（例: 完了をコミットの前にする順番）。`p3 agents <先>` で
  違いを確かめ、手で直していなければ `--force` で最新にする
- 以前の版との違い: 以前は `init --agents` で両方に置き、参加（init）のときも置き、登録済みのリポジトリで実行し直すと足りない方を
  置いていた。今は、置く先を選び、参加では置かず、後から置く・最新にするのは `p3 agents` だけ

ブラウザ用の REST API（`/api/...`、自己記述は `GET /api/ai/manifest`）もあるが、ローカルの画面のためのもの。

### CLI の一覧

| `p3 progress` | 要望ごとの進捗（マイルストーンごと。`--all` で完了・見送りも） |
| `p3 milestone ls\|show\|add\|set\|rm\|purpose\|goal` | マイルストーン（目的・予定している機能も） |
| `p3 milestone review\|reviews\|review-show\|review-cancel` | マイルストーンレビュー |

| `p3 ls` / `p3 show` / `p3 find` | タスクの一覧（`--all` で全要望）/ 詳細（`--brief`）/ 参照・タイトルで探す |
| `p3 new` / `p3 set` / `p3 move` / `p3 check` / `p3 archive` | タスクを足す / 直す / 状態を変える / 済みにする / アーカイブ |
| `p3 review <T>` / `p3 reviews <T>` / `p3 review-show <T> <run>` / `p3 review-cancel <T> <run>` | 完了したタスクの AI レビュー（[タスクの AI レビュー](#タスクの-ai-レビュー)） |
| `p3 quality` | 品質基準（テンプレート・採用・追加・変更・除外。[品質基準](#品質基準)） |
| `p3 block <T>` / `p3 unblock <T>` | 作業中のタスクに止まっている理由を付ける・直す / 解除する（[止まっている理由](#止まっている理由)） |
| `p3 criteria <T>` / `p3 evidence <T>` | 受け入れ基準を見る・足す・直す・消す・並べ替える / 基準ごとの証拠を残す・消す（[受け入れ基準と証拠](#受け入れ基準と証拠)） |
| `p3 preflight` / `p3 notes` / `p3 drafts` / `p3 accept` | Preflight の実行（`--note`。手元のエージェントなら `--prepare` / `--complete`。中断は `--cancel --run`）/ メモ / 評価とタスク案 / タスク化 |
| `p3 attach` / `p3 render` | 添付 / 画面イメージの描画 |
| `p3 chatgpt` / `p3 codex update` / `p3 serve` | ChatGPT の接続 / Codex のイメージ / 画面（`--all-projects` で登録したプロジェクトを跨ぐ） |
